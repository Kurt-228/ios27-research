# Device-stream builder для blit copy: оценочный дизайн

Дата: 2026-09-08 (обновлено 2026-09-09, N4 статика). Статус: **оценочный дизайн +
закрытая статическая разведка stream** (N4, §2.2) — имплементация не начата.
Контекст: `agx_queue_execution.md` §8 (вердикт «без энкодера AGXMetal исполнение из сырых
селекторов невозможно» — это стена, которую данный документ предлагает не обходить, а
воспроизводить), `agx_blit_stream.md` (статическая разметка blit copy), журналы part13/16/18
(v78–v112). Девайс и `fuzzer/` в рамках этого документа не менялись.

**TL;DR.** Мы умеем (v89, фаза `p_mtpatch`) читать и писать pool window и shmem живого
Metal command buffer'а, и исполнение пропатченных GPU-команд подтверждено на железе.
Blit copy — это CDM-диспатч встроенного compute-kerнела (`copy_buffer`), его байтовое
представление размечено статически на ~90 %. Предлагаемая архитектура v1 — **гибрид
«capture → template → replay на нашей type-1 очереди»**: снимаем валидный CDM-stream
и его таблицы с живого blit, параметризуем (GPUVA src/dst, size, offsets), прошиваем
через наш type-1 коннект (connect 0x1, рабочий сабмит-путь, kr 0). Ключевой аргумент
feasibility: control stream ссылается на driver/argument tables **pool-relative
32-битными offset'ами** (тег 0x100 в high dword, part13 §70), а не абсолютными GPUVA —
значит шаблон переносим в наш pool shmem без знания абсолютных адресов чужого контекста.
Оценка: **~5–10 дней** до первой подтверждённой GPU-записи через нашу очередь
(N4/v127 закрыл статически оба содержательных пробела: грамматику stream'а и
механизм привязки stream-страницы к kcmd — C2/C3 переоценены в §3.1);
главный неизвестный остался один — firmware-валидация содержимого
(статус 0 ≠ исполнение, v78).

## 1. Что строить в shmem побайтово: известное и неизвестное

Цель v1 — один `blit copy` (fill — частный случай) фиксированной конфигурации:
size 0x10000 (примитив v89 требует ровно этот размер; copy 0x4000 кодируется иначе
и pool-slot путь не использует — v91), один источник, один приёмник, без overlap,
без chunk-loop. Ниже — побайтовая раскладка того, что должно оказаться в нашем
shmem/pool, со статусом каждого блока.

### 1.1 Известно (подтверждено статически + живым capture)

**(a) Kernel cmd shmem** — командный буфер ядра, который наша очередь сабмитит
через trap0 (структура рабочая, kr 0; формат записей `{u32 type, u32 len}` —
part13). Для blit-пути содержит AGX-записи типов {3, 4, 0xb, 0xe, ...} + ссылки
на ресурсы. Записи копирования **GPUVA буферов не содержат** (проверены прямые,
сдвинутые и 32-бит формы, v89) — только внутренние ресурсы: bplist 0x1_000128000,
pool window 0x1_000138000, pool-слоты 0x1_000139480..498. Indirection:
«команда → pool slot → GPUVA».

**(b) CDM control stream** (capture-регион reg_10d460000, 0x130 байт packed AGX
packets) — по курсору `encoder+0x308`, первый токен **0x60000160**
(`BlitDispatchContext::blitCDMBuffer` @ `0x215028fd8`, AGXMetalG16G_B0). Ссылается
на таблицы **32-битными pool-relative offset'ами с тегом 0x100 в high dword** —
это и есть основание для переносимости шаблона.

**(c) BlitComputeDriverTable** (стек sp+0x108, ~0x80 байт, пулится через
`BlitUSCStateLoader::emitComputeProgramVariantArguments` @ `0x21503d164`):
+0x0c threadgroups = min(size, 0x400); +0x10 {1,1,1}; +0x18 size; +0x24 {1,1};
+0x38 size; +0x3c u32 0; +0x4c zeros(8); +0x60 {srcBase, dstBase} — **сюда
подставляются GPUVA наших ресурсов**; +0x74 `variant->0xca8 << 2`.

**(d) kDQuadParamTable** @ `0x2158398a8`: idx = min(clz(|srcOff−dstOff|), 4) →
{0x100, 0x200, 0x300, 0x800, 0xf00}. Правила нормализации: align 16, chunk ≤ 0x8000
(& ~0xf), threadgroups min(size, 0x400), overlap → chunk-loop. Для v1 (без overlap,
size 0x10000 ≤ 0x8000... см. риск — 0x10000 > 0x8000, значит для нашего размера
chunk-loop обязателен: два chunk'а по 0x8000; параметризатор обязан пересчитывать
по этим правилам).

**(e) Per-resource токены** 0x80 байт: тип из `[ctx+0x948 + kind*8]`, битмап
`[ctx+0x880]`.

**(f) Арена нашего коннекта**: pool-слоты окна **0x1_000138000+ доступны на запись
из процесса** (v89 WRITE CONFIRMED — именно туда Metal пишет {srcBase,dstBase}).
Арены data-driven (§8.5 `agx_queue_execution.md`), свои GPUVA валидны. Прямая
запись по GPUVA 0x10_* — DROP (v91).

**(g) Сабмит-путь нашей очереди**: kcmd нашего сабмита ссылается на наши shmem id
(seglist id1, kcmd id2), структура рабочая. Живой Metal пост-сабмит делает
sel 17/8/15 (macOS-нумерация) — аналоги на type-1 коннекте не закрыты.

### 1.2 Неизвестно (пробелы статической картины)

1. **Построчная разметка 0x130-байтного CDM control stream** — ✅ закрыта N4
   (§2.2): преамбула beginComputePass, reserve-механика, dispatch-цикл
   blitCDMBuffer, USC records emit'тера. Остаток чисто динамический: побайтная
   сверка построенного stream'а с capture (N1-расширение).
2. **Раскладка ArgumentTable** (sp+0x50 у blitCDMBuffer) — какие слоты какие
   буферы видят.
3. **Кто конвертирует CPU VA → GPUVA** и где точно ставится тег 0x100 — на пути
   `emitComputeProgramVariantArguments` есть шаг трансляции, не дизассемблированный.
4. **Как kcmd (ядерный уровень) ссылается на страницу, где лежит CDM control
   stream** — ✅ закрыт статически N4 (§2.2.5): через GPU VA в встроенном
   type-3 compute-дескрипторе (len 0x268), валидируемом kext'ом против
   зарегистрированных пулов; НЕ shmem id, НЕ пул-индекс, НЕ firmware-magic.
   Остаток: точечная динамическая верификация офсетов дескриптора в нашем
   собственном kcmd (см. обновление N3 в §2.1).
5. **Живёт ли 0x130 control stream в той же shmem-пул странице, что доступна нам
   на запись** (pool window 0x1_000138000+), или в отдельной, доступной только
   на чтение через курсор encoder+0x308. **Закрыто (v124, см. §2.0): в наших
   VM-регионах исполняемых полей НЕТ — только слот-таблица GPUVA; stream и
   DriverTable строятся драйвером вне снятого набора регионов.**
6. **Почему наша очередь исполняет «пустую» программу**: при verbatim-реплее
   эталонных байтов (v78 R1/R2/R3) — completion {0,5}/{0,0}, записи нет.
   Гипотеза part16 §79: kext при трансляции строит device stream из kernel cmd +
   ресурсов, и без корректных внутренних структур (bplist shader cache, pool
   таблицы) получается no-op. Template-replay эту гипотезу проверяет: мы несём
   с собой корректные таблицы, а не только kernel cmd.

## 2. Пробелы и план динамической разведки на девайсе

Всё ниже — существующие фазы и хелперы (`fuzzer/t_iosurface_scaler.m`), ничего нового
в fuzzer писать не требуется до старта имплементации; разведка = новые env-режимы
на базе `p_mtpatch` / `gscan_patch` / `p_mtlmut` и маркерные дампы через `devicectl`.

### 2.0 Результаты N1/N2 (v124, фаза dsrecon; `results/dsrecon/`, `results/run-dsrecon6.log`)

Снято 3 конфигурации blit copy в одном процессе (размеры 0x4000 / 0x10000 / 0x40000,
буферы A/B пересозданы между конфигами → GPUVA сдвинулись): kcmd shmem, seglist
и все VM-регионы, где скан нашёл gpuA/gpuB (4–6 регионов на конфиг, первые 16 KB
каждого), слепки до/после endEncoding. Кросс-конфиг qword-diff:

**Меняется между конфигурациями — ровно 4 сайта:**

| Сайт | Регион (CPU VA) | Поле | Значения по конфигам | Класс |
|---|---|---|---|---|
| pool0 +0x14a0 | 0x109158000 (0xc000) | gpuA (qword) | 0x1_000080000 / 0x1_000110000 / 0x1_000140000 | **GPUVA src** |
| pool0 +0x14a8 | 0x109158000 | gpuB (qword) | 0x1_000088000 / 0x1_000128000 / 0x1_000188000 | **GPUVA dst** |
| seg +0x108 | 0x1090f4000 | rid пары A/B (2×u32) | {0x15,0x16} / {0x23,0x24} / {0x25,0x26} | **residency rids** |
| seg +0x120 | 0x1090f4000 | sizeKB буферов (2×u32) | {0x10,0x10} / {0x40,0x40} / {0x100,0x100} | **size = size>>10** |

Самопроверка линейности (п.4 задачи): sizeKB = size/0x400 для всех трёх конфигов
точно (0x4000→0x10, 0x10000→0x40, 0x40000→0x100) — поле валидировано как
производное от размера копии. GPUVA-слоты валидированы совпадением с логом
(gpuA/gpuB по конфигам, по одному aligned-хиту каждый — больше НИГДЕ в дампах
gpuA/gpuB как qword нет).

**Константы (не меняются между конфигурациями размеров 0x4000/0x10000/0x40000):**

- **kcmd shmem целиком** — 0 отличающихся qword из 2048. Размер копии (и любые
  size-производные: threadgroups, chunk) в kernel cmd **не кодируется вовсе**.
  Значения 0x40000@+0x132, 0x400@+0x133, 0x10000@{+0xac,+0x177,+0x1cf,…} — константы
  (capacity/alloc-размеры), не параметры копии. kcmd — статический шаблон,
  reusable as-is для любого размера.
- kcmd/seg **байт-идентичны до и после endEncoding** — оба структуры полностью
  сформированы на этапе encode; endEncoding в них не пишет.
- Регионы 0x109800000, 0x10d400000, 0x16bf68000 — константы (в т.ч. «хиты»
  gpuA в них — stale-копии cfg0, не переписываемые в cfg1/cfg2). Регион
  0x10d800000 (cfg1/cfg2) — байтовое зеркало kcmd-региона.

**Ответ на открытый вопрос #2: исполняемые поля (DriverTable с size/threadgroups,
CDM control stream) в наших VM-регионах НЕ лежат.** Токен 0x60000160 не найден
ни в одном из 30 дампов; значения size (0x4000/0x10000/0x40000), threadgroups
0x400, chunk 0x4000/0x8000 как qword-параметры не присутствуют в kcmd/seg/pool*.
Что доступно нам на запись — только indirection-слой: слот-таблица GPUVA
(pool0 +0x14a0/+0x14a8) и residency-записи seglist (rids, sizeKB). Сам
DriverTable/stream строится драйвером в регионе вне снятого набора (ранее
известен как reg_10d460000, 0x130 байт) — видимо, на commit, либо в регионе,
не попавшем в скан. Следствия: (а) v89-style патчинг работал именно через
indirection — подтверждено; (б) **смена размера копии при replay требует
записи в DriverTable-регион — дамп N5** (полный VM-скан на момент после
commit + поиск size-значения; первый прогон v125 — см. §2.1, кластер-кандидат
найден, не верифицирован); при фиксированном размере (= capture size)
параметризатор обходится тремя сайтами выше.

### 2.1 План (остаток)

**Дамп N1 — полный байтовый snapshot blit-прохода (baseline template).** ✅ Закрыт (§2.0).
✅ Закрыт (§2.0). Фактический охват оказался шире/уже плана: сняты kcmd, seglist и
все GPUVA-hit регионы в 3 конфигурациях размера (0x4000/0x10000/0x40000) слепками
pre/post endEncoding; вместо окна 0x1_000138000 — его CPU-VA аналоги (регион
0x109158000 = слот-таблица GPUVA). Параметрические поля детектированы, список — в
таблице §2.0.

**Дамп N2 — дискриминация «константа vs указатель».** ✅ Закрыт (§2.0): GPUVA
присутствуют ровно в двух слотах (pool0 +0x14a0/+0x14a8), прямых GPUVA в kcmd/seg
нет (консистентно с v89); indirection «команда → pool slot → GPUVA» подтверждён
кросс-конфиг diff'ом. Ответ на вопрос #2 — отрицательный: исполняемый stream/DriverTable
в доступных регионах отсутствует, патчить придётся только indirection-слой
(как в v89) либо сначала найти DriverTable-регион (N5).

**Дамп N5 — локализация DriverTable (первый прогон, v125; частично).**
Полный VM-скан процесса ДО и ПОСЛЕ commit (blit 0x10000, gpuA 0x1_0001d0000,
gpuB 0x1_0001e8000; `results/run-dsrecon-n5.log`, дампы `results/dsrecon-post/`).
Pre: 75 регионов / 1245 хитов → post: 75 / 1257 (new-hits 24). Результаты:

1. **Кандидат найден, но НЕ подтверждён по дампам.** Лог фиксирует post-commit
   кластер в регионе **0x124400000** (RW, 0x400000): size(0x10000) @ +0x3a1f0/+0x3a1f8/
   +0x3a210/+0x3a290/+0x3a298, gpuA @ +0x3a208, gpuB @ +0x3a2a8 — всё в окне
   ~0x3a1f0..0x3a2b0 (~0x108 байт), появившемся только после commit. ОДНАКО дамп
   этого региона снят с окна 0x95600 (вокруг изолированного tgroups-хита +0x95e08)
   и **кластер 0x3a1f0 не покрыт** — верифицировать раскладку против карты
   (+0x0c/+0x18/+0x38/+0x60) по байтам невозможно. Относительные дельты кластера
   (gpuA→gpuB = 0xa0, size рядом с gpuA) с картой DriverTable из
   `agx_blit_stream.md` (gpuA@+0x60/gpuB@+0x68, дельта 0x8) **не сходятся** —
   либо это другая структура (resource records 0x80B?), либо раскладка в пуле
   иная, чем на стеке. **Требуется повторный дамп: окно 0x124400000+0x3a000.**
2. **Ложные срабатывания kind 3/4.** Кластер в 0x16b2f8000, который лог отнёс к
   gpuA/gpuB, по дампу — CPU-книжный массив (указатели heap 0x1e56ad518,
   0x1e81e5ca8… — userland VA, не GPUVA); kind-детектор, видимо, матчит пространство
   0x1_xxxxxxxx, а не точное значение. Единственные надёжные exact-match сигналы —
   kind 1 (size) и единичный kind 4 в 0x10d20c000 (см. п.3).
3. **Новая находка: kcmd-регион НЕ полностью статичен post-commit.** Сравнение
   слепка кcmd-региона post-commit (N5) с pre-commit показывает блок ~+0x3e0..+0x408,
   который был нулевым до сабмита и заполнен после: {1,1} @+0x3e0, **lo32(gpuB)
   = 0x1e8000 @+0x3ec**, {0x100, 0x28} @+0x3f0 (0x100 = size>>8 ✓), {0x200, 3}
   @+0x3f8, {0x64, 1} @+0x400. Т.е. kext при трансляции сам вписывает binding-
   записи в kcmd-регион. Следствие для replay: (а) поля этого блока в нашем
   шаблоне не обязаны быть корректными — kext перезапишет; (б) gpuA туда не
   вписан (только gpuB-lo32) — src подцепляется по-другому (rid? pool0-слот?);
   (в) точный список «kext-written» полей пока = этот блок + счётчики (+0xb0,
   +0x140, +0x168, +0x1d0, +0x1d8, +0x230, +0x240, +0x2c8, +0x2d0, +0x3a8,
   +0x3c8, +0x3d0), нужна чистая дифференциальная пара «до сабмита / после
   сабмита одного и того же cb».
4. **Записываемость 0x124400000+0x3a1f0 НЕ проверена** — дамп ≠ тест записи;
   нужен маркерный write-probe (как v89: записать, commit другого cb, readback/
   повторный дамп).

**Дамп N3 — привязка stream-страницы к kernel cmd (открытый вопрос #1).**
Статическая часть ✅ закрыта N4 (§2.2.5): привязка — GPU VA пул-страницы в
type-3 дескрипторе (len 0x268), встроенном в kcmd; слоты driver table на
стабильном офсете base+0x1480. Остаток динамический, объём эксперимента сжался:
в нашем post-commit kcmd найти qword нашего pool base (маркерный поиск по
известному VA нашей страницы), подменить его на вторую подготовленную страницу
(новый shmem через sel12) → сабмит → наблюдать status/completion. Это
верификация layout'а, а не разведка «есть ли ссылка вообще».
(Прежняя гипотеза «firmware сам находит stream по внутренним pool метаданным» —
снята: ссылки в дескрипторе достаточно, метаданные bplist не нужны.)

**Дамп N4 — сегмент beginComputePass/USC records.** ✅ Закрыт (v127, статика,
§2.2). Полная построчная разметка `beginComputePass`, `agxaReserveCDMTokenSpace`,
`blitCDMBuffer`, `emitComputeProgramVariantArguments`; ответ на открытый вопрос #1
(привязка stream-страницы к kcmd) получен статически и подтверждён байтами
post-commit kcmd (§2.2.5).

### 2.2 Результаты N4 (v127, дизасм AGXMetalG16G_B0 + сверка с dsrecon-post2)

Всё — VA из кэша macOS-референса. Срезы: `/tmp/n4_blitcdmbuffer.txt`,
`/tmp/n4_emit.txt`, `/tmp/n4_endcmd.txt` (полный дизасм функций).

#### 2.2.1 beginComputePass (0x21502ba60) — построчно

1. `newCommandEmb(size=0x330=816, [this+0x1334])` @ `0x21500d350` → rec (x21);
   обнуление rec:+0x68/+0x78/+0x88/+0x98; q0 из `0x2158373b0` → +0x94; нули
   +0xa4/+0xac/+0xb4; **`[this+0x60] = rec+0xc0`** (ComputeCommandRec —
   сериализуемая часть).
2. `[ctx+0x834] |= [this+0x1330]` (ctx = [this+0x8]); msgSend(rec+0xc0, w1=**0x268**
   =616) — слот под встраивание в kcmd (см. §2.2.5: post-commit kcmd содержит
   запись {len=0x268, type=3}).
3. Заполнение rec+0xc0: **[+0x00] = [ctx+0x318]+[ctx+0x308]** (CPU VA курсора CDM
   control stream); +0xd8/+0xf0/+0x60 = 0; strb +0x24c = 1; strh +0x248 = 0.
4. Резерв pass-заголовка: pool idx = `table32[0x21583a998][[ctx+0x770]-1]`
   (default 11); битмаска `1<<idx & 0x1fff00000490`; entry = `ctx+0x40+idx*32`
   {+0x00 limit, +0x08 cursor}; резерв **0x13 байт**; при нехватке
   `growNoInline` (`0x21500caa8`).
5. `ContextSwitcherGen3::setupComputeCommand` (`0x215066910`, this=`[this+0x18]`):
   резерв ~`this+0x7f` байт во втором пуле (idx из `table[0x21583a90c]`,
   entry {limit@0, base@8, cursor@0x10}), единственная запись —
   **rec+0x58 = pageAlign(pool cursor) + entry[+0x18], маска ~0x7f** — т.е.
   page-aligned GPU VA блока, куда пойдёт CDM-сегмент команды.
6. Debug-ветка ([this+0xf8] ≠ 0): msgSend tail, не основной путь.

#### 2.2.2 agxaReserveCDMTokenSpace (0x21500c624) — reserve-helper

Аргументы: w0=type (**0x16=22 — пул CDM control stream**), x1=allocator
(`ctx+0x18`), x2=size, w3/w4/w5=флаги, x6=config. Пул-энтри:
`allocator+0x28+type*32` = {+0x00 limit, +0x08 write cursor, +0x10 commit cursor}.

- Ремаппинг типа при `[allocator+0x75c]==1` (0x1f→0x2c; по `[allocator+0x758]`
  ∈{1,3,7} → 0x26/0x29/0x2c); битмаска допустимых пулов `0x1fff339e00000480`.
- Резерв size байт: growNoInline → resize(0x22) → **рекурсивный путь jump-токена**
  (w24=0xA0000000-маркер + ror-токен GPU VA, рекурсивный reserve(4), запись
  `(w5+1)&7` в новый курсор) — механизм межстраничных переходов stream'а.
- Флаг w3≠0: в позицию токена пишется **16-байт record** `{dword:
  ((gpu>>32)&0xffff)|0x20000000, dword: gpu_lo32, qword: CPU ptr}`
  (`getGPUAddress(type)` @ `0x21500ae9c` + `getPointer` @ `0x21500c994`).
- Иначе — 8-байт ror-токен: `{hi32: gpu_lo32|(1<<29), lo16: gpu_hi}` —
  тегированная GPU VA (именно такие tagged-формы видел part13 §71 как
  «32-бит offset с тегом в high dword»; фактический тег-бит здесь
  0x20000000/(1<<29), не 0x100).
- Возврата нет: курсор уезжает в [entry+0x10]; caller сам пишет токены
  через `[ctx+0x308]`.

#### 2.2.3 blitCDMBuffer (0x215028fd8) — полная последовательность записей

1. kDQuad: w11 = min(clz(|srcOff−dstOff|),4) (cap 4); w28 = kDQuadParamTable[w11]
   (0x100/0x200/0x300/0x800/0xf00 — ширина диспатча); chunk0 x21; x28 =
   (size−chunk0)>>w11 (число полных диспатчей); tail = остаток.
2. bindComputeResources (двухпроходный); если нет pending compute —
   `endPreviousBlitCommand(0)` + `beginComputePass(0)`.
3. **reserve(0x16, size=4) → dword 0x60000160 → [ctx+0x308] cursor**
   (сайт `0x2150291f8`). Порядок: токен 0x60000160 пишется ДО dispatch-цикла.
4. По каждому диспатчу (chunk0, x28×width, tail):
   - a. Резерв токен-региона: `ldp {limit,cursor}=[ctx+0xa0]`, cursor += **x27·2−1**
     (x27 = ширина kDQuad), store [ctx+0xb0]; growNoInline при нехватке.
   - b. База токен-региона: `x0 = align([ctx+0xa8]+x27, x27)`; **GPU VA =
     x0 + [ctx+0xb8]** — CPU→GPUVA трансляция одним вычитанием-дельтой
     (`0x215029470`); [ctx+0xa8] += x27 (чанк-степпинг src/dst).
   - c. **Per-resource токены** (0x80 байт): для каждого бита kind в
     `variant->0x880`: копия из `[variant+0x948+kind*8] + *(i32*)GOT[0x2701075d8]
     + 0x20` → resource list `[ctx+0x7a0]`. ВАЖНО: к шаблону токена
     прибавляется **процесс-глобальный signed delta** — релокация шаблонов
     под текущий пул (при переносе шаблона в наш пул delta пересчитывается).
   - d. `findOrCreateBlitProgramVariant(key)` — variant = скомпилированный
     copy_buffer (ключ: ветки 0x105/0x106 (+0x800000 для aux), вторая 5/6|w25).
   - e. **DriverTable sp+0x108** (0x80 байт, layout уточнён):
     +0x00 zeros(8); +0x08 u32 0; **+0x0c threadgroups=min(chunk,0x400)**;
     +0x10 {1,1}; +0x18 size; +0x1c {1,1}; +0x38 size; +0x3c 0; +0x44 zeros(8);
     **+0x60 {srcBase,dstBase}** (GPU VA пары, шагаются по чанкам);
     +0x74 variant->0xca8<<2. (Правка §2.3 agx_blit_stream: {1,1}@+0x1c и
     zeros(8)@+0x44, не +0x24/+0x4c.)
   - f. `emitComputeProgramVariantArguments(alloc1=blitctx+0x28, alloc2=ctx+0x18,
     variant, argTable=sp+0x50, driverTable=sp+0x108, w5=+0x74val,
     w6=threadgroups, w7=1, [sp]=ctx+0x7bc)`.
5. Spill-check `checkSpillParamsForCompute` перед каждым диспатчем.

#### 2.2.4 emitComputeProgramVariantArguments (0x21503d164) — USC records

- Резервы пулов alloc2: [x19+0xd8] += variant->0x730-диапазон+0x3f; [x19+0x98] +=
  variant->0x10+0x1f; [x19+0x2f8] += 0x28.
- USC-инструкции: `encodeImageBlockData` (`0x21503e38c`),
  `AGX3EncodedInstr<IotoInstruction_SPECLM_0>` (`0x21503e580`, слово
  0x100000000-based). **Shader binary reference**: код copy_buffer идёт из
  variant (поля +0x90 = таблица u32-индексов, +0x730 диапазон, +0x200/+0x208
  размеры); развёртка индексов → VA через argTable (`[argTable+idx*8]`,
  сайты `0x21503de20`–`0x21503deb8`) — argument buffer строится драйвером.
- **Shader state load**: `ESLStateLoadEncoderGen2::emitUscStateLoad
  <LdShdrTransformCompute>` (`0x2150a3ab0`) — USC-запись загрузки шейдера.
- **Workgroup setup — 0x28-байт USC record** в пул ([x19+0x2f0] cursor,
  `0x21503dcd4`–`0x21503dd20`): {w12=variant->0xc7c (&0xfff1ffff при !=2),
  w17=(w25>>16)|(variant->0xc80 & 0x3fffff)}, {counter++, variant->0xc88},
  **{driverTable->+0x18 (size), hi}, {driverTable->+0x20,
  driverTable->+0x0c & 0x7ff (threadgroups)}, {driverTable->+0x14 & 0x7ff, …}**.
  Т.е. driver table едет в stream ВЛОЖЕННЫМИ ПОЛЯМИ (не копией таблицы).
- **CDM link token**: `getGPUAddress(0x16)` → ror/mask/|0x20000000 → 8 байт
  в пул-22 страницу стрима (`0x21503dde0`) — ссылка стрима на саму страницу.
- Kick/завершение: `ContextCommon::endCommand` (`0x21500c30c`) — только
  resource-group bookkeeping; kick-токены сериализуются на commit из rec'ов.

#### 2.2.5 Ответ на открытый вопрос #1: привязка stream-страницы к kcmd

Статический ответ + байтовое подтверждение из `results/dsrecon-post2/
dsrecon-postcommit-kcmd.bin` (blit 0x10000, gpuB=0x1_0001e8000, post-commit):

1. **kcmd содержит встроенный compute-дескриптор**: запись {len=**0x268**,
   type=**3**} @ kcmd+0x150 — ровно 616 байт из beginComputePass (§2.2.1 п.2).
   Никакого shmem-id/пул-индекса для stream'а — дескриптор несёт адреса сам.
2. Дескриптор (старт +0x158) содержит:
   - kcmd+0x1cc: qword **0x1_00100000** — page-aligned GPU VA пул-страницы
     (база CDM stream/pool страницы);
   - kcmd+0x1e4..+0x1fc: qwords **0x1_00101480/488/490/498** — слоты driver
     table (= база страницы **+0x1480**). ПРОВЕРКА СТАБИЛЬНОСТИ: v89
     pool window 0x1_000138000 + 0x1480 = **0x1_000139480** — тот же офсет
     другого прогона ⇒ **+0x1480 — константа layout'а**;
   - kcmd+0x1d4: tagged dword-пары вида {0x000f0028, 0x00000001} — 32-бит
     offset с тегом в high dword (§2.2.2).
3. gpuA/gpuB в kcmd **отсутствуют** (прямые/сдвинутые/32-бит формы не найдены,
   N1) — indirection «дескриптор → пул-слот +0x1480 → gpuA/gpuB (pool0
   +0x14a0/+0x14a8)» подтверждён end-to-end.
4. kext-сторона: hw-парсер `0x8370d58` копирует 0xc0-байтный дескриптор и
   валидирует границы (0x100) + сумму ресурсных ссылок ≤0x3ff — т.е. GPU VA
   страницы валидируется против зарегистрированных пулов, **firmware не
   «находит» stream по магии** — ему дают VA в валидированном дескрипторе.
5. **Следствие для self-host replay** (заменяет гипотезу «воспроизвести
   bplist/pool метаданные», риск R2-ветка C3→v2): наш путь —
   (a) stream + driver table кладём в нашу пул-страницу (наш pool shmem,
       sel12 — регистрируется как ресурс сеглиста);
   (b) в type-3 дескриптор нашего kcmd пишем GPU VA нашей страницы
       (аналог +0x1cc) и слоты base+0x1480 (аналог +0x1e4..);
   (c) rid/sizeKB сеглиста по сайтам N1 (seg+0x108/+0x120);
   (d) kext-written блок kcmd +0x3e0..+0x408 (N5) можно не заполнять — kext
       вписывает post-commit сам.
   Остаток динамический (N3-точечно): layout нашего type-1/type-3 в kcmd может
   иметь другие относительные офсеты — маркерный эксперимент теперь точечный:
   искать в нашем post-commit kcmd qword «наш pool base» и патчить его,
   а не вслепую сканировать ссылки.

#### 2.2.6 Константность для фиксированного blit 0x10000 (srcOff=dstOff=0)

- **Константно (зашивается в шаблон)**: весь variant-derived слой (USC
  инструкции, shader state load, константы 0xc7c/0xc80/0xc88, +0xca8<<2),
  структура 0x28-байт USC records, kDQuad-разбиение (idx=4, width 0xf00),
  число диспатчей и их threadgroups=0x400 (при chunk ≥ 0x400), token-шаблоны
  0x80B (сдвинутые на delta), layout-офсеты (+0x1480 слотов, tagged-pair формы).
- **Параметрическое (пересчёт per-run)**: GPU VA пул-страницы (аналог +0x1cc),
  слоты base+0x1480.., {srcBase,dstBase} в driver table (+0x60), gpuA/gpuB
  в pool0 (+0x14a0/+0x14a8), rid-пары/sizeKB сеглиста (+0x108/+0x120),
  глобальный delta релокации токен-шаблонов (GOT[0x2701075d8]).
- Итого: 6 классов патчей против захваченного шаблона — столько же, сколько
  сайтов N1/N2 плюс дескрипторные VA. При фиксированном размере копии
  chunk-loop пересчитывать не нужно (детерминирован); смена размера = новые
  threadgroups/size-поля в driver table + возможно число диспатчей (§1.1d).

**Существующие фазы, переиспользуемые как есть:**
`p_mtpatch` (v89) — чтение/запись pool window и shmem живого cb, baseline стабильности;
`p_gpuvmscan` (v90/v91, FUZZ_GPUVMSCAN2, FUZZ_SCAN_WRITEONLY, FUZZ_SCAN_SKIP) —
VM-скан, read/write-зонды, дампы в results/gpuvm-dump/;
`p_mtlmut` (v112, FUZZ_MTLMUT SKIP/MAX/ONLY) — детерминированная нумерация кейсов,
xor-masked gpuA/gpuB, self-patch первым зондом, restore после кейса;
`p_pinned` (v92) — закрытый вектор, не используется; `relay/run_phase.sh` — раннер
(KEY=VAL argv, FUZZ_LOGFILE, детект самостоятельной смерти процесса).

C3 — самый рискованный блок был: если бы открытый вопрос #1 решился в сторону

### 3.2 Риски

- **R1. Firmware-валидация содержимого.** kext границы/счётчики не парсит, но
  firmware (RTKit) валидирует пакеты. Статус 0 ≠ исполнение (v78 R5: {0,0} без
  записи). Каждая итерация C4 требует readback-подтверждения, не completion-
  статуса. Митигация: маркерный readback встроен в критерий успеха (§4).
- **R2. Гипотеза part16 §79 не подтвердится.** Если no-op нашей очереди вызван не
  пустыми внутренними структурами, а отсутствием инициализации type-1 клиента
  (VM attach sel42/44/45, event setup — то, что Metal делает на своём коннекте,
  part16 §80), то правильный фикс — воспроизвести эту инициализацию ДО сабмита,
  а не строить stream. Это дешевле: sel42/44/45 давали kr 0 (v74). Закладывать
  +2–3 дня на прогон replay после полного VM-attach.
- **R3. PAC / подписанные указатели.** Внутренние структуры (bplist, pool
  метаданные) могут содержать PAC-подписанные CPU-указатели (на iPhone —
  arm64e). В capture-шаблоне они валидны только в контексте снятия; при переносе
  в наш коннекте подпись не сойдётся. Прямых наблюдений PAC-полей в blit-пути
  нет (таблица CPU-указателей 0x09_96xxxxxx в v90 — чистые VA, без тегов),
  оценка «низкая-вероятность, высокий эффект»: если всплывёт — пробел C3/C4
  удваивается.
- **R4. Per-build различия.** Вся разметка — AGXMetalG16G_B0 / iOS 27. На другом
  чипе/билде меняются kDQuadParamTable, токены, раскладка таблиц. Архитектура
  template-based устойчива (шаблон снимается на целевом билде), но статическая
  часть документа привязана к этому билду. Для fuzz-применения (цель проекта —
  один девайс/билд) приемлемо.
- **R5. Граничные случаи кодировки.** size > 0x8000 → chunk-loop (для 0x10000
  обязателен уже в v1), overlap → нормализация, threadgroups cap 0x400. При
  template-replay эти правила пересчитываются по §2.4 `agx_blit_stream.md`;
  ошибка в нормализации = silent no-op, диагностируется только readback'ом.
- **R6. Нестабильность нумерации зондов.** kcmd-internal ссылки плавают между
  прогонами (v90/v91) — resume только по адресу/хвосту лога, не по номеру кейса.

## 4. Минимальный критерий успеха и что это открывает

### 4.1 Критерий успеха (v1, одна команда)

> Наша type-1 очередь (connect 0x1) + наш построенный/параметризованный device
> stream → dst буфер (собственный ресурс нашего коннекта, rid пропатчен в
> residency) содержит паттерн источника, подтверждённый **CPU readback** через
> readback-механизм нашего клиента. Completion-статус — вторичен (из-за R1);
> первичен факт записи. Контроль чистоты: dst до сабмита занулён, источник
> заполнен маркером 0x41 (как в v89), readback показывает ≥ 99 % маркера.

Протокол приёмки, повторяющий v89: (1) zero dst; (2) submit; (3) drain completion;
(4) readback dst → сравнение с маркером; (5) отрицательный контроль — тот же
stream с dst GPUVA, сдвинутым на +0x100000 вне буфера (v89b: молчаливый drop),
доказывающий, что запись адресно-специфична, а не побочный эффект транслятора.

### 4.2 Что это открывает

1. **Снятие зависимости от живого Metal-контекста.** Сейчас единственный
   подтверждённый путь исполнения (v89/v90/v112) — in-place patch чужого command
   buffer'а: confused-deputy через Metal. Свой builder = исполнение GPU-команд
   из своего адресного пространства, без Metal в процессе вообще — тот же класс
   контроля, что и у kernel-эксплойта с GPU-примитивом, но из App-Sandbox.
2. **Произвольные команды, не только copy.** Шаблон generalizes: та же схема
   CDM-диспатча строит fill и, за рамками blit, любой compute-dispatch с
   известным pipeline (agx_cmd_template.h, magic 0x10000, subtype 3 — внутренняя
   compute-команда; сюда же p_mtlmutc v18 §57 с compute-вариантом mutator'а).
3. **Полный контроль над всеми полями команды** — то, что p_mtlmut (v112) делает
   мутациями по одному полю, builder делает конструированием: произвольные
   размеры, источники, threadgroups, множественные команды в одном сабмите
   (chained), чего mutation-fuzz физически не достигает.
4. **Честный фаззинг транслятора.** Пакет, целиком построенный нами, — единственный
   способ доставлять на вход firmware-валидации структуры, которых нет у живого
   Metal (невалидные токены, перекрывающиеся ресурсы, странные теги 0x100-offset'ов).
   v112 показал: валидация робастна к мутациям, но поверхность «с нуля» не
   фаззилась вовсе.
5. **Инфраструктурный задел.** Diff-capture (C1) и parameterizer (C2) — общие
   компоненты для любого будущего builder'а (render, compute c MSL-kerнелами).

### 4.3 Альтернативы и почему не они

- **IO-command path (sel41–48, `agx_io_command_path.md`)** — исполняется
  отдельным CPU-side путём (vnode read + shared events), не execution layer
  trap0/AGX. Для GPU-записи непригоден — закрыт как вектор.
- **Воспроизведение VM-attach инициализации Metal на type-0x100001 (v74, part16
  §80)** — остаётся дешёвым предварительным шагом (риск R2), но сам по себе не
  даёт stream'а: это снятие одного из кандидатных корней no-op, а не builder.
- **Построение с нуля (без capture)** — статический барьер снят N4 (§2.2):
  грамматика beginComputePass/USC records закрыта построчно, привязка страницы
  explicit. Для фиксированного copy_buffer capture всё же дешевле (6 классов
  патчей, §2.2.6), но v1 больше не блокирован «неизвестной грамматикой» —
  capture теперь нужен только как источник констант variant-слоя, а не как
  обязательный носитель формата.

### 4.4 Вероятность успеха гибридного replay (после N4 и ответа на #1)

До N4: привязка stream'а к kcmd была чёрным ящиком — оценка качественно
«низкая-средняя», риск C3→v2 (+3–5 дней) реален. После N4 (§2.2.5–2.2.6):

- **Механизм доставки известен end-to-end**: stream+driver table → наша пул-
  страница (sel12 shmem, регистрируется в сеглисте) → GPU VA страницы и слотов
  (base+0x1480, константа двух прогонов) в type-3 дескрипторе нашего kcmd →
  kext-валидация границ → firmware. Ни одного «магического» звена не осталось.
- **Остаточные неизвестные**: (1) побайтовая грамматика CDM-пакетов внутри
  stream'а — размечена на уровне генератора (какие записи, в каком порядке,
  какие поля), но не сверена с живым capture побайтово (нужен один diff-прогон
  N1-расширение); (2) firmware-валидация содержимого (R1) — несводима к
  статике; (3) точные относительные офсеты дескриптора в нашем kcmd.
- **Оценка**: при фиксированном blit 0x10000 успех критерия §4.1
  (CPU-readback ≥99 % маркера) — высокая (~70–80 %), главный провал-кандидат —
  неучтённое константное поле variant-слоя (лечится одним diff-прогоном против
  capture, дёшево), а не архитектурная стена. Смена размера копии — отдельный
  инкремент (chunk-loop пересчёт, §1.1d) после первого успеха фиксированного
  размера.
