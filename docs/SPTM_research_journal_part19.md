# Журнал, часть 19 (секция 107, 08.09.2026) — AGXUAT retirement: GPUVA reuse подтверждён, data-страницы в общем ядерном аллокаторе

## 107. v113: reclaim по статике AGXUAT (фаза p_uatrec, env FUZZ_UATREC)

Статика (внешняя, подтверждена дизасмом): destroy (trap1 sel1) → AGXUAT::queueUnmap
(32 слота, 33-й форсит AGXUAT::process): PTE clear, PT-страницы → inline GPU-арена
(два пула в __DATA_CONST), DATA-страницы дескриптора → IOMemoryDescriptor::release
→ общий kernel page allocator; tlbi aside1os (CPU DART); async firmware GMMU
invalidate — последним. Следствие: все прежние reclaim-спреи (v106-v110) ловили
не тот пул — GPU-арену, а data-страницы уходят в ядерный аллокатор.

### Эксперимент (results/run-uatrec1.log, фаза p_uatrec, fuzzer/t_iosurface_scaler.m)

**S1 (GPUVA reuse test)**: victim 0x10000 (rid 21, gpuva 0x10000080000) →
trap1-destroy (kr 0) + 40 junk destroy (форс AGXUAT::process) → немедленная
волна 16 ресурсов: **W0[0] получает ТОЧНО rid 21 и gpuva 0x10000080000** —
GPUVA/rid переиспользуются немедленно после process (LIFO). Следующие 10 —
в окне ±0x100000 (near). Волна +1с: дальше по арене, повторных точных хитов нет.
*** GPUVA REUSE CONFIRMED (путь через AGXUAT::process) ***

**S2 (write-after-reuse, 2 раунда: t+0 и t+1с)**: race_prepare (конгестия
8×16MB + пропатченный blit 0x41→V) → destroy victim + 40 junk флаш → волна
16 ресурсов 0x10000 (маркер 0x22), drain: оба раунда —
- контроль v105: старый маппинг victim = 65536×0x41 (write-after-destroy есть);
- волна: clean (ни 0x41, ни чужого контента); wave[0] НЕ получил gpuva victim'а
  (victim не был top-of-stack — конгестия/groom буферы созданы после него).

### Выводы

1. Виртуальный уровень переиспользуется мгновенно и предсказуемо (LIFO,
   первый аллок после process = точный rid+GPUVA victim'а) — GPUVA-groom
   возможен и детерминирован.
2. Data-страницы victim'а НЕ возвращаются в GPU-арену (волны clean) — уходят
   в общий kernel page allocator, как и предсказала статика. Там они лежат
   с нашим контентом (0x41 × 64KB), но CPU-наблюдение невозможно (userland
   страницы скрабятся при выдаче — v111/xpleak), а наблюдение в ядерных
   объектах требует kernel read-примитива, которого нет.
3. Запись in-flight blit'а легла в СТАРЫЕ страницы (старый маппинг = 0x41)
   при уже очищенных PTE — консистентно с окном «async GMMU invalidate
   последний» (stale TLB пишет в освобождённые страницы, уже ушедшие в
   ядерный аллокатор). Это физический phys-spray с полным контролем
   содержимого (байты буфера A) — ингредиент, ждущий примитив наблюдения.

### S3 (repoint-write, 3 раунда, results/run-uatrec-s3.log)

Victim строго top-of-stack, конгестия 24×16MB до commit'а victim-blit'а
(0x41→gpuvaV), destroy+флаш, волна до 32 ресурсов с заливкой 0x22:

- **wave[0] во всех 3 раундах получает ТОЧНЫЙ rid+GPUVA victim'а** (LIFO
  детерминирован даже при живой конгестии).
- **Reowner чист (0x22 65536, 0x41 = 0) во всех раундах; старый маппинг
  victim = 65536×0x41** — in-flight запись идёт через STALE GMMU TLB в
  старые страницы, а не через переуказанные PTE нового владельца.
- Окно stale-TLB покрывает весь цикл destroy→process→wave→drain
  (сотни мс) — async invalidate отстаёт минимум на этот порядок.

Вывод S3: write-into-reallocated-object через тот же GPUVA НЕ работает
(запись следует stale-трансляции, а не текущим PTE). Вектор «repoint-write»
закрыт; подтверждён и измерен единственный реальный путь — запись в
физические страницы, уже возвращённые в ядерный аллокатор (phys-spray с
полным контролем контента, окно ≥ сотни мс). Оружейная ценность завязана
на то, кто заберёт эти страницы до invalidate: другой GPU-клиент
(cross-process corruption) или ядерный объект (нужен kernel read для
наблюдения).

**Вывод по S4**: внешние эффекты коррелируют не с точностью патча, а с

серия крашей подряд, груминг под конкретного потребителя; цель — поднять

с коррелируемым маркером (USK_STLE) в дампе.

### Промежуточный итог вектора (stale-TLB cross-client spray)

Доказанная цепочка: destroy+flush при in-flight blit → страницы с нашим
контентом в ядерном аллокаторе (S1/S2/S3) → системные GPU-клиенты
(backboardd) их забирают, их очередь фолтится/рестартится (S4: kernel log
+ пользовательские фризы, воспроизводимо по заказу). Чего НЕ хватает до
эскалации: (a) контент-уровневая корреляция (маркер в чужом дампе) —
рестарты отчётов не пишут; (b) переход от per-queue fault (изолирован,
рестартится) к порче структур без per-queue containment (firmware/kernel
объекты). Идея: заливать не 0x41, а крафтленные DVA/дескриптор-паттерны —
чужой consumer, интерпретируя нашу страницу как GPU-структуру, сам пойдёт
по нашим адресам (fault requestor 208/209 в 03:52 уже читали по мусорным
«указателям» — канал управления адресом существует).

### Открытые follow-up (по убыванию ценности)

- Окно stale-GMMU-TLB (подтверждено широким, ≥сотни мс): если между PTE clear
  и GMMU invalidate страницы забирает ДРУГОЙ GPU-клиент (WindowServer,
  системная GPU-активность), запись с нашим контентом ложится в чужие
  страницы — cross-process GPU corruption. Груминг системной GPU-нагрузки
  параллельно с destroy+flush+in-flight blit; наблюдение: gpuEvent/паники/
  глитчи. Единственный живой путь «запись в чужое».
- ~~Repoint-write (волна ловит точный GPUVA)~~ — ЗАКРЫТ в S3: запись идёт
  через stale TLB в старые страницы, не через PTE нового владельца.
- Data-страницы в ядерном аллокаторе: без kernel read — парк.

**Прогон 6 (run-uatrec-s5-*, content steering, 10 итераций × 25 раундов,
NV=8×1MB, краш на 25-м; fill sweep: 0x4141…, 0x1_00000000,
0x3f01c80000, 0xfffffff007000000, 0x0)**: НОЛЬ системных эффектов — ни
GPURestarts в syslog, ни новых gpuEvent .ips, ни паник. После серий
кампаний fault-tolerance держится длительно (десятки минут): ранние
кампании на свежем устройстве продуктивны, повторные — глухие.
Вывод: для продуктивного прогона нужен сброс состояния (ребут) либо
длинный cooldown; steering по контенту не проверен именно потому, что
канал был закрыт иммунитетом — эксперимент повторить после ребута.

**Прогон 7 (run-uatrec-s6-*, ПОСЛЕ РЕБУТА, 5 fill-паттернов × 25 раундов,
NV=8×1MB, краш на 25-м)**: НОЛЬ эффектов — ни рестартов, ни gpuEvent, ни
паник, ни пользовательских наблюдений. Гипотеза «иммунитет» уточняется:
продуктивное состояние — это НЕ свежее устройство, а РАЗОГРЕТОЕ:
(a) дни фаззинга + активное использование (музыка/LTE/экран) фрагментируют
физ. аллокатор — наши freed-страницы реально переиспользуются чужими;
(b) per-app счётчик restarts у backboardd копится (Immunity выдаётся после
2+ рестартов в N сабмитов — видно по сообщениям) и на свежей системе
порог не достигнут. Следующий эксперимент: длинная priming-кампания на
свежей системе (сотни раундов с крашами) — проверить накопление.

## Промежуточная сводка примитивов (на 08.09)

Подтверждено: (1) scaler bug 210 panic DoS; (2) GPU read своего VM +
leftovers-leak при краше соседа по пулу; (3) GPU write в свои буферы по
произвольному GPUVA; (4) UAF write-after-free с полным контентом в freed
страницы ядерного аллокатора (stale GMMU TLB, окно ≥сотни мс); (5)
cross-process дестабилизация backboardd (GPU restarts, фризы, аудио) на
«тёплом» устройстве с пользовательской активностью; (6) детерминированный
GPUVA LIFO reuse после AGXUAT::process.
Закрыто на этой неделе: xpleak CPU-пути; repoint-write; leak-back в
service pages; sel27/sel9/sel7 глубокий фазз (204 кейса); sel27 downstream
(scaler/lock); mtlmut 3176-кейсовый план (3 app-kill точки, 0 паник);
restart-счётчики → panic (статика IOGPUFamily: эскалации нет by design).
Открытое направление эскалации: доставка нашего контента в структуры,
которые читает restart analysis (fence ring / stamp-таблицы) — целевой
путь к panic-assert'ам restartWorkQueue (287 веток) и getGuiltyChannel
«no guilty channel». И операционное: спрей-эффекты требуют тёплого
устройства с пользовательской GPU-активностью (музыка/экран/связь).

   живого mapped-объекта. Устройство в обоих случаях оставалось живым —

## 134. v147-v148: p_uatrec S5 — OOL-reclaim детектор; DATA-страницы ресурсов не уходят в общий аллокатор

   общий OOL-спрей с этими страницами не пересекается, контент при

Finding 3) — reclaim PT-страницы аллокацией с контролируемым контентом

достижимые целевые страницы либо наши, либо занулены. Для corruption
нужен reclaim PT-страницы или новый не-scrubbed слой.

волна первых 48 аллокаций брала младшие дырки, никогда не доходя до
жертвы. После переноса victim-переменной в **первую** аллокацию раунда

раундах — reclaim-путь реально активирован, и нули после этого

один size-class. Не-скрабленный слой существует, но лежит вне досягаемости
App-Sandbox: его аллокатор — внутренний пул драйвера, а разделяется он по
классам. Это согласуется со сканом (только free-ссылки) и закрывает
«cross-sizeclass» вариант §134 эмпирически, а не только статикой.
Следующая точка приложения усилий — не reclamation, а **write в live-объект
другого домена** (Scaler DVA-груминг §7.4: формула записи известна,
блокер — оракул чужих DVA, `GetAllocations` MACF-denied, §116).

## 136. v150-v151: scaler с ЧУЖИМ dst-id — cross-process запись невозможна

Идея, которой не было в проекте: все cross-surface попытки упирались в

### (a) jitbox-угон (запись в jitbox-дескриптор) — ЦЕЛЬ В ЯДРЕ XNU

Журнал §31.1 называл владельца дескриптора «IOKit OSObject (vtable

обработчик не выполнялся). Entitlement-гейт (`taskCanUsePool`) дал бы 0x2e2,
до него не дошли. Статика: строки «Memory pool ids exhausted», «Unable to
pre-allocate IOSurfaceMemoryPool memory», «Bucket buffer size», сайт
`IOSurfaceMemoryPool` подтверждают пул с bucket-аллокацией и **проверкой
«descriptor length isn't rounded to bucket size»** — то есть нужный
under-allocation класс там есть, но формат sel49 на iOS не восстановлен:
в iOS-кексте нет строк имён методов (в macOS-версии есть), symtab пуста
(stripped kext), GOT-ссылки не резолвятся офлайн. Восстановление формата
требует либо живого подбора структуры, либо реверса обфусцированной
таблицы диспатча. Не начинаем без понимания цены.

### (c) Entitlement'ы provisioning profile — расширение не помогает

Профиль `276VZS46K5` (dev, до 2027-08-11) содержит **45 entitlement'ов**,
включая kernel-класс: `com.apple.developer.kernel.extended-virtual-addressing`,
`kernel.increased-memory-limit`, `increased-debugging-memory-limit`.
Собрал приложение со **всеми 45** — девайс принял, приложение запустилось.

Результат: **битмаска entitlement'ов IOSurface не изменилась**
(`sel13 init`: `ff 3f 00 00 7f 00 00 00` — идентично baseline). Нужных для
наших целей `com.apple.private.iosurfaceinfo`,
`com.apple.private.IOSurface.protected-access`,
`com.apple.private.gpu-restricted`, `IOSurfaceMemoryPoolEntitlement` в
профиле **нет**, а они и не выдаются стороннему разработчику. Entitlement'ы
профиля не расширяют доступ к IOSurface/AGX-поверхности.

Вывод: **класс «добавить entitlement'ы и получить новую поверхность»
исчерпан** — Apple-приватные entitlement'ы недоступны без их выдачи Apple.
`ent.plist` возвращён к исходному (эксперимент дал ровно ноль).

### Сводка

Три вектора, давшие «нет» на разведку: jitbox-угон (цель в vm_map),
memory_pool (недостижим до handler'а, формат неизвестен), entitlement'ы
(профиля недостаточно). Ни один из них не является «недостаточно изучен» —
каждый упёрся в конкретное, проверенное препятствие.

### (d) v153: memory_pool — восстановление формата sel49 безуспешно, вектор закрыт

Попытка восстановить формат `s_create_memory_pool` (sel49) четырьмя
способами:

1. **Таблица диспатча офлайн.** В `__DATA_CONST` iOS-кекста **нет ни одного
   значения 3176** (маркер `stOut` поверхностей) ⇒ поля `checkStruct*` не
   лежат в макOS-раскладке `IOExternalMethodDispatch2022`. Поиск таблицы по
   «непрерывный регион мелких целых» даёт ложные срабатывания (выглядят как
   PAC-vtable'ы соседних объектов). Symtab пуста (stripped kext), строк имён
   методов нет. **Офлайн-восстановление невозможно** без реверса
   обфусцированной таблицы диспатча.
2. **Живой свип размера** (4..1024, шаг 4): все 256 значений → `0x2c2`.
3. **Перебор точки входа**: `IOCoreSurfaceRoot` в этом запуске не находится
   (находится `IOSurfaceRoot` type 0 — тот же клиент, что и в p_coresurf);
   type 0/1/2 на IOSurfaceRoot — type 0 единственный открывающийся.
4. **Решающий контроль отказов** (это то, что дало ответ). Сравнили
   заведомо-хорошие селекторы с pool-селекторами на том же клиенте:

| вызов | kr |
|---|---|
| sel6 create, 32 B (верный размер по документации) | 0x2bd |
| sel6 create, 31 B (неверный размер) | 0x2c2 |
| sel13 init, 0 B | 0x2c2 |
| sel49 pool, 32 / 160 / 3176 B | 0x2c2 |
| sel50/51/52, 32 B | 0x2c2 |

Вывод: **pool-селекторы неотличимы от отказа по правам** — тот же код, что
даёт «неверный размер». Отдельно всплыло, что и наш baseline-sel6 create
на этой фазе отдаёт `0x2bd`, то есть документальный layout sel6 на iOS тоже
не воспроизводится «как есть» (это отдельная поправка к §108: `sel6`
с 32-байтным входом по карте macOS на iOS 27.0b4 НЕ создаёт поверхность).

**Вердикт: memory_pool закрыт.** Требуется Apple-приватный entitlement
(`IOSurfaceMemoryPoolEntitlement`, §137c) — получить его сторонним
разработчиком нельзя, а внутри доступного пространства отказ неотличим от
«формат неверен», и перебор размеров ничего не различает. Статически
подтверждённый баг-класс («Descriptor length isn't rounded to bucket size»)
остаётся **недостижимым**: гейт стоит раньше.

## 138. v154: p_afterdeath — IOSurface sel7: поверхность АЛИАСИТ клиентскую память (cross-process класс)

### Смена класса цели

Все закрытые векторы (scaler §136, jitbox §137a, memory_pool §137d,
reclaim §134–135) упирались в одно: **нельзя ни записать по своему
адресу, ни увидеть чужую цель**. GPU/IOSurface-класс для этого не годится.
Новый класс: **zero-copy alias клиентской памяти через ядро** — механизм
`sel7 create_surface_client_mem`, документированный в
docs/iosurface_sel_formats.md §4 и никогда не проверенный на живом iOS.

`IOSurface::parse_properties` → `IOMemoryDescriptor::withAddressRange(addr,
size, kIODirectionOutIn, owningTask)`: поверхность не копирует данные, а
разделяет страницы вызывающего процесса. Дескриптор удерживает ссылки на
эти страницы, значит **поверхность может пережить создавшую задачу** —
инверсия модели владения, на которую упирались все прошлые векторы.

### Методологическая заметка (ошибка парсинга → SIGSEGV)

Первые прогоны падали SIGSEGV, и девайв ушёл в corpse-throttle
(`kernel: Corpse failure, too many 6`), из-за чего диагностика ушла в
side-трек на перезагрузку. Реальная причина — в моём разборе
`IOSurfaceLockResult`: я брал `bpr`/`total` как u32 по +0x14/+0x10, получил
`alloc = 8022656` (7.6 МБ) при клиентском буфере 256 КБ и затем читал за
его пределами. Правильный layout: word0 = CPU base, word3 = sid,
**word4 = alloc size** (совпало с нашим 0x40000 = 262144).

Второй урок того же класса: `run_phase.sh` не создавал лог, и это выглядело
как «фаза не запускается». На деле процесс **переживал** таймаут, а лог не
успевал быть вычитан. Диагностика через прямой `devicectl copy` дала полный
лог с первой попытки. Правило: если лог пуст, проверять процесс отдельно
(`device info processes`), а не делать вывод о падении фазы.

### Результат (run-ad-direct, /tmp → results/run-afterdeath-final.log)

```
[ad] client buffer 0x107224000 size 0x40000 filled 0xad
[ad] sel7 -> kr 0x00000000 sid 14 *** SURFACE ALIASES OUR MEMORY ***
[ad] surface base 0x107224000 sid-word 14 alloc 262144
[ad] surface content: 262144/262144 bytes == our marker 0xad — alias CONFIRMED
```

**Подтверждено на живом iOS 27.0b4:** sel7 от App-Sandbox без entitlements
принимается (kr 0), создаёт поверхность, чей CPU base **равен адресу
нашего буфера**, и чьё содержимое — наши байты (100% маркера). Это
фиксирует §108- расхождение: на девайсе sel7 работает (в §109 значилось
«alias создаётся (kr 0), но gather не видит маркер» — gather использует
другую семантику, сам алиас реален).

### Значение

1. Ядро **разделяет** пользовательские страницы с объектом, доступным по
   глобальному sid. Отсюда два вектора, которых в проекте не было:
   - **write через alias**: с другой стороны (GPU/scaler/другой клиент)
     запись в эту поверхность пишет в память нашего процесса — примитив
     «злоумышленник пишет в мою память», обратный привычному;
   - **survival-after-death**: если дескриптор переживает задачу, страницы
     уходят в общий аллокатор, а алиас продолжает указывать на них. Это
     **именно тот reclaim в общий kernel page allocator, которого GPU-ветка
     не могла достичь** (§134/§135: DATA-страницы скрабятся, PT-пулы вне
     досягаемости) — здесь страницы клиента, без скраба.
2. Механизм не требует ни приватных entitlement'ов, ни обхода SPTM.

**Статус:** класс открыт, это первая находка с write-вектором, не упирающимся
в гейт. Дальше — фаза 2: пережить смерть задачи (нужен второй процесс,
который создаёт поверхность-алиас, умирает, а первый читает/пишет через sid
и проверяет, что страницы переиспользованы).

## 139. v155: sid переживает освобождение handle; AllowGlobal через sel9 недостижим

### Доказано: поверхность живёт независимо от клиентских ссылок

Фаза `p_gsurvive` step 1 (результат: run-gsurv1):

```
[gs] sel7 -> kr 0x00000000 sid 14
[gs] sel1 release sid 14 -> kr 0xe00002c2   (у клиента НЕТ дескриптора)
[gs] sel2 lock after release -> kr 0x00000000 osz 0xc68
[gs]   base 0x107ee8000 alloc 262144 (our buf 0x107ee8000)
[gs]   after release: 262144/262144 marker bytes — SURVIVED handle release
```

Ключевое: **`sel1 release` возвращает 0x2c2** — то есть клиентская
ссылка на sid отсутствует с самого начала (sel7 создаёт поверхность в
глобальном реестре, а не в клиентской карте). Тем не менее `sel2 lock` по
этому sid **работает** и возвращает алиас на наши страницы с 100% маркера.

Это ровно та инверсия модели владения, ради которой вектор и открывался:
**идентификатор поверхности переживает отсутствие ссылок**, и поверхность
продолжает указывать на память процесса. Значит второй процесс, получив
sid, может работать с памятью первого — а после смерти первого страницы
уходят в общий аллокатор, тогда как дескриптор на них ещё жив.

### AllowGlobal: контроль показывает, что отказ не в ключах

Цель step 2 — выставить root-свойство `AllowGlobal`, которое в статике
рядом со строками «creating global IOSurfaces accessible to any other
process» / «relying on global (insecure) IOSurface lookups» и должно сделать
поверхность доступной другому процессу.

Результат: **все ключи → 0x2c2**, включая заведомо-валидные
(`IOSurfaceName`, `ColorSpace`) и контрольный `kShouldBeAccepted`.
Дискриминатор — публичный API на той же поверхности:

```
[gs] CONTROL IOSurfaceSetValue('ProbeKey') on surface 168 (void API)
[gs] CONTROL IOSurfaceCopyValue -> value present
[gs] CONTROL round-trip value = 42 (expect 42)
```

То есть значение на поверхность ставится и читается штатно, а **сырой
sel9 с sid от sel7 непригоден** (несогласованность sid-пространств либо
неверная форма кадра OSUnserialize — в §109 рабочий кадр был получен на
другом sid). Отсюда важный вывод: перебор ключей через sel9 бессмысленен,
пока не восстановлен рабочий кадр для sid этого класса. Вторая попытка с
Foundation-сериализацией (60–75 байт) дала тот же 0x2c2, значит дело не в
кодировке payload.

### Статус

**Открытый класс:** sid + zero-copy alias переживают освобождение handle —
необходимое условие для cross-process примитива подтверждено. Не хватает
одного: **второго процесса**, который предъявит этот sid (нужен либо
`AllowGlobal`, либо обход `find_surface`, либо гонка с release). Один
bundle id в песочнице второй процесс не поднять, поэтому это отдельная
инфраструктурная задача, а не фаза в текущем харнессе.

## 140. v156: второй процесс из одного бандла недостижим — нужен второй bundle id

Фаза 2 из §139 требовала второй задачи. Проверены все три маршрута из
одного sandbox-бандла, все закрыты **платформой, а не настройкой сборки**:

1. **posix_spawn бинаря из своего бандла** — sandbox отказывает.
   Замер: `_NSGetExecutablePath` даёт
   `/private/var/containers/Bundle/.../fuzz27.app`, `posix_spawn(.../vic/vic)`
   → **errno 1 (EPERM)**.
2. **XPC-сервис** — `NSXPCConnection initWithMachServiceName:` и
   `xpc_connection_create_mach_service` на iOS **не экспортируются**
   (ошибка линковки: "unavailable: not available on iOS"). Прототип сервиса
   (`fuzzer/vic_xpc.m`) оставлен в репозитории как запись о закрытом пути.
   Единственная связанная функция, доступная iOS-приложению, —
   `bootstrap_register`/`bootstrap_look_up`, но регистрировать порт должен
   кто-то, а запустить регистрирующего процесса мы не можем (п.1).
   Побочно: `bootstrap_insert` в отличие от `bootstrap_register` не
   экспортируется вообще.
3. **fork()** — sandbox блокирует: `fork() FAILED errno 1` (EPERM).

**Вывод.** На iOS из одного бандла второй task не получить: все три пути —
EPERM или отсутствие символа. Это не ограничение iOS 27 и не песочницы
конкретной конфигурации, а платформенное правило: задачу создаёт
launchd, а не процесс.

**Что это значит для вектора.** §138/§139 доказали обе половины примитива
внутри одной задачи (алиас sel7 = страницы клиента; sid переживает
`sel1 release`). Для кросс-процессной части нужен второй bundle id со своим
provisioning profile — это отдельная задача по инфраструктуре, а не фаза.
Она разрешаема технически (dev-профиль позволяет зарегистрировать второе
приложение в той же команде), но требует действия вне репозитория.

**Статус класса:** доказанное ядро примитива есть (zero-copy alias +
независимый от клиента sid, без гейтов и без SPTM); недостающий элемент —
второй bundle id, чтобы проверить переживание смерти задачи и reclaim
страниц в общий аллокатор.

## 141. v157: p_persist — поверхность НЕ переживает задачу; вектор закрыт

§140 установил, что второй task из одного бандла недостижим (EPERM ×2,
XPC не экспортирован). Но то свойство, которое нужно, — про **время жизни**,
а не про одновременность. Контейнер `Documents/` переживает смерть процесса,
поэтому тот же бинарь можно запустить дважды подряд, и второй запуск будет
**другим pid с другим task** — ровно та проверка, которую мы искали, без
новой инфраструктуры.

Фаза `p_persist`:
- step=1 (make): sel7-алиас поверх собственных страниц, маркер 0x5a,
  контроль алиаса, запись sid в Documents/sid.txt, выход;
- step=2 (take): новый pid читает sid.txt, **сначала заливает аллокатор**
  64 блоками того же размера (маркер 0xc3), затем лочит поверхность.

Порядок «заливка ДО чтения» — и есть эксперимент: если страницы мёртвой
задачи вернулись в общий аллокатор, наши блоки — наиболее вероятные новые
владельцы.

### Результат (run-persist-make/take)

```
[ps] MAKE: sel7 -> kr 0x00000000 sid 15 (base 0x107460000 size 0x40000 marker 0x5a)
[ps] MAKE control: lock -> kr 0x00000000, base 0x107460000, marker 262144/262144
[ps] TAKE: new pid 1334, reading sid 15 left by the dead task
[ps] TAKE: flooded allocator with 64 x 0x40000 blocks of 0xc3
[ps] TAKE: lock sid 15 after its creator died -> kr 0xe00002c2
[ps] VERDICT: surface did NOT survive its task — lifetime bound to the creator
```

**Поверхность НЕ пережила смерть задачи: `find_surface` вернул 0x2c2.**

Важная деталь надёжности: pid 1329 после step=1 **ещё жил** (приложение
не завершилось само — worker ждал), и я завершил его принудительно перед
шагом 2. То есть тест проверил именно **принудительную** смерть задачи —
самый жёсткий случай. Поверхность не выжила и при нём.

### Что это означает

Инверсия модели владения из §139 оказывается **ограниченной**: sid не
привязан к клиентским *ссылкам* (`sel1 release` → 0x2c2, §139), но
привязан к **задаче-владельцу**. Как только владелец умер, реестр снимает
поверхность, дескриптор освобождается, страницы уходят в аллокатор вместе с
описателем — и алиас, указывавший на них, исчезает.

Это закрывает класс целиком:

| Условие | Статус |
|---|---|
| Алиас sel7 = страницы клиента | подтверждён §138 |
| sid не привязан к клиентским ссылкам | подтверждён §139 |
| **Поверхность переживает задачу** | **опровергнуто §141** |
| Reclaim страниц через живой дескриптор | недостижим: дескриптор умирает вместе с задачей |

То есть «смерть задачи → страницы в общем аллокаторе → доступ по
пережившему дескриптору» не работает: ядро снимает дескриптор первым. Это
ровно тот защитный порядок, который нужен был, чтобы класс был закрыт, и он
реализован в IOSurfaceRoot, а не в SPTM.

**Итог по проекту.** Смена класса цели дала реальные результаты (§138–§141),
и все они отрицательные в части эскалации: zero-copy alias подтверждён, но он
жив ровно столько, сколько жив его создатель. Кросс-процессного и
read-after-reclaim примитива из App-Sandbox получить не удалось — и теперь
это установлено для всех трёх доступных путей (GPU reclaim §134–135, scaler
§136, IOSurface lifetime §141), а не «осталось проверить».

| AppleKeyStore | 0 | изучен частично (§99 SEPKeyStore) |
| AppleJPEGDriver | 0 | изучен частично (§122, 30 кейсов) |
| IOHIDEventService | 2 | изучен, мёртво (5740 кейсов) |

Остальное: **gated** (сервис есть, `IOServiceOpen` → 0x2c2/0x2e2) либо
**absent** (сервис не опубликован — именно так ведут себя все кандидаты по
ANE и AVD: `ANEUserClient`, `ANEPrivilegedVMAccess`, `AppleAVDUserClient`,
`IOAccessoryManager` — классы существуют в бинаре, сервисов на устройстве
нет).

### Вывод — и он важнее, чем список

Класс «достижимое из App-Sandbox» **действительно почти исчерпан**, но
не по незнанию, а по устройству iOS: публичная поверхность IOKit на iOS
27 это ~5 сервисов. Мой прежний вывод («проект исчерпал доступное») был
правильным по существу, но у него не было измерения — теперь есть
измеренный знаменатель: **460 кандидатов → 5 открывается, 4 из них уже
изучены**.

Практическое следствие: единственная **неизученная** достижимая поверхность —
**IOMobileFramebuffer** (открывается, type 0). Именно она упомянута в
§6.1 scaler_dva_formula как владелец системного DART-домена. Это
следующая точка, а не 114 неисследованных кекстов — до них песочница
не дотягивается.

Методологическая ценность: триаж по строкам даёт верхнюю оценку
потенциала, а измерение `IOServiceOpen` — настоящую. Одно без другого
даёт ложный оптимизм (в нашем первом прогоне все кексты выглядели
одинаково «богатыми»). Сначала знаменатель, потом анализ.

## 143. v159: IOMobileFramebuffer — закрыт полностью, с расшифровкой кодов

§142 оставил одну достижимую неизученную поверхность. Разобрал её методично.

### Статика

`IOMobileFramebuffer` на iOS 27 даёт **`com.apple.iokit.IOMobileGraphicsFamily`**,
а `IOGraphicsFamily` — это macOS. Xref на строки проверок не резолвится:
GOT обфусцирован chained-fixups'ами (тот же барьер, что закрыл статику IOSurface
в §136). Но сами строки говорят о классической форме IOKit — валидные длины
проверяются против количества, вычисленного из `structureInput`:

```
data:  in_args->data_size  (%lu) > in_args->data[]  count (%lu)
block: block_size (%lu) > out_args.block[] count (%lu)
chunk: in_args->chunk_size (%lu) > in_args->chunk[] count (%lu)
```

Поэтому селектора восстановлены эмпирически.

### Коды возврата (IOReturn.h, iPhoneOS.sdk)

Это ключевая поправка: **0xe00002e3 — это `kIOReturnNoPower`, а не «нет
девайса»**, и **0xe00002c1 — `kIOReturnNotPrivileged`**, тогда как
0xe00002e2 — `kIOReturnNotPermitted`. Раньше я называл 0x2e2 «NotPrivileged»
(§142 reach-фаза) — это две разные константы с разными значениями.

| код | имя |
|---|---|
| 0xe00002e3 | **kIOReturnNoPower** — доминирующий ответ |
| 0xe00002c1 | **kIOReturnNotPrivileged** |
| 0xe00002c2 | kIOReturnBadArgument |
| 0xe00002bc | kIOReturnError |
| 0x00000001 | KERN_INVALID_ADDRESS |

### Что измерено

Два экземпляра, оба класса `AppleCLCD2` (настоящий LCD-контроллер, не прокси).
Прогнано 121 селектор × (22 значения × 4 формы скаляров + 15 размеров входа ×
2 заливки) ≈ 3900 кейсов, плюс отдельные фазы.

Живых селекторов **19** из 121. Ни один из них не даёт выходных данных:
**osz == 0 во всех 214 + 2476 + 286 замерах**. Канала утечки нет.

- **sel6** — ровно 3 скаляра, `scalar[1]` это код операции. `=3` → kr 0;
  `=4` → BadArgument; остальное → **NoPower**. `scalar[0]` и `scalar[2]`
  полностью игнорируются (все значения 0..~0xffffffffffffffff → kr 0).
  Любой непустой structure input → BadArgument: обработчик наши данные не
  читает вообще, это чистая команда.
- **sel84** — единственный метод, читающий наши данные: принимает **ровно
  4 байта** входа и **ноль скаляров**. Прогнано 619 значений 32-битного слова
  (0..64, лестница степеней, края ширины, байтовые паттерны, 512 псевдослучайных)
  × 4 формы скаляров = 2476 кейсов. Все дают kr 0, osz 0. Содержимое слова не
  влияет ни на что — это acknowledge-заглушка, а не индекс и не режим.
- **sel23, sel78** → NotPrivileged: единственная логика за привилеги-гейтом.
- **sel20, sel47, sel72** → kIOReturnError.
- остальные 11 → kr 0 / osz 0, то есть no-op.
- **sel89** → константный `KERN_INVALID_ADDRESS` при любом значении, включая 0,
  то есть не наш адрес, а заглушка.

### Доказательность отрицательного результата

Нагрузочный вывод — «ни один живой селектор не читает structure input» — я не
стал выводить из свипа, а проверил отдельной фазой: все 19 живых селекторов ×
15 размеров входа × (без скаляров и с 3 скалярами) = **286 вызовов, 284
дали BadArgument**. Исключения ровно два: sel6 при `in=0` (не читает) и sel84
при `in=4`. Это урок §5 в действии: раньше отрицательные результаты пять раз
оказывались «фаза не выполнялась», поэтому нагрузочные утверждения требуют
отдельного измерения, а не вывода по умолчанию.

### Гейт привилегий открыть нечем

Проверил профиль: в нём **45 entitlement'ов, и все публичные** — ни одного
`com.apple.private.*`. «Kernel-класс» там — только
`increased-memory-limit`, `increased-debugging-memory-limit`,
`extended-virtual-addressing`, то есть подсказки лимитов памяти для отладки,
а не выдача привилегий. Это окончательно объясняет нулевой эффект §137c:
набор entitlement'ов просто не содержит ничего, что могло бы что-то открыть.

### Итог

Поверхность `IOMobileFramebuffer` закрыта: 19 живых селекторов, из них
18 — no-op, заглушки или методы за гейтами питания/привилегий, и один
(sel84) — единственный читающий наши данные, но нечувствительный к их
содержимости. Канала утечки нет, поверхности для length/offset-confusion нет.

**Общий итог v158+v159: публичная IOKit-поверхность iOS 27, достижимая из
App-Sandbox, измерена полностью — 5 сервисов, все закрыты.**

## 144. v160: доказательство детектора крашей — и его провал

Перед тем как искать краши в новых целях, я решил проверить, что детектор
вообще срабатывает. Логика простая и должна была быть очевидна раньше:
**детектор, который ни разу не увидел краш, неотличим от отсутствующего** —
он соглашается с каждым отрицательным результатом именно потому, что сломан.

### Что сделано

`relay/crashdiff.sh` — снимок корпуса крэш-логов устройства до и после
команды, вывод только нового. Корпус берётся через домен `systemCrashLogs`
(единственный device-global домен, доступный с хоста) и уже содержит 300+
чужих крашей сторонних приложений — поэтому дифф по именам обязателен, счётчик
не годится.

Фаза `p_detcheck` роняет процесс четырьмя разными способами: запись по
нулевому адресу, по неотображённому адресу, `__builtin_trap` (EXC_BREAKPOINT,
а не сигнал) и `abort()`. Перед крашем `fflush` + `fsync` на stderr, чтобы
лог доказывал выполнение фазы даже в провалившемся прогоне — иначе проверка
сама стала бы тем нерезультатом, который предотвращает.

### Результат: детектор молчит

```
kind=null   -> фаза отработала (pid 1444), лог есть, отчёта нет
kind=wild   -> фаза отработала, лог есть, отчёта нет
kind=trap   -> фаза отработала, лог есть, отчёта нет
kind=abort  -> фаза отработала, лог есть, отчёта нет
```

Корпус 310 → 310. Ни через `devicectl`, ни через `idevicecrashreport`
(282 файла выкачаны, свежайший отчёт `fuzz27` — 07:39, прогоны — около 09:50).
Все четыре фазы отработали: строки `[detcheck] alive pid ... kind ...`
и `this line is fsynced BEFORE the fault` присутствуют в логе.

### Почему это важнее самой находки

Это retroactively подрывает методологию проекта. Все отрицательные выводы
«крашей / паник не было» держались на детекторе, который никогда не был
проверен на срабатывание. Пять провалов §5 были частным случаем того же класса
ошибки; здесь та же ошибка обнаружена в самом инструменте наблюдения.

Гипотеза: троттлинг ReportCrash — приложение падало десятки раз 8–9 сентября,
и отчёты по повторяющимся сигнатурам подавляются. Ребут сбрасывает состояние.
Проверка отложена до ребута, но сам вывод («детектор не доверен, пока не
увидит собственный краш») уже действует.

**Правило, введённое для дальнейшей работы: ни один отрицательный результат
не считается, пока детектор не подтверждён хотя бы одним срабатыванием на
известном входе.** Для новых целей это значит — сначала фаза с гарантированным
крашем, потом измерение «крашей нет».

## 145. v161: AppleKeyStore — вторая достижимая поверхность тоже закрыта

§142 оставили две достижимые поверхности, не изученные полностью. §143 закрыл
IOMobileFramebuffer. Это — вторая.

### Почему это была лучшая цель из оставшихся

Крипто-хранилище: userclient существует ради импорта и экспорта ключевого
материала, и каждый такой путь несёт объявленную пользователем длину, которую
обязан сверять с фактически переданным буфером. Это в точности класс
length/offset-confusion, ради которого проект и жив, — и в сервисе, который
действительно открывается.

### Измерено

Прогнаны селекторы 0..40 × (20 значений × 4 формы скаляров + 17 размеров
входа × 2 заливки) = **2196 вызовов**. Открыто **32 селектора из 41** — вдвое
плотнее, чем фреймворк (19 из 121).

Новые коды, которых не было в IOMobileFramebuffer:

| код | имя |
|---|---|
| 0xe00002f0 | **kIOReturnNotFound** — «данные не найдены» |
| 0xe00002db | kIOReturnNoSpace |

Результат:

- **Ни один селектор не принимает structure input.** 0xbiteвых вызовов со
  структурным входом: все дали BadArgument/Unsupported. Это главный результат —
  метода, читающего наши байты, здесь нет вообще.
- **`osz == 0` во всех 2196 замерах.** Канала утечки нет.
- Все ответы — гейты: `NotPrivileged` (0x2c1) на sel3-6, 20-23, 26, 27, 33-37;
  `NotPermitted` (0x2e2) на sel8, 9, 12, 18, 19, 24, 30, 32; `NotFound` (0x2f0) на
  sel3, 8, 9, 12, 17, 23, 31, 32, 35; `NoSpace` (0x2db) на sel17, 31, 35;
  `kIOReturnError` (0x2bc) на sel10, 11, 13.
- `NotFound` приходит от **скаляров**, не от входа: это «искали по
  идентификатору — не нашли». Скаляр здесь это тег ключа. У песочницы нет
  чужих тегов, а перебрать 64-битное пространство нельзя, поэтому путь чтения
  закрыт по данным, а не по правам.

### Итог

Все 5 сервисов, которые достижимы из App-Sandbox на iOS 27, теперь закрыты, и
каждый закрыт **измерением**, а не предположением: IOSurfaceRoot (§134–141),
IOMobileFramebuffer (§143), AppleKeyStore (здесь), AppleJPEGDriver (§122),
IOHIDEventService (§— мёртв, 5740 кейсов).

Два независимых измерения, оба отрицательные: 5 открытых сервисов из 460
кандидатов, и ни один не даёт ни канала утечки, ни метода, читающего
пользовательский буфер без гейта. Это уже не «мы не нашли» — это «пути нет».

## 146. v162: Mach-поверхность привилегированных демонов недостижима — 0 из 132

Инвентаризация по IOKit (§142) дала знаменатель и закрыла обе неизученные
поверхности. Тот же вопрос к Mach-стороне никогда не задавался: проект только
пытался **создать** свой endpoint (§140), но никогда не смотрел, что уже есть.

### Сначала — самопроверка, а не замер

Первый прогон вернул `kr 0x0000044c` на **все** 132 имени. Это подозрительно:
у несуществующего сервиса должен быть `KERN_NAME_NOT_FOUND`, а не тот же код, что
у заведомо живого `com.apple.backboardd`. Два объяснения — песочница запрещает
lookup, или вызов сделан не той сигнатурой — неразличимы по этому результату,
а фаза с неверным прототипом замером не является.

Заголовок `<mach/bootstrap.h>` в iOS SDK пуст: *«obsolete: included only for
compatibility»*. То есть `extern` в проекте — это догадка.

Проверка (dlsym реального символа + контрольное несуществующее имя):
- `bootstrap_look_up` резолвится, адрес один и тот же для обеих форм;
- `task_get_bootstrap_port` **не экспортируется вовсе** (0x0), то есть
  3-аргументной формы с bootstrap-портом на iOS 27 не существует;
- контроль `com.apple.__nonexistent_control_9f3a2b` → `0x44c`;
- реальный `com.apple.backboardd` → `0x44c`.

**Вердикт: контроль == реальное имя, существование не проверяется.** Реестр
не опрашивается, `bootstrap_look_up` перехватывается песочницей. 0 открытых
из 132, где 22 имени взяты из crash-корпуса самого устройства, то есть
демоны эти точно существуют.

### Что это закрывает

Не только инвентаризацию. Идея «достучаться до привилегированного демона и
скормить ему свой файл» опиралась ровно на этот lookup — и потому недостижима
ровно в той же степени. Любой XPC-триггер (QuickLook, AVFoundation,
Core Spotlight) идёт через `bootstrap_look_up`/`xpc_connection_create`, то есть
мимо той же стены.

### Итог по трём векторам

| вектор | измерено |
|---|---|
| IOKit userclients | 5 из 460 открывается, все за гейтами (§142–145) |
| Mach-сервисы | **0 из 132**, lookup заблокирован песочницей |
| XPC-триггеры в привилегированные демоны | недостижимы тем же механизмом |

Что остаётся достижимым из App-Sandbox и при этом даёт контролируемые байты
**внутрь ядра** — сетевой стек: сокеты песочница разрешает, а ядро само
разбирает то, что мы отправили. Это единственный оставшийся вектор, и он же
единственный, где детектор не зависит от ReportCrash: паника ядра видна как
перезагрузка устройства.

Методологическая заметка: контрольное имя обязано быть в каждом фазе-инвентаризации.
Без него «0 из 132» читалось бы как «сервисов нет», и это была бы ложная
интерпретация заблокированного инструмента как пустого множества.

## 167. SecureROM и загрузочная цепочка: что удалось доказать

Появились расшифрованные дампы secureROM и полный IPSW. Ниже — что из этого
реально установлено, с разделением на доказанное и гипотезы.

### Полная цепочка извлечена

`Firmware/all_flash/{LLB,iBoot,iBootData,sep-firmware}`, `Firmware/dfu/{iBEC,iBSS}`,
`Firmware/sptm.t8122.release.im4p`, `Firmware/txm.iphoneos.release.im4p`,
`Firmware/pmp/t8130pmp.im4p`, `Firmware/SmartIOFirmware_ASCv6.im4p`,
`DeviceTree.d84ap.im4p`, `kernelcache.release.iphone16`. ChipID 0x8130.

### Метод: сначала измерение, потом выводы

Три ошибки инструмента подряд, и все три давали **чистый и неверный** ответ:

1. Первый архив был на 75 МБ короче (zip64-локатор указывал на 12 354 135 033 при
   размере 12 275 259 708). Оказалось, `unzip`/`zipinfo` бессильны и против
   целого — пришлось читать поток напрямую.
2. Мой `resync`-э Inflater «успешно» распаковал **мусор** для 5 файлов: inflate
   не падает, если начать с неверного смещения. Поймано только сверкой с
   эталоном из полного архива: `iBoot`/`sep-firmware`/`SmartIO` совпали,
   `sptm`/`txm`/`iBEC`/`iBSS`/`pmp` разошлись. **Без сверки я бы анализировал
   мусор.**
3. `xref_maestro.py` пять прогонов подряд рапортовал «эта строка не
   используется». Три причины, все по очереди: VA считался как
   `vmaddr + fileoff` вместо `vmaddr + (fileoff - fileoff_сегмента)`; сканировался
   только `__TEXT`, а код лежит в `__TEXT_EXEC`; и главное — guard `off & 3`
   отбрасывал каждую инструкцию, потому что `__TEXT_EXEC` начинается с
   file offset `0x242f7`, то есть **не выровнен по 4**. Ноль находок читается
   как измерение; на деле это был сломанный инструмент.

Третья ошибка — главная. Она того же класса, что §5 и §144: инструмент, который
молчит, неотличим от инструмента, который ничего не нашёл.

### Установлено

1. Дампы secureROM/AppleSEPROM **не зашифрованы** (энтропия 3.7 / 4.9), тысячи
   ARM64-инструкций. Встроенный **самоподписанный корень**:

       CN=Apple Secure Boot Root CA - G2, O=Apple Inc., C=US
       RSA-4096, sha384WithRSAEncryption, CA:TRUE
       Certificate Sign, CRL Sign, 2014-12-19 .. 2034-12-14

   Подпись проверена openssl по собственному ключу: `verify : OK`.

2. Цепочка **на RSA, а не на ECDSA** — констант P-256 нет ни в одном ROM. Именно
   поэтому наивный поиск `p`,`b`,`Gx`,`Gy` даёт пусто и читается как «проверки
   подписи тут нет».

3. **payload-части iBoot, iBEC, iBSS, LLB, SPTM, TXM, SEP и DeviceTree
   зашифрованы** в IPSW (энтропия 7.99, нет ни магии Mach-O, ни строк). То есть
   **Image4-верификатор статически нечитаем** без ключа расшифровки.

### Не установлено

**База загрузки образа secureROM не восстанавливается.** Все ADRP+ADD-ссылки
попадают в одну полосу `0xfc038000..0xfc048c40`, которая не отображается внутрь
файла 512 КБ ни при каком постоянном смещении. Перебор 455 616 баз: совпал **1
якорь из 9**. Два места, которые выглядят как чтение адреса сертификата
(`adrp/add #0xcc8`, затем `ldr h0`), читают **2 байта**, а не 4096-битный модуль,
и одно из них — `b`, а не `bl`, то есть не вызов. Считать это проверкой
подписи — гипотеза, а не результат.

**Вывод по направлению:** путь к джейлбрейку через аудит верификатора подписи
на этом устройстве закрыт по существу, а не по трудности. Верификатор живёт в
iBoot, iBoot зашифрован, ключ приходит из SHSH-блобов, которых нет.

### Куда переключиться

`IOAccessoryManager` — по строкам самая перспективная из 114 неизученных кекстов:

```
IOAccessoryHSAIDBusTransport::receiveLongFormPacket: No rx packets
  Received packet longer than receive buffer size (%u > %u)
  Received packet shorter than minimum long format packet size (%u)
  Received packet with command data longer than available buffer space (%u > %u)
  Received packet with unexpected sequence number. Got %u, expected %u
```

Третья проверка — «длина данных команды» против «доступного места» — это и есть
целевая форма: вычитание размера заголовка из объявленной длины может уйти в
ноль. Транспорт Bluetooth, код в ядре, длина из пакета.

Ссылки на строки найдены (5 сайтов, 0x08409f..0x0840d7), но все они в
**логгере**, а не в самой проверке: за строкой следует `bl 0x8401f` (печать), а
рядом `stp x29,x30` — пролог вложенной функции. Значит проверка ссылается на
строку иным способом, и разбор не доведён до конца. Инструмент
`xref_maestro.py` при этом рабочий (находит ссылки после починки выравнивания),
и он применим к любому кексту — это основная ценность.

## 168. v168: инструмент починен — и фильтр, который при этом врал

Цель была довести сбор данных до состояния, в котором числа можно брать всерьёз.
Сделано; попутно исправлено два метода, и второй интереснее первого.

### Сбор строк: кекст не контигуален

Fileset-entries описывают **только `__TEXT`** кекста. Проверено на числах:
`com.apple.iokit.IOAccessoryManager` находится по 0x86dfb0, следующая entry — по
0x891bd0, дельта **0x23c20** = размер `__TEXT` этого кекста (0x23c1f) с
выравниванием. Остальные сегменты лежат в отдельных fsegments:

```
__TEXT        foff=0x86dfb0     ← то, на что указывает entry
__TEXT_EXEC   foff=0x2bcdab0
__DATA        foff=0x4493458
__DATA_CONST  foff=0x10f8f90
__LINKEDIT    foff=0x4530000
```

Поэтому «вырезать кекст» одним куском неверно by construction, и все попытки
падали молча в разные стороны:

- extent по следующей entry → **146 КБ**, обрез до начала `__TEXT_EXEC`;
- extent = `max(foff+filesize)` → **64 МБ**, потому что `__LINKEDIT` принадлежит
  чужому региону;
- extent по `max(foff+size)` с fallback на `vmsize` → bss-сегмент (filesize=0) с
  огромным vmsize уводил конец за пределы коллекции.

Правильный инструмент (`results/securerom/kext_strings.py`) не собирает образ
вовсе: он берёт список сегментов кекста и вычитывает строки из каждого
диапазона. **314 593 строки с точной атрибуцией**; `tmpfs` из 72 521 строки
превратился в 530.

Итого за сессию **восемь** ошибок разбора форматов: `LC_FILESET_ENTRY` (дважды:
порядок полей и компактная форма без `reserved/count/stroff`),
`segment_command_64` (vmsize/fileoff/filesize), выравнивание инструкций в
`__TEXT_EXEC` (смещения ≡ 3 mod 4), PC в ADRP (VA, не file offset), и extent
кекста (трижды). **Каждая давала чистый успешный прогон, а не ошибку.** Это
ровно тот класс, который уже записан в §5 и §144, и он оказался не частным
случаем, а свойством инструментов этого проекта.

### Фильтр границ: метод даёт ложные срабатывания

Фильтр ищет асимметрию «проверка сверху есть, проверки снизу нет», по лексике
`longer than` / `too big` против `shorter than` / `too small`. На `AppleAVE2`
он дал 54:2, и это выглядело как лучший кандидат. Но среди строк:

```
DPE register address is out of range 0x%x [0x%x, 0x%x]
address is out of range 0x%llx [0x%llx, 0x%llx)
```

Нижняя граница **проверяется** — просто в том же сообщении, в формате
`[min, max]`. Фильтр такую проверку не считает.

Значит фильтр измеряет не отсутствие нижней границы, а отсутствие
определённой лексики, и **систематически завышает асимметрию**. Ранжирование
пригодно как лид; вывод «проверки снизу нет» из него делать нельзя.

Честная таблица после починки (верхняя/нижняя по лексике):

| кекст | верхних | нижних |
|---|---|---|
| com.apple.kernel | 88 | 98 |
| com.apple.driver.AppleAVE2 | 54 | 2 |
| com.apple.driver.AppleH16ANEInterface | 39 | 7 |
| com.apple.driver.AppleAVD | 21 | 5 |
| **com.apple.driver.AppleMSG** | 11 | **0** |
| com.apple.driver.ApplePPMCPMS | 9 | **0** |
| com.apple.driver.corecapture | 7 | **0** |
| com.apple.iokit.IOThunderboltFamily | 4 | **0** |

Единственный, где асимметрия пережила проверку на формат диапазона, —
`AppleMSG`: четыре однотипных счётчика (`Number of interrupts/sync configs/
reg value updates/lut entries exceeds max size`), каждый проверяется только
сверху, и все четыре строки не имеют пары в формате `[min, max]`. Это GTB —
синхронизация времени между чипами, то есть вход приходит **от соседнего SoC**.
Не от локального пользователя, но и не от нас.

Инструмент, который это дал, рабочий и применим к любому кексту. Следующий шаг
требует ручного разбора арифметики в `AppleMSG`, а не дальнейшего расширения
автоматизации: лексический фильтр исчерпан, он принципиально не видит
двухсторонние проверки.

## 169. v169: фильтр, который считает форму проверки, а не слова

`length_audit.py` из §168 сравнивал лексику и потому врал: он выдал
`AppleAVE2` как 54:2, хотя среди этих строк есть
`address is out of range 0x%llx [0x%llx, 0x%llx)` — нижняя граница проверяется,
просто в том же сообщении. Ложное срабатывание именно в ту сторону, которая
выглядит самой привлекательной, хуже отсутствия срабатываний.

`bound_audit.py` классифицирует не слова, а **форму** проверки:

| форма | признак |
|---|---|
| `TWO_SIDED` | «out of range» + два конца диапазона `[min, max]` |
| `UPPER_ONLY` | «exceeds max», «too large», «N > cap», «overflow» |
| `LOWER_ONLY` | «too small», «shorter than», «below minimum» |

и склеивает их по **имени поля**, а не по кексту целиком: «Number of
interrupts exceeds max size» и «Number of interrupts too small» — это пара,
даже если лежат в разных функциях. Именно на этом уровне проявляется реальное
пропущенное место.

Оговорка к самому фильтру: он всё ещё лексический, поэтому
`multipass index out of bounds (range: [0,%d])` он посчитал как `UPPER_ONLY`,
хотя нижняя граница там задана литералом `0`. То есть оценка «сирот» завышена и
в эту сторону — список лидов, не вывод.

### Проверка топ-кандидата вручную: AVE2

93 «сироты» — в основном одно и то же: `size overflow` (21 шт.) плюс вариации
под конкретные структуры — `DPB size overflow`, `PS data overflows`,
`pixel area overflow`, `LRB size overflow`, `HSCOutput size overflow`,
`MCTFOutput size overflow`. Это проверки переполнения при вычислении размера
(ширина × высота × bpp), то есть ровно тот класс, где нужен нижний предел.

Гипотеза: размер проверяется на переполнение, но **не на ноль**, и аллокация
нулевого размера вернёт либо NULL, либо разделяемый буфер, куда потом пишет
копирование.

**Гипотеза не подтвердилась.** В строках есть assert-условие целиком:

```
msize > 0 && size > 0 && unitSize >= 0 && (unitSize == 0 || (unitSize & (unitSize - 1)) == 0)
```

Проверка `size > 0` присутствует, причём вместе с требованием степени двойки к
размеру юнита. Дополнительно: `Clear an unempty task`, `list is not empty`,
`empty slice`. То есть нулевой размер покрыт.

Оговорка: assert в release-сборке может быть выключен, и тогда `size > 0`
останется только в отладочной сборке. Это общая практика, не находка, но это
означает, что строками подтвердить *исполнение* проверки нельзя — только её
наличие в исходнике. Разница принципиальная, и её не закрыть без дизассемблинга.

## 170. v170: bad_query — песочница пробита, и что это дало на самом деле

Пользователь указал на публичный эксплойт, который он проверил на своём
устройстве: **bad_query** (forcequitOS/bad_query, zero-day от b4orvn259).
Поддержка заявлена для iOS 26.0–26.6.1 и **27.0b1–b4**; патч закрыл только
27.0 **beta 5**. У нас 24A5390f, то есть до патча.

### Что это за уязвимость

Path traversal в `container_query_operation_set_part_domain`
(`libsystem_containermanager.dylib`). Часть домена не нормализуется, поэтому
запрос вида `../../../../../../../../..<path>` получает от `containermanagerd`
sandbox extension на `<path>`, а `sandbox_extension_consume` выдаёт настоящий
дескриптор. Ядро санкционирует путь, о котором его не просили, через штатный
приватный API; нужна только `com.apple.security.application-groups`, которая в
нашем профиле уже есть (5 групп).

### Проверено на устройстве — работает

```
/var/containers/Data/System             is_group=0 -> дескриптор, 9 контейнеров
/var/mobile/Containers/Shared/AppGroup  is_group=0 -> дескриптор, 8 групп
/var/mobile/Containers/Data/Application is_group=* -> -4 (ядро отказало)
/var/mobile/Containers/Data/InternalDaemon is_group=* -> -4
/var/containers/Shared/SystemGroup      is_group=* -> -4
```

Две поправки к README автора, обе проверены, а не приняты на веру:

- на iOS 27 работает **только `is_group=0`**; с `is_group=1` тот же путь
  даёт `-4`. Автор писал, что флаг на 27 не нужен — это подтвердилось, причём
  установленным значением, а не отсутствием эффекта;
- контрольный путь `/var/mobile/Media` даёт `-3` («outside of sandbox»), то
  есть контроль честно показывает, что механизм для этого пути недоступен.
  Без него «получили дескриптор» ничего бы не значило.

`-4` — это `copy_sandbox_token() == NULL`: контейнер найден, но **ядро отказало
выдавать extension**. То есть обход доходит до запроса, а решение принимает ядро.

### Область: файлы, а не память

Это **файловый** escape, а не kernel r/w. Контейнеры приложений и
`InternalDaemon` недоступны. Цель проекта — ядерный примитив — этим не
достигнута, и называть иначе было бы выдачей желаемого за достигнутое.

Но впервые за сессию получен доступ, которого не было ни при каких условиях:
контейнеры **системных демонов**.

```
EDFBF92A  ReportCrash, PerfPowerServices, HangTracer, SpinTracer
AF589EEA  com.apple.launchservices.securepreferences.plist
          com.apple.launchservices.appmarketplaces.plist
8EB68272  db-shm
```

### Побочно закрыт вопрос §144

Отчёты о крашах §144 не появлялись ни через `devicectl`, ни через
`idevicecrashreport`, и причину тогда выбрать было нельзя: «устройство не пишет»
против «инструментарий не видит» дают одинаковую картину.

Теперь каталог читается напрямую: `ReportCrash` существует, внутри 11
per-bundle каталогов (`com.google.ios.youtube`, `com.openai.chat`,
`us.zoom.videomeetings`, `apps.homepreserves.prohome`, `com.google.Drive`,
`ru.yandex.blue.market`, …), и **все они пусты**.

Значит троттлинг был неверной гипотезой: `ReportCrash` не пишет ничего вообще.
Канал отчётов на этом устройстве закрыт, и чинить его нечем — остаётся ребут на
панику ядра, как и указано в §163.

## 171. v171: недостающие логи v163–v165 — что на самом деле дала сеть

Фазы `p_net`, `p_lsvc`, `p_ipopt` гонялись в v163–v165, но логи не были
сохранены — дыра §147–166 в журнале. Прогнаны заново через `runf.sh`
(свежие логи: `results/v171-net.log`, `results/v171-lsvc.log`,
`results/v171-ipopt.log`).

**p_net** (v163): raw-сокеты — `IPPROTO_RAW`, `IPPROTO_ICMP`, IPv6 raw — все
EPERM(1). Loopback v4/v6: 0–8000 байт доходят целыми; 65500/65507 →
EMSGSIZE(40). Мультикаст `224.0.0.1:5353` → errno 65 при любом IP_TTL (в §174
выяснено, что 65 = EHOSTUNREACH и это не «нет интерфейса», а отсутствие
мультикаст-маршрута).

**p_lsvc** (v164): 66 портов — открыт ровно один, TCP 127.0.0.1:1080; UDP
ответов 0.

**p_ipopt** (v165): IP_OPTIONS(13 байт) → EINVAL(22); IP_HDRINCL → ENOPROTOOPT(42);
IP_DONTFRAG → 42; IP_TOS(±1), IP_RECVTTL, IP_RECVPKTINFO → приняты; IP_MTU=68
принят, и 8192-байтовый пакет ушёл на loopback (фрагментация на loopback не
происходит — не результат о политике). 1080 принял 18 байт и промолчал
(EAGAIN 35).

Важнее всего то, что §165 из этого **не** вынес: «IP_OPTIONS refused» был
выводом на детекторе, который не проверил формат. Ошибка повторяет класс §163 —
см. §173, где тот же вызов с корректной длиной принимается.

## 172. v171: p_bq2 — escape даёт ЗАПИСЬ; параметры шире, чем у PoC

§170 проверил bad_query в одной точке пространства: класс 7/13, part 3, два
значения флагов, семь путей, `create=0`. Фаза `p_bq2` прошла остальные
измерения. Три контроля, в порядке:

1. точка §170 → handle 1 ✓;
2. запись в собственный контейнер (без escape) → w=4 r=4 ✓;
3. **негативный контроль**: запись в `/var/containers/Data/System` без
   дескриптора → `open(O_CREAT)` EPERM(1), отказано ✓.

### Главная находка: запись через escaped-дескриптор работает

```
/var/containers/Data/System                  -> created, w=4 r=4 'fz27' unlink=0  WRITE OK
/var/containers/Data/System/AD7D3E87-…       -> created, w=4 r=4 'fz27' unlink=0  WRITE OK
```

С дескриптором — создание, запись, чтение обратно и удаление; без него —
EPERM. Вывод §170 «escape даёт чтение» был неверным по методу: запись
**не проверялась**. Sandbox extension, выдаваемый traversal'ом, несёт и
write-операции. Для джейлбрейка это меняет класс вектора: можно сажать и
менять файлы внутри контейнеров системных демонов (в §170 перечислены
LaunchServices-preferences, ReportCrash, HangTracer), а не только читать.
Следующий шаг — найти в этих контейнерах файл, который привилегированный
демон читает, изменить его и наблюдать поведение.

(Первый прогон фазы дал r=-1 из-за чтения через O_WRONLY-дескриптор — баг
инструмента, не результата; исправлено, негативный контроль добавлен во
втором прогоне. Оба лога сохранены.)

### Корень: q0 == q1 везде, где lstat проходит

`lstat` успешен для **всех** 22 корней (включая /System, /usr) — песочница
не прячет пути на этом уровне, гейт стоит на consume токена. Отличие
`create=0/1` поэтому нулевое; различаются сами корни:

| корень | результат |
|---|---|
| `/var/containers/Data/System` | handle (3), listing ✓ |
| `/var/mobile/Containers/Shared/AppGroup` | handle (4), listing ✓ |
| `/var/containers`, `Shared/SystemGroup`, `/var/mobile/Library`, `Library/Logs`, `/var/tmp` | **-4** — результат есть, kernel отказал в токене |
| остальные 15 (`/var/db`, `/etc`, `/System`, `/usr`, `/var/protected`, `/var/root`, …) | -3 — containermanagerd не знает пути |

-4 против -3 — это карта того, что MCM вообще обрабатывает, но не отдаёт:
кандидаты на расширение через другой class/part/flags.

### Часть пространства, не тронутая PoC

- **class 1–16, обе маршрутизации**: ручат только 7 (grp) и 13 (null), как
  и §170. class 2 → стабильно -4 на обоих маршрутах (знает, но не отдаёт).
  Остальные 14 → -3. Вывод §170 «system daemon containers only» подтверждён
  на полном срезе, а не на двух значениях.
- **part 0–7**: **part 2 тоже даёт handle** (обе маршрутизации), part 3 —
  контроль; part 0/7 → -4, part 1/4/5/6 → -3. Part — это стартовое
  поддерево внутри контейнера, значит part 2 открывает *другой* набор
  каталогов, ещё не листавшийся. Часть: в следующем прогоне сделать opendir
  для part-2-дескриптора.
- **flags**: кроме контрольного `0x8000000000` работает
  **`0x4000000000` → handle 6**; `0`, `0x80000000`, `0x1000000000`,
  `0x40000000`, `0x800000000` → -4. Семантика нового бита неизвестна —

### Символы и sibling-операции

## 173. v171: p_netv6 — §165 ошибся на формате опций; SCTP/MPTCP в ядре нет

Контроли: sysctl-чтение `kern.maxproc` → rc 0 (v 2000); loopback-дейтаграмма
3/3 ✓.

### IP_OPTIONS: повтор с корректной длиной меняет вывод §165

RFC 791 требует кратности 4 и ≤40; 13 байт §165 — заведомо неверный формат.
Повтор:

```
4x NOP (4B)            -> rc 0  ACCEPTED, egress send OK, getsockopt round-trip
EOL + pad (8B)         -> rc 0  ACCEPTED
LSRR 1 hop (8B, тип 131) -> rc 0  ACCEPTED, getsockopt возвращает 7f 00 00 01
LSRR len=40 в 8B буфере   -> EINVAL  (формат-контроль работает)
security opt len=0        -> EINVAL
unknown type 0x1f (4B)    -> rc 0  ACCEPTED
```

Парсер опций IP **доступен** из приложения на разрешённом dgram-сокете:
setsockopt принимает, хранит (round-trip через getsockopt), egress-посылка
проходит. Контр-принимаемость: приёмник с IP_RECVOPTS/IP_RECVRETOPTS на
loopback получил controllen 0 — по проводу опции не наблюдились (либо
loopback их снимает, либо возвращает их иначе). Честный статус: *setsockopt-
путь достижим, присутствие на проводе не доказано*. Следующий шаг при
необходимости — слать на адрес en0 и слушать там же (не-loopback-путь).

cmsg-путь: `IP_RETOPTS` через sendmsg принят (4 байта ушли), `IP_PKTINFO` с
ifindex 0x7fffffff → ENXIO(6) (валидация есть), IPv6-HOPOPTS-cmsg на v4-сокете
принят и проигнорирован (пакет доставлен).

### Транспорты: закрыты отсутствием, не политикой

```
SCTP(132)    stream/dgram -> EPROTONOSUPPORT(43)
UDPLITE(136) stream/dgram -> EPROTONOSUPPORT(43)
MPTCP(262)   stream/dgram -> EPROTONOSUPPORT(43)
```

43 = протокола в этом ядре нет — sctp/mptcp-парсеры атаковать нечего,
векторы закрыты по существу (в отличие от EPERM, который был бы политикой).
RAW-контроль: SOCK_STREAM/DGRAM с proto 255 → EPROTOTYPE(41), что с §163
(EPERM на SOCK_RAW) не противоречит.

### sysctl/ioctl: записи закрыты, чтение частично

- sysctl: `kern.maxproc`=2000, `kern.ipc.maxsockbuf`=8388608 читаются;
  **все `net.inet.*` чтения → EPERM(1)** (песочница запрещает даже чтение);
  `net.inet6.ip6.hoplimit`, `net.inet.ip.mtudisc`, `net.inet.icmp.icmplim` →
  ENOENT(2) — имён нет (не мои опечатки в журнале — это строки-кандидаты,
  которых в XNU нет). Запись туда, где чтение прошло → EPERM.
- ioctl: SIOCGIF* чтения проходят; SIOCSIFMTU/SIOCSIFFLAGS с тем же значением
  → EPERM(1); SIOCSIFADDR на несуществующем `fz0` → ENXIO(6) — lookup
  интерфейса здесь раньше политики, но обхода нет: на существующем `lo0`
  запись получает EPERM. SIOCGIFCONF вернул список, но имена в моём дампе
  частично мусорные (несовпадение раскладки ifreq в дампе — артефакт
  инструмента; надёжный инвентарь интерфейсов дал getifaddrs в §174).

## 174. v171: p_mdns — mDNSResponder не отвечает ни в одном формате; 1080 молчит всем диалектам

Контроли: getifaddrs → 20+ интерфейсов (lo0, pdp_ip0, ipsec0, utun0–4, en0,
en2, awdl0, anpi0, llw0, nan0); self-roundtrip UDP 3/3 ✓.

### Метод: три сломанных детектора починены до доверия к негативу

1. `errno` печатался от `recv` и затирал код ошибки `send` — исправлено
   раздельным захватом;
2. первый слушатель был на эфемерном порту, а mDNS-ответы уходят в
   мультикаст-группу 5353 и в исходный порт запросчика — слушаем оба;
3. в дополнительной петле не было `SO_RCVTIMEO` — `recv` завис навсегда,
   процесс убит вручную, таймаут добавлен.

### Результат: ответа нет ни откуда

- unicast 127.0.0.1:5353, mDNS-meta-query и DNS-вариант (id 0x1234, RD) —
  send 46 OK, recv EAGAIN(35);
- мультикаст: **только lo0** принимает send (46); все остальные интерфейсы →
  send EHOSTUNREACH(65) даже с заданным IP_MULTICAST_IF — мультикаст-эгресс
  приложению закрыт (это и есть природа errno 65 из §163, а не «не выбран
  интерфейс»);
- **детектор-ремонт**: сокет на 5353 (SO_REUSEADDR/REUSEPORT bind rc 0) +
  IP_ADD_MEMBERSHIP rc 0, контрольные запросы — тишина;
- unicast на реальные адреса en0 (192.168.68.102) и en2 (192.168.234.3) —
  send OK, тишина;
- запрос **с исходного порта 5353** (bind rc 0) — тишина.

Остаётся две гипотезы, которые с этой стороны устройства не разрешить:
«резонер игнорирует запросы из песочницы» и «резонер не работает вообще».
Разделяет их внешний тест: с Mac `dns-sd -B _services._dns-sd._udp local` —
если iPhone отвечает на постороннего наблюдателя, резонер жив и фильтрует
нас; если нет — демон мёртв/заглох. Запланировано как внешний шаг.

### TCP 1080: принимает и сразу закрывает

`connect` → 0; неизвестный баннер → recv **0** (FIN сразу после accept);
SOCKS5-приветствие → 0; HTTP CONNECT → 0; SOCKS4a → 0. Во всех диалектах —
0 байт ответа. В §165 тот же порт дал EAGAIN(35) после записи 18 байт, то
есть поведение нестабильно во времени (то FIN, то молчание до таймаута).
Протокол не идентифицирован; это не SOCKS и не HTTP-прокси. Открытых
разговорных сервисов на loopback больше нет — связность с привилегированными
демонами по сети подтверждена как закрытая (один порт, без протокола).

### Итог недели по трём теориям

1. **bad_query-пространство** — неожиданно плодотворно: подтверждена
   **запись** в системные контейнеры (главный результат), найдены второй
   рабочий part и второй рабочий flags-бит, отрицательно закрыт self-minting
   токенов, карта -3/-4 по 22 корням;
2. **сеть** — kernel-поверхность, достижимая из песочницы: IP_OPTIONS-парсер
   доступен (поправка §165), SCTP/UDPLITE/MPTCP в ядре отсутствуют,
   sysctl/ioctl-записи закрыты EPERM;
3. **loopback-демоны** — mDNSResponder не отвечает ни в одном из семи
   форматов/адресов (с валидным детектором), 1080 без протокола;
   остался один внешний тест различения гипотез.

## 175. v172: p_bq3 — запись в файлы демонов подтверждена; part 2 открывает LaunchDaemons

§172 дал примитив (создание/запись/удаление в каталогах), но не отвечал на
вопрос, ради которого примитив нужен: **какие именно файлы привилегированных
демонов открываются на запись**. Фаза `p_bq3` (лог `results/v172-bq3.log`)
проходит три контроля в порядке и затем инвентаризацию.

### Контроль 1: release действительно ревокает

```
open до release rc=0, после release rc=1 (EPERM)
```

Важно методически: без этого измерения каждая write-проба навсегда расширяла
бы процесс, и все последующие фазы пришлось бы считать идущими «с уже
открытым escape». Release работает — расширение живёт ровно пока handle
удерживается, фазы изолированы.

### Контроль 2: part 2 и part 3 открывают РАЗНЫЕ деревья

§172 нашёл «part 2 → handle» и не спросил, что этот handle открывает.
Ответ оказался содержательным:

| корень | part 2 | part 3 |
|---|---|---|
| `/var/containers/Data/System` | denied | **OK** |
| `/System/Library/LaunchDaemons` | **OK** | **OK** |
| остальные 6 кандидатов | denied | denied |

`/System/Library/LaunchDaemons` открывается **независимо от part** — это
базовый доступ, не escape (part 3-контроль показывает тот же OK). А вот
Data/System part-2-токен не даёт: part меняет не глубину traversal'а, а
**какое поддерево контейнера токен несёт**. Part 2 — отдельный вектор с
неизвестным деревом (что именно он открывает — вне восьми протестированных
корней; кандидаты на следующий прогон: `/var/mobile/Library`,
`/Library/Preferences` с part-2-токеном уже пробовались и отказали, так что
дерево part 2 лежит в других местах — например, SystemGroup).

### Инвентаризация: 22 из 22 файлов, 63 из 63 созданий, ноль отказов

Прогон по 23 UUID-контейнерам `/var/containers/Data/System`:

- **W-open: 22 ok / 0 denied** — каждый встретившийся обычный файл
  открылся `O_WRONLY` и закрылся без изменения байта;
- **create: 63 ok / 0 denied** — маркер создавался, читался обратно и
  удалялся в каждом каталоге каждого уровня (корень UUID, Documents,
  Library, tmp, ReportCrash, HangTracer, SpinTracer, SpaceAttribution,
  PerfPowerServices, …);
- файловые капы (60 файлов / 40 каталогов) не достигнуты по файлам и
  достигнуты по каталогам — второй уровень листался не весь; кап логирован.

Среди открытых на запись — цели, ради которых это и делалось:

- **LaunchServices**: `com.apple.launchservices.securepreferences.plist`,
  `com.apple.launchservices.appmarketplaces.plist`, `DefaultAppQueryState.plist`
  (контейнер AF589EEA) — конфигурация, которую читает `lsd`;
- **кейнчейн-подобное**: `com.apple.softposreader.keychain` (7CB67CBE);
- **SQLite с WAL**: `db`/`db-wal`/`db-shm` (8EB68272),

- **секретный бандл**: `LoadAndInstallBundle_DEFAULT.sefw`;
- **аплет-индексы и кэши**: `adi.pb`, `apps.plist`, `btjm`,

W-open доказывает разрешение на open(), но не что write() не отклоняется

### Контроль 3: write(2) по-настоящему, на четырёх файлах

Write-back: прочитать файл, записать **те же байты**, fsync, перечитать,
сверить. Содержимое побайтово идентично (система не меняется), но сам
`write()` выполнился на файле, которому мы не владеем:

```
SUS_History_Tracking.log          w=4096 same=1
AppProtectionBackup.plist         w=179  same=1
katana-subscription-cache.plist   w=694  same=1
DefaultAppQueryState.plist        w=190  same=1
```

Выбор целей сознательный: логи и кэши, которые демон всё равно переписывает;
живые SQLite и кейнчейн в write-back не берём — не ради безопасности песочницы,
а чтобы не сломать измеряемую систему.

### Статус вектора

Escape bad_query — **читающий и пишущий примитив во все системные контейнеры
устройства**, с изолированными фазами (release ревокает) и без единого
отказа в инвентаризации. Следующий шаг сознательно не автоматизируется:
нужен файл, изменение которого **наблюдаемо меняет поведение демона**
(plist LaunchServices — главный кандидат: `lsd` читает его, и эффект
виден без рута). Это уже эксперимент с изменением состояния, а не проба —
планируется отдельно, с бэкапом содержимого и явным планом отката.

Изменение состояния файла демона **сделано и обратимо**: примитив не только

нашем контейнере и переживает смерть процесса — UUID контейнера меняется
между прогонами, файл остаётся (проверено прежними прогонами).

### Наблюдение за демоном: канал из песочницы закрыт — это результат

Сначала канал строился через `LSCopyApplicationURLsForBundleIdentifier` —
символ отсутствует в exports даже после явной загрузки CoreServices и
MobileCoreServices (оба dlopen успешны). Затем через
`LSApplicationWorkspace.allApplications` — класс присутствует, запрос
проходит, но возвращает **0 записей**: lsd сам фильтрует ответ для
приложения из песочницы. Значит «видит ли демон наше изменение» из
песочницы спросить нечем; mtime-канал остался единственным, и он молчит.

Честная трактовка молчания mtime: **неотличимо** от «lsd читает файл один
раз при старте и не трогает». Это не негатив о бессмысленности записи —
это негатив о канале наблюдения. Вывод для следующего шага: наблюдаемость
изменения надо строить не через mtime того же файла, а через **побочный
эффект**, который виден без песочницы (например, чтобы демон перечитал
файл, его нужно заставить перезапуститься — а перезапуск демона из
песочницы как раз и есть та привилегия, ради которой весь вектор).

Эксперимент с изменением состояния выполнялся по шаблону, который отныне
обязателен для всех подобных: контроль → верифицированный бэкап в чужом
контейнере → изменение детектируемым способом (репарс с ключом) → наблюдение
→ побайтовый откат. Четыре прогона фазы (два честных негатива по символам,
один по фильтрации, один итоговый) не оставили систему изменённой ни разу.

4. скан adrp+add в дизассембле → VM-адреса строк (`__cstring`,

`t=165s WAL +49K` и **oracle-строка удалена сервисом, контрольная
(реальный bootId) выжила**. Семантика `DELETE WHERE bootId != current`
подтверждена **в том же буте** — cleanup исполняется при каждом открытии
магазина, если есть чужие строки; гипотеза «только при смене бута»
отвергнута. Три контрольных окна чисты: бездействие / «спросил время»
(чужой фид) / «сколько таймеров» (прямое чтение фида) — **чтение не
открывает store на запись и cleanup не запускает**.

Третье и четвёртое окна закрепили триггер: **запуск таймера в Clock =
детерминированное событие** (`com.apple.mobiletimer` пишет строку →
открытие → cleanup; срабатывания на t=272 и t=31). По §144 порядок
выдержан: сперва доказанный детектор (oracle + WAL-stat), потом
измерения. Все окна заканчиваются побайтовым откатом (2/2, 8/8,
identical=1).

### Формат строки магазина (захвачен целиком, bq27-дамп)

7 столбцов: `feedId|bootId|bundleId|entityId|lastUpdate|lnValue|metadata`.
`lnValue` — NSKeyedArchiver-bplist. Строка таймера (714 байт) декодирована:
`LNValue{valueType=LNEntityIdentifierValueType, value=LNEntityIdentifier`
`{typeIdentifier="TimerEntity", instanceIdentifier=<UUID>,`
`bundleIdentifier="com.apple.mobiletimer", stableIdentifier=nil,`
`auditToken=nil}, exportedContent=$null, displayRepresentation=$null}`;
`entityId="TimerEntity/<UUID>"`, `metadata=NULL`. Строка хранит **только
идентификатор сущности** — без длительности и названия. Отмена таймера →
producer **сам удаляет** свою строку (наблюдено в bq34-erase).

3. Остающиеся варианты, если направление возобновлять: (а) **crash-oracle**

## 187. v179: INPUT ДОКАЗАН — подсаженная строка видна Siri, битые байты роняют intelligencecontextd

### Оговорки методики (обе сломали первый «откат»)

1. **Второй `plant` перезаписал бэкап**, сняв его поверх уже
   посаженных строк, — `rollback` вернул заражённый снапшот, и первый
   дискриминатор Siri оказался недействителен.
2. **LIKE-баг**: `entityId LIKE 'FZ29%'` не совпадает с

### Что это даёт

1. **Примитив написания сущностей, видимых Siri** — интегральность:

2. **Десериализация атакующих байтов в привилегированном демоне**

   наша песочница — IOKit/sysctl/raw-сокеты §142–146 снова достижимы).
3. Триггер чтения — пользовательский запрос Siri к фиду (не autonomous);

## 188. v181: аудит whitelist-декодера через Siri-оракул (bq38), живая консоль, починка UI

### bq38: читатель отвечает по устаревшему снапшоту — новый протокол

Главная методическая находка серии: **сразу после изменения магазина
Siri отвечает по старому состоянию**. Доказательство — `m0`
(контроль прозрачности: оригинальный архив 714 B, прогнанный через
plistlib round-trip без единой правки, 643 B): сразу после посадки
Siri «нет таймеров», **через несколько минут фантом появился сам**
(«откуда-то взялся таймер» — оператор). То есть:

1. перепаковка plistlib **валидна** (фантом = архив m0 успешно
   распакован декодером) — сомнения в формате отпали;
2. ранние «нет» в этой серии (в т.ч. первый тест m1 и m0-«нет»)
   **недоказательны** — гонка чтения, не решение декодера.

Новый протокол bq38 (и для любых тестов этого класса): **после plant
ждать ≥5 минут** перед вопросом к Siri; быстрые ответы в счёт не
идут. Контроль `ctrl` (оригинальные 714 B) совпал только потому, что
перед вопросом случайно была пауза.

### Вердикты (все — с паузой ≥5 мин, кроме явно помеченных)

| вариант | байты | что подделано | ответ Siri | вывод |
|---|---|---|---|---|
| ctrl | 714 B оригинал | — | «один» | детектор жив (§144) |
| m0 | 643 B round-trip | ничего (контроль формата) | «нет»→позже «один» | гонка чтения; формат ок |
| m1 | 652 B | value-объект `LNEntityIdentifier` → `NSMutableString` | «нет» | **reject** |
| m2 | 611 B | `valueType` `LNEntityIdentifierValueType` → `NSDictionary` | «нет» | **reject** |

**Белый список строг на обоих проверенных слотах.** `NSKeyedUnarchiver`
с secure-coding ловит class-masquerade в value- и valueType-слотах —
эксплойт-поверхность class-masquerade по этим слотам **закрыта**.
Итог направления §187: остаются два подтверждённых примитива —
**integrity** (валидная подсаженная строка видна Siri) и **DoS**
(битые байты роняют демон). Остаточный незакрытый риск: вложенные
контейнеры (если LNValue декодирует словари/массивы без ограничения
содержимого — классические гаджеты). Проверить его без RE нечем:
офлайн-разбор карвов упёрся в устройство dyld-кэша — одинаковые
строки коалесцируются между образами (селекторы вне карва), а
заголовки карва инструменты отвергают как обрезанные (`objdump`:
"truncated or malformed object"). Путь — тянуть целый сабфайл кэша
(много десятков МБ) либо символику `.symbols`; отложено.

| T8 | RR36 | **65472** | ок | дроп | ПЕРВЫЙ байт раннего выхода |
| T9 | NOP4 | 65507 | ок | дроп | ранний выход и при optlen=4 |

Расчёт `36 + (20+8+P) > 65535 ⇔ P ≥ 65472` совпал с наблюдаемой
границей (T7 доставлен / T8 дроп) **байт-в-байт** — чем подтверждено,
что `ip_len` включает IP-заголовок (согласуется с успех-веткой:2265
`ip->ip_len += optlen`). T9 показывает, что граница зависит только от
`ip_len`, не от размера опций. `send()` возвращает **успех**: пакет с
ihl=0 строится и убивается на входе (`ip_input`, hlen<20 → `ips_badhlen`,
ip_input.c:1082, — до PF и до `ip_dooptions`). Это тихая потеря пакета,
не ошибка и не паника.

Однократно (прогон 2, до добавления T7–T9) T6b вернул EMSGSIZE
(в прогоне 3 тот же тест прошёл). Невоспроизведённый отказ похож на
state-dependent ветку (гипотеза: динамически регистрируемый ipfilter
вместе с CSUM_TSO → ip_output.c:1187/1570); лог прогона 2 утрачен —
runf перезаписывает общий лог. Урок: сохранять лог после каждого
прогона, а не только финального.

### Эксплуатируемость

- **локально — нет**: пути после ihl=0 проверены по исходникам и
  подтверждены живым прогоном: `ip_fragment` с hlen=0 (len = mtu&~7 ≥ 8,
  EMSGSIZE при len<8 недостижим), m_adj, PF/NECP читают фиксированные
  смещения; дроп — на `ip_input` с hlen<20 ДО PF и до парсера опций.
  Ни паники, ни неограниченных чтения/записи.
- **примитив — генерация битых ihl=0 фрагментов**: локально умирают на
  loopback; при dst через en0 уйдут на провод — DoS-сигнатура, не r/w.
  Эмиссию наружу не тестировали (en0 мёртв для достижимости парсера —
  loopback бьёт в тот же `ip_input_first_pass`; отловить можно tcpdump
  на Mac).
- icmp-ветка (T4) шлёт PARAMPROB с code = смещение опции (bounded ≤ 60);
  наблюдение невозможно без raw-сокета (EPERM).

### Вердикт направления

Reachable-код IP_OPTIONS — старый hardened BSD: все четыре ветки
`ip_dooptions` (LSRR/SSRR/RR/TS) разобраны, `ip_pcbopts` валиден,
`ip_stripoptions` безопасен, переполнение `ip_insertoptions`
воспроизводимо, но ведёт только к тихой потере пакета. Ненулевого
ущерба (r/w, corruption, panic) не найдено ни статикой, ни динамикой —
**по части r/w вектор исчерпан**; остаются (а) эмиссия ihl=0 наружу
через en0 и (б) state-dependent EMSGSIZE — оба низкой ценности.

### Результат: CONTROL жив, TREATMENT = негатив (read NOT proven)

```

Прогон 2 (treatment):     CONTROL-REPAIRED at 361s
```

1. **Cadence СОБЫТИЙНО-зависимая, не таймерная**: control 150s (прогон 1) vs

2. **Демон перезаписывает поверх ЛЮБОГО контента** — plain dict так же

§180 «закрыт как OUTPUT-канал влияния»). Подмена контента через bad_query не
даёт ни исполняемого содержимого, ни остановки write-back. Различить H_read

`unarchiveObject`/чтение файла у демона через lldb (см. §194 про darwin-vm).

## §194 (v186). darwin-vm: реальное ядро 24A5390f под lldb + t8130 boot-hang

Разделение ролей VM-инструментов (решение оператора): **darwin-vm** — kernel,
**vphone-cli** — userspace. Причина: darwin-vm грузит kernelcache **из restore
IPSW** (kernel + SPTM + TXM + DeviceTree реальной платы) — то самое ядро, что
на устройстве; vphone-cli берёт kernel/SEP/devicetree из cloudOS `vphone600ap`
(26.4-линия) — чужое ядро, поэтому kernel-выводы из vphone не переносим.

### Что сделано (host: Apple Silicon, macOS 27, SIP НЕ менялся)

- `brew install ipsw ninja pkg-config glib`; клон `jprx/darwin-vm`.
- `get_files.sh` с нашим точным IPSW `iPhone16,2_27.0_24A5390f`:
  board `d84ap`, kernel ext `iphone16`, chip **`t8130`** (A17 Pro). Извлечены
  `bootkc` (73 MB) + `dtree` + `ramdisk.dmg` + trustcache. **Отдельного
  `sptm`/`txm` для t8130 в IPSW нет** (`get_files.sh` это учёл — «not all chips
  have SPTM»), поэтому `-sptm/-txm` в qemu не передаются.
- `fix_perms.sh` (нужен sudo, выполнял оператор): `bin`/`System`/`libexec` ->
  `root:wheel`, `com.jprx.bash.plist` на месте.
- qemu-sptm собран: `configure --target-list=aarch64-softmmu --disable-pvg`
  (PVG не компилируется на macOS 27, PGTask_t obsoleted) -> `make -j`,
  бинарь 37 MB, 3200/3200.

### Проблема захвата serial-консоли (разобрана, не блокер)

`run.sh` использует `-nographic -serial mon:stdio`. В фоне (без реального tty)
stdio-вывод буферизуется/теряется: ни `script` (pty), ни `-serial file:`, ни
TCP-chardev не дали boot-лог. Причина `-display none` + socket — гость не
стартует вовсе (0% CPU, vCPU не поднимаются). **Вывод**: для ядерных
исследований serial-консоль НЕ нужна — работает GDB-стаб qemu (`-s`).

### Ключевой результат: lldb на настоящем ядре 24A5390f

qemu с `-s` (GDB на :1234) + `-nographic`. `xcrun lldb` -> `gdb-remote 1234`
подключается, читает регистры и память:

```
Process 1 stopped (SIGTRAP)
pc = 0x000001000b01c10c
->  0x1000b01c10c: cbz  x21, 0x1000b01c10c   ; x21 = 0
```

Breakpoints, `memory read`, `register read`, `bt` — всёфункционально. Это
живой kernel-debugging доступ, которого раньше не было (KDK/development-kernel
путь описан в README, но для iOS он бессимвольный — lldb всё равно работает).

### Честная находка: t8130 зависает на ранней загрузке

PC **не продвигается** между сэмплами (минуты разрыва, resume между ними):
`x21 = 0`, `cbz x21, <себя>` = бесконечный спин-луп. Это **hard-hang**, не WFI
и не краш-луп. Адрес `0x1000b01c...` (~4.3 GB, низкий) — ранняя стадия
(SPTM/ignition) **до перехода XNU на high-VA** (`0xfffffe00...`), т.е. гость
не доходит до основного ядра. Вероятная причина — chip-специфичная фича
t8130, не моделируемая qemu-машиной `darwin`. В протестированной матрице
darwin-vm явно boots только t8140 (iPhone17,3 / iPhone 16); t8130 (iPhone 15
Pro) в таблице отсутствует.

**Статус**: capability доказана (gdb-remote -> lldb -> реальное ядро), но
полноценный boot-to-shell на t8130 сегодня не получен. Пути вперёд (на
завтра, не ночью): (а) диагностика hang'а через lldb (что за poll в `x21`,
нужен ли SEP/timer, который qemu не даёт); (б) повторить на **t8140**
(`iPhone17,3_27.0_24A437`, протестированная связка) — даёт XNU 27.0 для
отладки/фаззинга, очень близко к цели, хотя и не наш точный чип; (в) изучить
`-S` (старт с первой инструкции SPTM) для пошаговой трассировки раннего boot.

### Артефакты

`~/darwin-vm/` (firmware: `bootkc`/`dtree`/`ramdisk.dmg`/`ramdisk.tc` для
iPhone16,2 24A5390f), qemu-sptm собран. `relay/get_kc27.py` даёт точный IPSW
URL для `get_files.sh`. Параметры qemu с GDB: `-s` (port 1234).

## §195 (v187). darwin-vm: полный boot до root-shell — SPTM-фикс (t8122) + iPhone17,3 (t8140) 24A5390f

### Контекст

§194 закончился на t8130 boot-hang: PC `0x1000b01c10c` (ранняя стадия,
до high-VA), `x21=0`, `cbz x21,<себя>`. Hypothesis — chip-специфичная фича
не моделируется qemu. **Hypothesis оказалась ложной: причина была в
отсутствующем SPTM/TXM.**

### Корневая причина t8130-hang'а (найдена пользователем)

`get_files.sh` определяет `CHIP_NAME` через `ipsw device-info` → для
iPhone16,2 это `t8130`, и скрипт искал `sptm.t8130.release`. Apple же в
этом IPSW называет файл для A17 Pro **`sptm.t8122.release`** (согласно
BuildManifest). `check_for_file "sptm.t8130.release"` не находил файл →
`sptm`/`txm` не скачивались → `run.sh` не передавал `-sptm/-txm` → гость
висел на ранней SPTM-стадии. Фикс пользователя: fallback `t8130`→`t8122`
в `get_files.sh` (строки 110–127). Доказательство работы фикса: с
`firmware/sptm`+`firmware/txm` гость прошёл ранний hang и дошёл до
`Load Address: 0xfffffff02700c000` (Kernel UUID определён) — дальше t8130
упёрся в **другой** поллинг (`0xfffffff02a7fa5dc`, линкед-лист walk,
45с без продвижения) — уже не SPTM, а поздний kernel-boot wait
(SEP/timer, не эмулируется).

### Решение: iPhone17,3 (t8140) + та же сборка 24A5390f

Пользователь нашёл IPSW `iPhone17,3_27.0_24A5390f` (тот же build, что на
нашем устройстве, но для iPhone 16 / t8140 — протестированного в darwin-vm
до home screen):

```
https://updates.cdn-apple.com/2026SpringSeed/fullrestores/140-57108/5E816D0E-89BB-4B95-8825-6A3EDF22E509/iPhone17,3_27.0_24A5390f_Restore.ipsw
```

`get_files.sh` с этим URL: board `d47ap`, chip `t8140`, `sptm.t8140.release`
найден напрямую (fallback не понадобился). `fix_perms.sh` повторён
(get_files заново пропатчил ramdisk — 118 файлов были не root:wheel,
включая `com.jprx.bash.plist`).

### Результат: полный boot до root-shell

**Гость t8140/24A5390f загрузился до root-shell:**

```
Darwin localhost 27.0.0 Darwin Kernel Version 27.0.0: Tue Jul 14 21:27:55
PDT 2026; root:xnu-13432.0.94.502.2~2/RELEASE_ARM64_T8140 iPhone17,3 arm
bash-5.3#                              <- root-промпт, интерактив
System Policy: bash(5) allow process-exec* /bin/uname   <- sandbox активен
ACMTRM: waitForSEPEndpoint: timed out waiting for AppleSEPManager (timeoutMs=5000)
```

- **ядро — точная сборка 24A5390f / xnu-13432.0.94.502.2~2** (совпадает с
  устройством по build, отличается только чип-специфика t8140 vs t8130);
- `bash-5.3#` — root-шелл, спавнится launchd'ом (`com.jprx.bash`);
- System Policy пишет audit-записи — sandboxed-политика гостя активна;
- SEP-tаймауты (`waitForSEPEndpoint`) — циклический поллинг, **не блокирует
  shell** (ядро многопоточное; поллинг-цикл на одном потоке, bash — на
  другом). PC-сэмпл lldb часто ловит именно SEP-poller — это не hang.

### Интерактив через TCP-serial: рабочая методика

Проблема: `-serial mon:stdio` в фоне — ввод уходит в QEMU-монитор (мутиплекс,
focus по умолчанию monitor, переключение Ctrl-A c), FIFO-stdin блокируется на
открытии без писателя, `-display none` — vCPU не стартуют (паттерн
подтверждён повторно), stdout в файл даёт block-buffering (малые ответы не
flush'атся), kill nc-opencode'ом рвёт процесс-группу → bash получает SIGHUP
и умирает (serial-сессия не восстанавливается новым подключением!).

**Рабочая схема:**

```sh
qemu-sptm/build/qemu-system-aarch64 -M darwin \
  -bootkc firmware/bootkc -dtree firmware/dtree -tc firmware/ramdisk.tc \
  -ramdisk firmware/ramdisk.dmg -sptm firmware/sptm -txm firmware/txm \
  -args "rd=md0 serial=3 -v -noprogress wdt=-1 wlan-olyhal-abort" \
  -nographic -serial tcp:127.0.0.1:4556,server=on,wait=off -s -m 8G
```

- boot ~2–4 мин (вариативно); **не подключаться раньше ~200с** — ранний
  serial шлёт только ACMTRM/launchd-сообщения;
- после boot гость **idle на prompt (CPU 0%) — это норма**, не hang;
- одна nc-сессия со всеми командами сразу:
  `{ printf 'uname -a\r\n'; sleep 2; ... } | nc -w 14 127.0.0.1 4556`;
- **bash переживает разрыв nc** (SIGHUP убивает его, если disconnect в момент
  активности; в тихом состоянии выживает между попытками — проверено: входы
  накапливаются, ответы приходят со следующей попыткой);
- постоянная nc-сессия через `nohup + двойной fork + exec 7<>fifo` живёт
  между tool-вызовами, но `stdbuf -o0` обязателен, иначе stdout-буфер nc
  прячет вывод до выхода.

### lldb — основной инструмент исследований (надёжнее serial)

```
(lldb) gdb-remote 1234
Kernel UUID: 09C85910-8327-37E3-8AFE-1CF3F99052EF
Load Address: 0xfffffff02700c000
(lldb) memory read --size 8 --format x --count 4 0xfffffff02700c000
0xfffffff02700c000: 0x0100000cfeedfacf 0x00000002c0000002 ...
```

Регистры, память, bt — работают; Mach-O magic по load address. Attach
останавливает гость — после сэмпла обязательно `process continue`.

### Итог v187

1. **t8130-hang разобран**: не qemu-limitation, а отсутствие SPTM из-за
   несовпадения имён (`sptm.t8122` vs `sptm.t8130`). Фикс — в get_files.sh.
2. **Рабочая ядерная песочница получена**: iPhone17,3/t8140/24A5390f —
   точная сборка устройства, root-shell, sandbox-политика активна, lldb
   читает живое ядро. Kernel-фазы/исследования через gdb-remote теперь
   доступны без реального устройства.
3. t8130-firmware сохранена (`firmware_t8130_backup/bootkc_t8130`) —
   kernelcache нашего чипа для статического RE.

`~/darwin-vm/firmware/` — iPhone17,3 24A5390f (d47ap/t8140); `boot_proof_t8140_bash.log`

## §196 (v188). VM-лаборатория: пайплайн «собрать→положить в ramdisk→запустить→вывод» + первый ядерный фаззер IP_OPTIONS

### Пайплайн выполнения кода в госте (после §195 serial-эпопеи)

Цель этапа: не заливать бинари через serial (квирки tty-буфера убили множество
попыток), а класть их в ramdisk-образ с хоста. Рабочая схема, проверенная
end-to-end (`/bin/probe` и `/private/var/tmp/probe` выполнены в госте):

1. **Сборка**: `xcrun -sdk iphoneos clang -target arm64-apple-ios17.0 prog.c -o prog && codesign -s - prog`.
2. **Положить в образ — БЕЗ sudo**: `hdiutil attach -owners on -mountpoint $MNT firmware/ramdisk.dmg`
   (образ user-owned, монтируется от kurt228) → `cp prog $MNT/private/var/tmp/` →
   `chmod 755` → `detach`. В госте `/private/var/tmp` = 1777, файл виден как
   `mobile:wheel` (хост-uid 501) и world-exec — **AMFI пускает** (см. п. 4).
   Альтернатива с sudo: `sudo ~/darwin-vm/addprog.sh prog` → `/bin/probe`
   (root:wheel, добавляет cdhash автоматически).
3. **Trustcache**: `codesign -d -vvv prog | grep cdhash= >> firmware/all_hashes`
   (если нет) + `./build_tc.py firmware/all_hashes firmware/ramdisk.tc` — без sudo.
4. **Запуск гостя**: `socat PTY,link=/tmp/gpty,rawer,echo=0,ignoreeof EXEC:"/tmp/run_qemu.sh",pty,setsid,ctty`
   + **один** `cat < /tmp/gpty > pty_console.log` с первой секунды (захват boot-лога).
   stdin-fifo для `-serial mon:stdio` не работает (qemu stdio-mux теряет ввод без tty);
   PTY через socat — работает.
5. **Команды**: python `os.open('/tmp/gpty', O_RDWR|O_NOCTTY)` + non-blocking,
   запись с retry (EAGAIN = tty-ввод переполнен → читать и ждать), ответы
   приходят **с задержкой десятки секунд** — читать повторными drain-сессиями.

### Ловушки serial/PTY (дополнение к §195)

- Boot ненадёжен: ~50% попыток зависает на SEP-poll (`0xfffffff02abc5914`,
  ACMTRM молчит). Детект: `grep "spawned bash" pty_console.log` за 400 с,
  иначе рестарт. Авто-цикл «старт → ждать 400с → рестарт» проходит с 1–2 попыток.
- **Два `cat`-читателя на одном PTY = данные делятся, лог затирается truncate'ом**
  (потеряно несколько захватов). Ровно один читатель.
- Детектор SIGALRM (`alarm(2)` → `write(1)` в фоне) **не сработал** — ALIVE=0;
  детектор живости фаззера = `MILESTONE`-write в основном цикле (~1/с).
  По §144: подтверждено, что MILESTONE реально доходят в лог.
- `set -e` + `pkill` отсутствующего процесса = exit 1 на середине установки.

### Recon гостя (root, полный вывод в pty_console.log)

- `uname -a`: `Darwin localhost 27.0.0 ... xnu-13432.0.94.502.2~2/RELEASE_ARM64_T8140 iPhone17,3`.
- `/` = `dev/md0` **apfs read-only** — runtime-запись в ФС невозможна; вывод только в консоль.
- `/System/Library/Extensions` = 6 kext (AppleHPM, AppleSPURose, IOHIDFamily,

- System Policy логирует каждый exec (`System Policy: bash(N) allow process-exec* ...`) —
  sandbox в госте активен, bash в нём.
- kASLR: mach_header найден по `0xfffffff027004000` → **slide = 0x20000000**

### Первый ядерный фаззер: IP_OPTIONS (запущен)

## §197 (v189). Ядерные фаззеры в VM: матрица ioctl-поверхности + КРИТИЧЕСКОЕ исправление методики (lldb-pause = ложные «зависания»)

### Исправление методики (главный итог — иначе будущие выводы ложны)

**ВСЕ «зависания гостя» этой итерации оказались артефактом lldb**: каждая
команда `xcrun lldb -o "gdb-remote 1234" -o "register read pc" -b` СТОПИТ
vCPU (gdbstub), а при завершении/убийстве lldb qemu **не возобновляет** гостя
— vCPU остаётся в cond-wait (`mttcg_cpu_thread_fn → qemu_cond_wait_impl`),
CPU 0%, PC заморожен, ACMTRM (таймерные printk) прекращаются. Так
«зависли» ipfuzz+ioctlfuzz+bash (§ hang#1/hang#2 этой сессии) — на самом
 деле ядро работало, всё было по-прежнему живо.

Симптомы артефакта: PC идентичен в нескольких сэмплах подряд, CPU qemu 0%,
нет ACMTRM >30 с, команды в консоль молчат. Лечение: запустить lldb в фоне
`nohup xcrun lldb -o "gdb-remote 1234" -o "continue" -b` (гость
возобновляется и продолжает с того же места; убийство lldb снова стопит).
Правила:
1. PC-сэмплы — только по крайней необходимости; каждый сэмпл = pause гостя.
2. После любого gdb-подключения — обязательно `continue` (держать lldb живым
   до конца серии) и проверка «ACMTRM пошли / вывод растёт».
3. «Зависание гостя» констатировать только по СВЕЖЕМУ выводу консоли
   (не cat-буфер: cat block-buffered ~4–8 КБ, лог «стоит» минутами при
   живом госте — это уже не раз ловило на ложный диагноз).

Попутно подтверждён реальный (не артефактный) феномен: **ioctl на /dev/oslog
блокирует вызывающий поток** (см. ниже) — в hang#1 ioctlfuzz реально встал
на oslog-ioctl, но система при этом жива (bash отвечал, kill -0 работал).

### IP_OPTIONS фаззер: 1 036 000 итераций без паники (§196 продолжение)

`ipfuzz` (udp-сокет,5 режимов кривых IP-опций → setsockopt(IP_OPTIONS) → при
успехе getsockopt + sendto loopback:9) отработал **1,036,000 раундов
(ok=153,026 / fail=882,974)** до планового рестарта. Детектор MILESTONE
(write в цикле, подтверждён потоком в лог). Паники/крашей нет — негатив
валиден по §144 (детектор доказанно работал). Ограничение: 1 vCPU гостя,
парсер опций — XNU 13432.0.94.

### Матрица ioctl-поверхности /dev (sweep, §197 инструмент)

Инструмент `sweep.c`: матрица «устройство × ioctl», каждая ячейка = fork,
ребёнок крутит ioctl-цикл с «тиками» в pipe, родитель ждёт тики ≤8 с;
тикнуло >1 = здоров, только стартовый тик (n=0, до первой ioctl) = блок.
Открытые как root: bpf0, bpf1, pf, oslog, monotonic, random (klog — нет).

| устройство | BIOCSETWF | BIOCSETBLEN | BIOCSETIF | rand-req | BIOCGBLEN | FIONREAD |
|---|---|---|---|---|---|---|
| **oslog** | **1** | **1** | **1** | **1** | **1** | **1** |
| bpf0 | 25 | 25 | 24 | 25 | 25 | 155 |
| pf | 26 | 26 | 26 | 26 | 26 | — |
| monotonic | 13 | 11 | — | — | — | — |
| random | — | 26 | 26 | 27 | 27 | 184 |

(значения = ticks, «здоровые» ячейки ≫1)

**/dev/oslog: ЛЮБАЯ ioctl (включая бенигн BIOCGBLEN/FIONREAD) блокирует
вызывающий поток навсегда** — воспроизводимо 6/6; независимо подтверждено
ioctest osl6 (завис на 1-й итерации при живой системе: bash отвечает,
`kill -0` подтверждает процесс) и ioctlfuzz v2 (встал на I10:f6:m6, fd6=oslog).
**Переносимость на устройство НЕ установлена**: наиболее вероятно
qemu-специфичное поведение (нет oslog-бэкенда/коллектора — ioctl ждёт
транспорт навсегда); на 24A5390f не проверялось (там oslog функционирует).
Как DoS-вектор с устройства — нерелевантен (из песочницы /dev/oslog не
открывается).

**bpf0/pf/monotonic/random здоровы**: тысячи ioctl/8 с, BIOCSETF с программами
из валидных BPF-opcodes с кривыми jt/jf/k и BIOCSETFNC с сырыми байтами —
без паник; случайные ioctl-номера — ENOTTY. Это здравый негатив по
BPF-интерпретатору ядра в данной сборке.

Предыдущая изоляция: `/dev/random`+mode6 (ioctest rnd6) — 54,782 итерации
без блоков (не он причина hang#1).

### Что это значит

1. **Гаджет-поверхность открыта.** В либеральные слоты можно положить
   произвольный $class-объект — NSKeyedUnarchiver сервиса проинстанцирует
   любой класс с initWithCoder из адресного пространства
   LiveEntityService в момент, когда клиент с `live-entities.read`
   (navd) прочитает фид. Дальше безопасность зависит только от набора
   классов с опасным initWithCoder в сервисе и его фреймворках
   (AppIntentsLiveEntitySupport, IntelligenceFlow{Context,Planner}Runtime
   — бинарии изъяты, §185/bq21).
2. **Бизнес-валидация LinkServices кидает исключение** ПОСЛЕ успешного
   декода (слот value: неизвестное значение типа/пустая строка). Throw
   всплывает из unarchivedObject (у нас его поймал @try). Если вокруг
   unarchive в итерации feedEntries сервиса нет @catch — это
   наблюдаемый краш сервиса, триггеруемый посадкой архива в БД (запись
   в 8EB68272/db доступна, §170/§184). Проверить: RE сайта 0x1000156b0 в
   svc.bin на compact-unwind/exception-хендлер.
3. **§188 переосмыслен**: «whitelist строг на value/valueType» с
   валидными байтами подтвердилось, но механизм — throw бизнес-валидации
   (value), а не класс-гейт: NSMutableString и вложенный LNValue в value
   ДЕКОДИРУЮТСЯ. Старые m1/m2-вердикты списываются на формат.

## §199 (v191). bq40–bq43: гейт добит до конца — произвольные классы закрыты, сырые значения отбрасываются сеттерами; эскалация через декодер LNValue ЗАКРЫТ, остался DoS-кандидат

### bq40: эксзотические классы в либеральные слоты — все REJECT

`$classname=EXOTIC + $classes=[EXOTIC]` в stableIdentifier (и
cross-slot в exportedContent): NSNull, NSUUID, NSURL, NSPredicate, NSSet,
NSMutableSet, NSIndexSet, NSMutableData, NSObject, LNEntityIdentifier,
LNEntityIdentifierValueType — **REJECT 4864 все 11 вариантов**. Слот
принимает NSDictionary (инлайн, §198) — но НЕ как $class-инстанцию.

### bq41: спуф $classes не работает

`$classname=NSNull + $classes=[NSDictionary, NSObject]` (и NSNull с
честным `[NSNull]`, NSObject/NsPredicate/NSUUID/LNEntityIdentifier со
спуфом) — REJECT 4864 все 8. Проверка идёт по РЕАЛЬНОМУ классу
($classname -> class), не по массиву $classes из архива. Спуф-вектор
закрыт. Вылезла аномалия: `NSDictionary + $classes=[NSDictionary]` (без
NSObject) тоже REJECT, а bq39-формула `[NSDictionary, NSObject]` — ACCEPT.

### bq42: разбор аномалии — инлайн vs $class-инстанция

`m_dict_full` (NSDictionary+[NSDictionary, NSObject], ровно формула
bq39, но через UID-ссылку в $objects) — **REJECT**. Причина найдена в
генераторе: bq39 `mkdict()` возвращал словарь, который присваивался в
слот ИНЛАЙНО (сырое plist-значение в поле архива) — оно НЕ проходит
$class-машинерию вовсе. Т.е. «принимающие» слоты §198 принимали СЫРЫЕ
значения, а не объекты. Следствие: единственные $class-инстанции,
проходящие на si-слоте, — с `$classes` содержащим NSString
(`NSMutableString+[NSString,NSObject]` — ACCEPT, единственный успех
bq42); NSDictionary/NSArray/NSData/NSNull/NSPredicate-$class — REJECT.

### bq43: property-census — инъекция в состояние объекта НЕ работает

Декодированные из «принимающих» вариантов LNValue (si_dict, si_str,
bi_dict, ec_dict, at_dict, dr_dict, ct_dict) — census всех свойств
(KVC): **каждое мутантное свойство = nil** (включая si_str: сырая
строка 'FZSI' тоже отброшена, хотя allowed-гейт NSString-инстанции
пропускает). Сеттеры LNValue/LNEntityIdentifier тип-чекают присваиваемое
и дропают неверное — состояние объекта байт-в-байт эквивалентно ctrl
(те же nil). **Типовой путаницы нет, gadget-поверхность мертва.**

### Итоговая модель декодера (все глубины, полная)

1. Top: сервис зовёт Swift `unarchivedObject(ofClass: LNValue.self)` —
   ObjC-гейта для сырых plist-значений нет (top_str ACCEPT в bq39), но
   Swift-мост вернёт nil -> лог «Found nil when unarchiving LNValue» ->
   мягкий пропуск строки. Для сервиса безвредно.
2. `value`/`valueType`/`typeIdentifier`/`instanceIdentifier` — строгие:
   класс-гейт проверяет и сырые значения (по нативному классу), и
   $class-инстанции (по реальному классу).
3. Прочие слоты (`exportedContent`, `displayRepresentation`,
   `bundleIdentifier`, `stableIdentifier`, `auditToken`, `contentType`):
   decode без классовой проверки -> сырые значения ДОХОДЯТ до
   сеттеров, но сеттеры отбрасывают по типу (bq43) -> объект не меняется.
4. $class-инстанции везде: allowed = маленький набор (на si подтверждён
   NSString); эксзотика и спуф закрыты.
5. **Выживший вектор**: маскарад `value`-слота (NSMutableString,
   вложенный LNValue, строка вне enum IdentifierValue) -> decode
   проходит -> бизнес-валидация LinkServices кидает
   NSInternalInconsistencyException («BUG IN CLIENT OF LINKSERVICES:
   ... is not member of type IdentifierValue») -> исключение всплывает
   из unarchivedObject; в svc.bin **нет ни одного objc_begin_catch**
   (grep дисассемблеи: 0 хендлеров) -> Swift-вызывающий ObjC-исключения
   не ловит -> краш LiveEntityService при чтении строки клиентом с
   `live-entities.read` (navd). DoS-кандидат; эскалации не даёт;
   наблюдаемость рестарта сервиса из песочницы слабая.
6. Декодер-поверхность сервиса ИСЧЕРПАНА: fixups показывают ровно ОДИН
   keyed-unarchive API (`unarchivedObject7ofClass4from`, auth-stub
   0x10004c6fc) и ровно один whitelist (LNValue). NSKeyedArchiver тоже
   импортируется — сервис что-то архивирует (write-back в БД, согласуется
   с §184).

### Решение по линии bq

Эскалация через feed-БД/декодер LNValue **закрыта** (нет произвольной
инстанциации классов, нет инъекции в состояние, top-level защищён
Swift-мостом). DoS-краш сервиса — низкоценный баунти, требует оператора
(посадка + триггер чтения + наблюдение) — откладывается. bq-линия
исчерпана как вектор эскалации.

Следующие живые направления (карта AGENTS.md): IP_OPTIONS/LSRR как
инструмент (легальные опции достижимы, §165/§189), loopback-демоны
через публичные фреймворки (не пробовались), VM-soak (идёт), AppleMSG
(§169).

### Два воспроизводимых kernel data abort (оба — через IOServiceOpen)

1. **AppleAstrisGpioProbe, type=0** — `Kernel data abort at pc
   0xfffffff028865598` (кекст+0xA38), far=0x0 (NULL+поле), ESR 0x96000006.
   Детерминирован: ×4 в четырёх независимых загрузках, репро
   `iokitfuzz Astris 0 0 0 1` — входит в кекст и падает ДО своей
   авторизации. Кекст **есть в retail-кэкше 24A5390f** (строки: своя
   авторизация, `cscommand_t`-гейты с готовыми warning'ами про out-of-bounds
   и buffer overflow, RelayGet, `function-grape_cs`), **НО сервиса в
   IORegistry устройства нет** (matching → nil ×3 из песочницы) — нуб
   девайс-борда-специфичный, на retail-железе не публикуется. На устройстве
   недостижим; баг закрыт для нашей цели, отмечен для отчёта.
2. **H1xANELoadBalancer, type=0** — `Kernel data abort at pc
   0xfffffff02a352168` внутри `com.apple.iokit.IOSurface(402.5)` (+0x1ea68),
   far=0x140, в бэктрейсе `AppleH16ANEInterface(10.16.2)` (lr кекста +0xa230).
   Цепочка: open ANE-сервиса → newUserClient H16ANE → вызов в IOSurface по
   NULL. ×2. В qemu ANE-железа нет — NULL от неинициализированного стека.

Оба открытия из контекста root в госте прошли MACF (логировался deny только
на `RootDomainUserClient`); гостевой MACF подтверждает: **даже root в
restore-окружении получает iokit-open deny на отдельные классы**.

### Устройство: живая ANE-поверхность из песочницы

## §201. ANE-линия закрыта: type=4, сплошной BadArgument-гейт, MIS-отсечение entitlement (v193)

### Расширение карты типов ANE

`IOServiceOpen(H1xANELoadBalancer)` принимает **два** type: 1 и 4 (свип
0..0xff: 252 проверки, остальные → NotReady/BadArgument). На ОБОИХ
соединениях полный свип идентичен и безуспешен: 512 селекторов × 4 формы +
проба форматов 700 (insz 1..2048 × nsc 0..8 × 10 селекторов) + скалярная
форма 1024 (nsc 1..8, insz=0) = **2236 вызовов на тип, все 0xe00002c2
BadArgument**, выходные буферы не тронуты, SetNotificationPort → NotReady.
Итого по ANE из песочницы: 4472 вызова, ноль исключений из формат-гейта.
Кекст (carve `com_apple_driver_AppleH16ANEInterface.macho`, 2.27 МБ, xref-RE
через objdump): два класса клиентов (H11ANEInUserClient,
H11ANEInDirectPathClient), entitlement `com.apple.ane.iokit-user-access`
вычисляется в initWithTask в байт-поле объекта (сравнение с
kOSBooleanTrue), рядом `com.apple.ane.allow-dataChaining-access`; лог-строка
`External Method Call with selector %u result %u [Client: %s, PID: %d]`
подтверждает existence диспетчеризации, но таблица IOExternalMethodDispatch
не поднимается офлайн (nsyms=0, PAC-подписанные указатели в DATA_CONST).

### Entitlement-инъекция: MIS режет на установке (определённый негатив)

Тест (согласован с оператором): `com.apple.ane.iokit-user-access = YES`
добавлен в ent.plist (python plistlib — **plutil -insert не принимает
точки в имени ключа**, трактует как keypath), 5 app-groups не тронуты.
Установка: **«This app cannot be installed because its integrity could not
be verified» (IXUserPresentableErrorDomain 14)** — MIS отвергает приватный
entitlement вне provisioning-профиля. Прошлый прогон «с entitlement»
фактически гонял старый бинарь: проверка установки `grep -ci installed`
была обманута текстом ошибки (в нём тоже есть «Install») — **проверять
exit-код devicectl, не текст**. ent.plist откачен из бэкапа byte-identical
с HEAD, установка восстановлена (exit 0).

Вердикт: на стоке iOS песочница **не может** получить ANE-entitlement →
методы ANE- user-client'ов закрыты для нас by design (BadArgument на
верхнем уровне, обход форматами исчерпан). Единственное достижимое —
open/close типов 1 и 4.

### Детектор собственных entitlement'ов (с контролем, §144)

`SecTaskCreateFromSelf` + `SecTaskCopyValueForEntitlement` через
dlsym(RTLD_DEFAULT) в фазе p_astris: контроль
`com.apple.security.application-groups` → **PRESENT** (наши entitlement'ы
реально доходят до процесса), ANE-ключ → ABSENT (после отката, как и
ожидалось). Детектор валиден и остаётся в фазе.

### Гостевой iokitfuzz v8: матрица отказов

fork+watchdog v7 переигран с логом kr неудачных open: **316/316 пар
(класс,type) → единый kr=0x10000003** (нетипичный для IOReturn-таблиц,
единый sandbox-трансляционный отказ), OPEN=0, WEDGE=0, HIT=0. Root в
госте не открывает НИ ОДНОГО userclient, кроме двух паникеров (оба — в
MACF-allow-списке или их open-path не доходит до политики). Допущение §196
«в госте root открывает всё» для userclient'ов **закрыто окончательно**:
ценность гостя — только бесплатные паники известных кекстов.

### Итог по ANE-вектору и инструментальные уроки

ANE-фаззинг из песочницы **закрыт**: оба доступных типа дают единый
верхнеуровневый гейт, entitlement-путь перекрыт MIS на стоке. Открытые
заметки на будущее: привилегированные клиенты (ANEPrivilegedVMAccessUserClient,
ANEDriverDebugClient) достижимы только вне песочницы; на госте возможен
отдельный трек — разработка эксплойта поверх паники H16ANE→IOSurface

Логи: `results/v193-astris-ane-type4-final.log`,
`results/v193-ane-ent-install-fail.log`.

Направление v194: (а) гость — эксплойт-разработка по данным-аборту

## §202. Перечисление XPC из песочницы: единственный reachable-сервис — extensionkitservice с TCCProxy-подсервисом (v194)

### Перечислитель с контролами (§144)

Новая фаза `p_xpcenum` (`FUZZ_XPCENUM=1`, полное перечисление / `=2`,
статика-сбор): кандидаты = CFBundleIdentifier всех `*.xpc`-бандлов
/System/Library/{Frameworks,PrivateFrameworks,CoreServices} + Label и
MachServices-ключи launchd-пллистов. На каждое имя —
`xpc_connection_create` + resume + ping(пустой словарь) + классификация
события (XPC_TYPE_ERROR vs обычный словарь). Контроли: заведомо
несуществующее имя (`com.apple.zzz.invalid.control`) обязано дать invalid
— дал; **любой позитив доказывает канал**.

Итог: **3012 кандидатов, 3007 invalid, 4 без события, РОВНО ОДИН
позитив**: `com.apple.extensionkitservice`. Метод валиден; негатив по
остальным 3011 именам — валиден (контроль + позитив прошли).
`xpc_connection_create_mach_service` на iOS не экспортируется (§v155, замер
линковки) — mach-имена в принципе недостижимы; достижимы только
XPC-сервисы.

### Что такое reachable-сервис

`/System/Library/Frameworks/ExtensionFoundation.framework/XPCServices/`
`extensionkitservice.xpc` (exe 70 КБ, версия 97, iPhoneOS 27.0).
Info.plist: **BSServiceDomains.XPCService.Services = { Discovery, Launch,
Observer, TCCProxy }** — BootstrapService-домен с четырьмя подсервисами.

`com.apple.private.tcc.manager.access.read = [kTCCServiceAll]` (чтение
ВСЕЙ tcc-базы), `com.apple.private.coreservices.canmaplsdatabase`,
`com.apple.private.extensionkit.host.any-extension`,
`com.apple.private.xpc.domain-extension.proxy`,
`com.apple.private.xpc.persona-manager`,
`com.apple.runningboard.{launch_extensions,launchprocess,process-state,

Подсервисы как имена-суффиксы (`...Discovery` и т.д.) → invalid:
адресация BS-домена не по имени — нужен wire-формат первого
bootstrap-сообщения (живёт в клиентском коде BootstrapServices/
ExtensionFoundation — в dyld-кэше, on-disk бинари framework'ов на этом
билде нечитаемы: bytes=0).

### Значение вектора

Живое соединение с процессом, у которого есть права на запуск любых
расширений (`launchprocess` + `host.any-extension`), чтение всей tcc-базы

## §203. BSXPC extensionkitservice: чекин живёт в приватном libxpc-слоте, а не в первом сообщении — хендшейк из песочницы работает (v195–v202)

### Тупик «первого сообщения» (bq44–bq52)

Все пробы v195–v199 (activate/connect/SEL/голые словари/теги bsxpc) и
полный «чекин» `{lp, s, i}` первым сообщением (bq51, v199: 6
сервис-имён × 2 инстанса + 3-сообщевые последовательности; bq52, v200:
`'mx'` root-пробы) получали один и тот же `{"bsxpc":"invalidate"}`.
Контроли при этом жили (§144): голое `{}` → invalidate, lp-only →
invalidate. RE v199 декодировал серверный путь:
`+[BSXPCServiceConnection _connectionWithIncomingXPCConnection:forEndpoint:]`
(0x18fb00044) читает `'lp'` (обязателен, иначе «Rejected due to
malformed checkin_info» → invalidate) из объекта, полученного вызовом
`0x1900f58c0(x1)`; затем `+[BSServiceListenerConnection
_connectionFromIncomingConnection:]` (0x18fb03924) декодирует из
initiating-context `'s'` (0x1e0a7e7a8 → CFSTR 's' 0x1e9e288f8,
обязателен — nil даёт cancel `-[BSXPCServiceConnection cancel]`
0x18fb21db8) и `'i'` (0x1e0a7e7b0 → 0x1e9e28918); lookup в
`servicesByIdentifier` домена (`objectForKey:` на [[spec]+0x18]),
мимо — «Unknown service … Invalidating the connection».

### Резолв кэш-стабов: настоящий механизм (v200)

Все `0x190xxxxx` — стабы `/usr/lib/objc/libobjcMsgSend1.dylib`;
`0x1900f5xxx` оказались branch-тунками (adrp+add+br) на реальные
функции. Резолв через nlist `.symbols` (маппинг 16.3M записей; blob
`.symbols` = {nlistOffset=0x12540, nlistCount=0xf83360, stringsOffset,
entries: 4690 образов по 8 байт} при заголовке 0x4000):

- `0x1900f58c0` → libxpc `0x1805b18c8` =
  **`_xpc_connection_get_bs_checkin_info`** — чекин читается НЕ из
  первого сообщения на проводе, а из **приватного слота соединения**:
  сериализатор `conn+0x90` + размер `conn+0x98`, one-shot (слот
  обнуляется после чтения), только peer-kind (`conn+0x18 == 2`) и
  не-live (`conn+0x40 == 0`), не listener («Attempt to fetch the
  bs_checkin_info on a live/listener/non-peer connection»);
- `0x1900f5810` → BaseBoard `BSStoreTokenFromXPCConnectionToVar`
  (audit-token → BSAuditToken → `-pid` → targetWithPid:);
- `0x1900f5910` → libxpc-регион `__xpc_*_impl` (описание для лога
  реджекта).

Доставка: КЛИЕНТ до resume заполняет слот
`xpc_connection_set_bs_type` (0x1805b1510) +
`xpc_connection_set_bs_checkin_info` (0x1805b1664, сериализует словарь,
требует bs_type ≠ NONE); при resume libxpc шлёт setup-сообщение
**'wINt'** (msgh_id 0x77494e74, чекин на +0x34) или 'w00t' (0x77303074,
без чекина); сервер-парсер копирует payload в слот (тег сериализации
0x996d4fd9, memcpy с +0x34), гейты: port-derivation (0x1805b4784,
«Failed to verify check-in connection port was derived from the
listener port») и CS-requirement («Dropping check-in message due to
code signing requirement»). bs_type: 0=NONE, 1=TBD, 2=SPECIFIC,
3=ANY; для kind==0 (соединение по имени, не из endpoint) разрешён
только TBD.

Серверные пути после чтения слота: `'mx'` в чекине → root-путь
(`configure:` 0x18faf39dc + блок-диспетчер 0x18fb01098, «Incoming root
connection is»/«Activating incoming root connection», без service
lookup); без `'mx'` → wrap (`'s'` обязателен) → lookup → «Registering
incoming connection» + диспетчер 0x18fae48b4 (теги bsxpc:
activate/connect/invalidate/interrupt; connect читает bsxpc_context +
lp). Домен extensionkitservice: mult=3 (дефолт 0x18fb15778 — в plist
нет 'Multiplexing'), идентификаторы сервисов — голые ключи plist
Services без трансформаций (строитель 0x18fb17890): Discovery/Launch/
Observer/TCCProxy.

## §204. Карта интерфейсов extensionkitservice: селекторы всех подсервисов + сигнатуры; протокол вызова (v203–v205)

### Формат вызова на живом соединении (bq54, v203)

Пробы на живом соединении (checkin {lp,s=TCCProxy} + activate-ACK):
P0 `{}` / P1 `{bsxpc_SEL:description}` / P2 `+r` / P3 `{bsxpc:description}` /
P4 `+bsxpc_CID` — молчание, соединение живо (повторный activate не
дублируется); P5 `{bsxpc:"connect", bsxpc_context:{s,i}}` — сервер
оборвал соединение («Connection interrupted»); P6 SEL через
send_message_with_reply — reply-канал вернул «Connection interrupted».
Диспетчер (0x18fae48b4 = `___…_lock_activateNowOrWhenReady:]_block_invoke.226`,
пойман целиком): dict → `+[BSXPCServiceConnectionMessage
initWithMessage:]` (0x19003b690, класс [0x1e0a80558]) →
`coderWithMessage:` (0x19003b100) → tag-ветвление: 'activate' →
0x18fb0297c; 'connect' → bsxpc_context (decodeObjectOfClass:forKey:)
+ lp + expectsReply («new child connect message shouldn't have
expectsReply»); 'invalidate'/'interrupt' → 0x18faf9114; **НЕТ тега →
0x18fae50bc — путь вызова**: гейт `[conn+0xab]==1` («Ignoring message
because the connection has been invalidated»), CID-роутинг для root
(детская таблица [conn+0x48]), иначе прямой диспатч 0x18fae69c4
(«we should never get here if we've never set up the connection
queue») → 0x18fae6f64. Вызов — reflection:
`+[BSXPCServiceConnectionProxy invokeMethod:onTarget:withMessage:
forConnection:completion:]` (0x18fae7d94) с BSObjCMethod
(argumentCount/methodForSelector:/performSelector:).

### Селекторы подсервисов (v204–v205)
