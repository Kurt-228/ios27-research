# Журнал, часть 13 (секции 68–70, 13.08.2026) — AGX command grammar

## 68. Submit end-to-end (финальная карта)

Цепочка из userland (всё проверено на устройстве, kr 0):
1. sel14 {numEntries, entrySize} — notification queue (sc[1] = entrySize!). out {userVA, id}.
2. sel6 (блоб 0x410, version u32 @+0x400 < 5) — command queue. out {qid, traceTag}.
3. sel24 {qid, nqid} — bind (иначе submit = 0x2bc молча).
4. sel12 {size, 0} — IOGPUDeviceShmem, out {userVA, size, id}. **id из этого реестра (+0x78) — то, что ждут поля записи submit** (sel8-ресурсы НЕ подходят, error 9).
5. Запись 0x40: +0x00 = kernel command shmem id (A), +0x04 = segment list shmem id (B), +0x08 = sideband (0 = нет). Submit: trap0 (p1=qid, p2=0x40, p3=entryVA, p4=outVA) или sel25 {qid, 0, count, 0x40}. Per-entry код в out: 0=ok, 8=нет kernel VA, 9=lookup fail, 0xa=format.

## 69. Грамматика стримов

**Segment list shmem (B)**: +0x08 u32 count ≥1; +0x0c hdr u32: bit31=end, bit30=has-type, bits29:0=type. type 2 = конец; type 1 = segment list: count пар {lo,hi} u32 по +0x10 — диапазоны в A (молча клампятся); type 0 (только offset 0) = submitCommandBuffer.
**Kernel command shmem (A)**: записи {u32 type @+0x00, u32 len @+0x04 (≥8, 4-align)}, типы 2..0x12 + AGX {3,4,0xb,0xe,0x10002,0x10004}. type 2 = noop (проверено: outw 0).
**AGX inner commands** (vt[20] @ 0x831d84c): magic u32 @+0x00 = 0x00010000; subtype u32 @+0xa8 ∈ {1,2,3,6,7}; must-be-zero @+0x8c; tailLen u32 @+0xa4 > 0, tail @+0xc8; OR-check @+0xac..+0xc3 ≤ 0x3ff. Тело cmd+0x08..+0xc8 → cmdObj 1:1. **tail qword'ы копируются в GPU-дескриптор без проверок диапазона** (case 2: tail+0x278/+0x2c0/+0x388 → desc поля).
- Классы дескрипторов: AGXTA/3D/CL/RemoteNode/IOSurfaceSharedEvent CommandDescriptor (kalloc 0x158..0x638).
- GPU пишет по адресам из этих дескрипторов (firmware submit TA/3D/CL channel).

## Дополнение (секция 70.1, 13.08.2026 ~23:30)
- Tail-парсеры разобраны: subtype 1 (min tail 0x9a8) и 2 (0x480) — verbatim copy в дескриптор БЕЗ валидации значений; subtype 3 — всегда принимается (fallback submit); 6 — нужны зарегистрированные events; 7 — вложенные суб-парсеры с проверками desc-полей.
- Динамика: subtype 1/2 с полными zero-tail → всё равно per-entry 0xa. Значит отказ глубже парсера — в channel-submit подготовке (fn_0x831e1ec/fn_0x831ea18): нулевой дескриптор там невалиден. Это следующий слой для статики.
- Текущий фазз (run-v63/64): мутация адресных qword'ов tail (subtype 1: +0x138/+0x140/+0x24c/+0x638; subtype 2: +0x278/+0x2c0/+0x388) — >1.2M раундов, без принятий (0xa) и без паник.
- Практический вывод: слепой фазз AGX-команд не проходит многоуровневую структурную валидацию; дальше — только управляемый крафт по полному layout'у fn_0x831e1ec (следующий раунд реверса) либо захват настоящей GPU-команды из Metal-трейса (дамп command shmem в момент submit на Mac).

## Секция 71: захваченный эталон AGX-команды (с Mac, compute dispatch)
- Настоящая subtype-3 inner command снята с macOS 27 Metal compute: len 0x358, tailLen 0x268, полный дамп в `docs/agx_cmd_template.h`, разбор по смещениям — ниже.
- Segment-list фрейминг: +0x08 count, +0x0c hdr (bit30/31), пары {lo,hi} по +0x10 с timestamp-qword'ами; kernel command shmem: записи {type,len} (type 0x0f = nop/pad).
- Tail команды ссылается на подструктуры через 32-битные offsets в multi-window shmem pool (тег 0x100 в high dword) — НЕ GPUVA. GPUVA-поля живут глубже (в окнах 0x28000/0x2a000 пула; единственный видимый: 0x07aa0177).
- Реплей на iOS (v65): шаблон с санитизированными offset'ами → 0xa. Нужны сами подструктуры (они есть в дампах /tmp/agx_regions/) — следующий шаг: встроить блобы и починить ссылки на них. Это полноценная реконструкция AGFI-дескриптора — объёмная задача.

## Секция 72: реконструкция AGFI (v66) — 0xa
- Встроил в shmem A шаблон + подструктуры из дампов (blob по 0xc8000 и т.д.) с переписанными tail-ссылками на локальные офсеты. Submit → всё ещё per-entry 0xa (молча, без IOLog). Остаются незамоделированные зависимости (вероятно: timestamp-поля segment list, поля +0x10/+0x18 записи — user-указатели на Metal-структуры, и/или ожидаемые resource-ссылки в descriptor pool'ах).
- Вывод: слепая реконструкция AGFI-дескриптора требует полного понимания Metal-стороны (MTLIOGPUCommandBuffer/AGXCommandEncoder) — это следующая отдельная сессия (реверс Metal.framework MTL*CommandBuffer machinery или доводка fn_0x831e1ec до конца).

## Секция 73: ПРОРЫВ — валидный AGX submit на iOS (v67/v68)
- Полностью валидная AGX-команда принята на устройстве: outw=0. Ключи: (а) точный фрейминг segment list из захваченного дампа (два блока: nop-запись type 0x0f + команда, timestamp-qword'ы, hdr low-bits 0x01/0xf0); (б) rec0 nop перед командой в kernel shmem; (в) валидные heap-указатели в entry +0x10/+0x18 (раньше были 0); (г) встроенные подструктуры с переписанными tail-ссылками.
- Т.е. мы теперь исполняем настоящую захваченную AGX-команду (compute dispatch subtype 3) на iOS GPU через самописный клиент без Metal. 
- Следующее для write-примитива: рекурсивно встроить зависимые блобы (blob @0x800 ссылается на окна 0x28000/0x2a000) и перенаправить буферные ссылки на наш sel8-ресурс → GPU compute-write в контролируемую память, затем за её пределы (GPUVA-фазз).

## Секция 74: итог по GPU-write (v68)
- Полная самосогласованная AGFI-образа (рекурсивное встраивание зависимостей) принимается: outw 0, стабильно. Мы исполняем настоящую compute-команду на iOS GPU без Metal.
- Наблюдаемость записи: НЕТ. 0x5A-скан адресного пространства до/после submit — без изменений (единственный хит — предсуществующий контент shmem). Запись уходит по буферным ссылкам в pool-окна (0x28000/0x2a000), которых нет ни в одном дампе (не сдамплены/ASLR), и они не маппятся на наши объекты.
- Для наблюдаемой GPU-записи нужно: найти в descriptor-цепочке поле output-buffer GPUVA и перенаправить на наш sel8-ресурс (его GPUVA из sel8 out — вероятно out+0x00 low32, напр. 0x108000). Затем GPUVA-фазз за пределы = write-примитив.
- Оценка дистанции: это уже откровенно multi-session reverse-engineering AGFI/Metal command encoding. Полная инфраструктура (протоколы, шаблон, дампы, инструменты) задокументирована и запушена.

## Секция 75: output-buffer редирект (v69) — итоговая оценка
- Output-buffer GPUVA найден: command+0x340 (GPUVA 0x1_00030000, подтверждено диффом двух прогонов + дескриптор ресурса {+0x20 gpuva, +0x28 flags|size, +0x30 cpu_va, +0x40 size}).
- Редирект на наш sel8-ресурс: submit принимается (outw 0), но записи в наш буфер НЕТ — захваченная compute-команда ссылается на скомпилированный шейдер (в других pool-структурах), без него dispatch не исполняется (no-op). Т.е. принятие на уровне парсеров есть, исполнения — нет.
- Полная рабочая compute-команда требует репликации всего Metal-стека кодирования (шейдер, pipeline state, буферные дескрипторы) — это предмет самостоятельной долгой работы (уровень Asahi-проекта по объёму).

## Секция 77: GPUVA наших ресурсов (v72/v73) — закрытие направления
- sel8 out раскладка подтверждена: out+0x00 = {lo32 = offset в client-shared пространстве (шаг 0x8000), hi32 = 0x100 (тег пространства)}; out+0x28 = wired size; out+0x30/+0x38 = токены. **GPUVA там НЕТ** — GPUVA принадлежит другому семейству адресов (тег 0x1, как у Metal output buffer 0x1_00018000) и появляется только при GPU-маппинге (sel45 mapping ops / prepare), который у нас не задействован.
- IORegistry не отдаёт IOGPUResource/AGXDevice объекты в sandbox (пусто).
- Итог: GPUVA наших ресурсов не известен → blit-редирект слеп. Для продолжения: (а) завести sel45 (mapping ops) — нужен VM-объект с attach (sel44) и memObj (ns 0x90, создаётся неясно чем — см. part11); (б) трейс Metal'овского resource binding (как GPUVA присваивается при submit prepare).

## Секция 79: почему принятые команды не пишут (финальный анализ направления)
- Mac-трейс: Metal НЕ вызывает sel45/mapping-селекторы при обычной работе — GPU-маппинг ресурсов делается неявно (при создании или submit-prepare). Значит наши sel8-ресурсы могут быть GPU-мапнуты, но blit-запись их не накрывает.
- Ключевой недостающий компонент: **device command stream** (packed AGX-пакеты, пример в дампах reg_10d460000). Принятая kernel-команда ссылается на него косвенно; без валидного device stream'а исполнение — фактический no-op. Именно stream содержит реальные GPU-операции (state setup, draw/dispatch call'ы), а kernel command — обёртку.
- Т.е. принятие (outw 0) = пройдена KEXT-валидация; исполнение на GPU требует валидного device stream'а, чей формат (packed AGX packets) — последний недекодированный слой.
