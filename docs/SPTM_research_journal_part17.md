# Журнал, часть 17 (секция 86, 14.08.2026) — JPEG-трек: разведка боем

## 86. AppleJPEGDriver из App-Sandbox (v93, фаза p_jpeg, env FUZZ_JPEG=1)

Цель: аппаратный JPEG-декодер (DMA-класс: рассинхрон размеров из JPEG SOF vs dst
surface — кандидат из part9 §57: sel7 SOF 0xffff×0xffff).

### Разведка
- Сервис в registry один: `AppleJPEGDriver` (матчинги SJPEGDriver/AppleH16JPEG
  не найдены; в KC-строках есть ещё `SJPEGDriverUserClient` — отдельного сервиса
  на устройстве нет).
- **IOServiceOpen принимает ЛЮБОЙ type** (0..8, 0x100, 0x1000, 0x10000,
  0x100000..0x100005) с kr 0 — type-blind newUserClient, что само по себе
  признак деградированного/стабового клиента (настоящие per-type клиенты type
  валидируют).
- Класс коннекта прочитать нельзя (IOObjectGetClass → 0xe00002c2, как в v87).

### Карта селекторов (полная, все формы вызова)
sel 0..9 × {CallStructMethod, CallAsyncMethod(wake+ref), CallScalarMethod,
CallMethod(scalar+struct), CallMethod stIn{0x1d0,0x2c8,0x3c0}×stOut{0x100,0x1d0,
0x1000}, IOConnectTrap0/1} × types {0..8, 0x100..0x100005}:
**ВСЁ 0xe00002c2 (kIOReturnUnsupported)**. Ни один селектор ни в одной форме не
дошёл до dispatch. (run-v93{,b,c,d,e}.log)

### Вывод
С нашими entitlements userclient не имеет ни одного доступного метода — клиент
деградирован (вероятно, полный клиент создаётся только для entitled-процессов;
в KC-строках видны гейты com.apple.applejpegdriver.poweron (sel 8/9) и
com.apple.applejpegdriver.ajpegtestapp). Sanity decode и SOF-фазз через прямой
userclient из App-Sandbox **невозможны без entitlement'а** — трек закрыт на
этом этапе. Альтернативный путь к декодеру — через mediaserverd/ImageIO
(косвенно, без контроля над struct'ами) — для DMA-фаззинга бесполезен.

Статика для будущего: /tmp/AppleJPEGDriver.macho (extract_fileset.py), но
fileset-extract теряет chained fixups → таблица externalMethod не восстанавливается
наивным поиском text-ptr'ов; при возврате к треку — декодировать
LC_DYLD_CHAINED_FIXUPS или анализировать newUserClient на предмет entitlement-веток
(строки гейтов известны).

## 87. DART-домен скейлера: PERSISTENT + SHARED, cross-request write подтверждён (v94)

Фаза `p_dartmap` (env FUZZ_DARTMAP=1, FUZZ_DART_STEP=0..3, run-v94{,b,c,d}.log).
База: killshot-пейлоад (sel1, dst rect 32×32 в 64×64 BGRA, flags bit28,
border X=Y=32 W=H=0xFFFFFFE0, цвета 0xff) — baseline: panic (bug 210) в 30–50%
выстрелов, иначе 0xe00002d6.

### Эксперименты

- **E1 (step 0)**: легитимный scale 2048×2048 (2×16MB поверхности) → kr 0;
  затем 10 killshot'ов на ТОМ ЖЕ коннекте: **10/10 recoverable (0xe00002d6),
  ни одной паники** (baseline 30–50%/shot → p≈0.001 за чистую удачу).
  Маппинги переживают запрос — домен НЕ per-request.
- **E2 (step 1)**: то же, но killshot'ы на СВЕЖЕМ втором коннекте (после big-map
  на первом): **10/10 recoverable** — маппинги первого коннекта видны второму:
  домен **shared между коннектами** (общий DART context скейлера).
- **E4 (step 3)**: большая dst (16MB) заполнена page-маркерами (байт = номер
  страницы), легально замаплена нормальным scale; затем 6 killshot'ов с
  маленьким dst. CPU-readback: **4080/4096 страниц повреждены** (первая — уже
  страница 1, оффсет 0x1000) — *** CROSS-REQUEST WRITE CONFIRMED ***.
  Паттерн записи: страницы **зануляются** (ff 0 / zero 4096 / other 0) — цвета
  0xff из пейлоада НЕ проходят (видимо, premultiply/format path), пишется 0x00.
  Охват — практически весь extent легального маппинга (~16MB).

### Вердикт (ИСПРАВЛЕН v95, см. секцию 88)

DART-домен AppleM2ScalerCSCDriver — **persistent + shared**: маппинги живут
после завершения запроса и общие между userclient-коннектами. ~~wraparound-запись
попадает в страницы, замапленные ДРУГИМИ запросами~~ — ОТОЗВАНО: E4-«порча»
маркеров была артефактом (легитимный scale затирал маркеры нулями ДО killshot'а;
в v95 markers-after-scale контроль это вскрыл). Статистический аргумент E1/E2
(10/10 recoverable после big-map при baseline-паниках 30–50%) под вопросом:
возможна временна́я гонка в fault-handling, а не персистентность. См. секцию 88.

## 88. v95: контрольный эксперимент — cross-request write НЕ подтверждается

Фазы `p_dartval` (FUZZ_DARTVAL) / `p_dartaim` (FUZZ_DARTAIM), run-v95{,b,c}.log.

**Ключевой контроль**: в E4-схеме v94 маркеры заливались ДО легитимного scale,
который пишет в ту же dst-поверхность нулями (src = свежий нулевой IOSurface) —
вся «порча 4080 страниц» объяснялась самим scale. В v95 маркеры заливаются ПОСЛЕ
легитимного scale (+200 мс на завершение), сканируются ОБЕ поверхности (src и dst,
разные маркерные базы +0x80):

- CONTROL (без killshot): 0 порчи ✓ (схема измерения чистая).
- 8 вариантов killshot (цвета 0xff/0xffff/ffffffff/alpha-варианты): kr 0xe00002d6
  (recoverable) или 0xe00002c2 (отвергнуто невалидным alpha), **порчи нет ни в
  src-, ни в dst-губке** (32 МБ замаплено легально).

Выводы:
1. Recoverable-исход (0xe00002d6) = запрос прерван с DART-фолтом БЕЗ записи в
   наблюдаемые маппинги. Подтверждённой записи по контролируемому/наблюдаемому
   адресу у нас НЕТ — ни в свои замапленные страницы, ни в чужие.
2. Паника bug 210 (write fault DVA 0x1000003c000) остаётся единственным
   подтверждённым эффектом: запись ИДЁТ по адресу, не покрытому нашими
   маппингами (даже 32 МБ легального extent её не перехватывают) — целевой DVA
   фиксирован параметрами wrap'а и не совпадает с layout'ом наших поверхностей.
3. «Persistent+shared» из v87: статистика E1/E2 (20/20 recoverable) больше не
   считается доказательством — вероятна гонка в fault-handling (большой легальный
   запрос перед killshot'ом сдвигает тайминги к recoverable-исходу).
4. Controlled value (задача A) и прицел (задача B) в текущей постановке
   бессмысленны без точки записи в наблюдаемую память — приостановлено.

Следующий шаг по скейлеру: снять ТОЧНЫЙ fault-DVA для серии dst-size (E3,
FUZZ_DART_STEP=2) и понять формулу write-адреса от W/H/X/Y — тогда можно будет
подобрать параметры так, чтобы запись попала в наш замапленный extent
(адресная арифметика wrap'а из дизасма validateBorderFill, 4 сайта).

## 89. v96: формула записи и поиск точки падения (статика + динамика)

### Статика (AppleM2ScalerCSCDriver-iOS27.macho, mackc/)

validateBorderFill (4 сайта 32-bit wrap @0xfffffff008f81504/528/54c/570):
проверки вида `add w10, w9, w8; cmp` — складывают border-поля
(state+0xc4c/0xc50/0xc54/0xc58 = X/Y/W/H из request +0xac..+0xb8) с dst rect
полями request (+0x20..+0x2c) — сложение 32-битное, overflow не проверяется
(при X=32, W=0xFFFFFFE0 сумма = 0x10 → «влезает»).
Потребитель (строительство HW-дескриптора, ~0xfffffff008f8c2d4):
`add w26, w8(borderW=[x19+0xc54]), w26(dstW-pole)` / `add w24, w8(borderH), w24`,
затем **`and w4, w26, #0x1ffff`** (и w24 аналогично) — поля дескриптора
маскируются до 17 бит и уходят через виртуальные вызовы (blraa) в дескриптор
(оффсеты ~0x2dc/0x2e0). Т.е. в железо уходят W'=(borderW+dstW)&0x1FFFF,
H'=(borderH+dstH)&0x1FFFF: для baseline W=H=0xFFFFFFE0, dstW=H=32:
W'=H'=(0x100000000)&0x1FFFF = **0** — вероятно, трактуется как 0x20000
(полный диапазон) — отсюда гигантский span. Точная формула write_start_DVA
статически не добрана (descriptor→register programming выложен через vtable
blraa-цепочки; требует полного трека по HAL) — зафиксированы якоря:
0xf8c2d4/0xf8c344/0xf8c370.

### Динамика (run-v96{,b,c,d,e}.log)

- **Чистый контроль** (giant dst 4096×4096=64MB, settle 1s, маркеры после
  wire, NOSHOT): 0 порчи — схема измерения корректна.
- **Killshot с giant dst**: recoverable 0xe00002d6, **0 порчи** — wrap-запись
  не попадает даже в 64MB нашего dst. (В первой попытке с settle 100мс видели
  16128 байт «порчи» — это поздний writeback легального scale, артефакт гонки.)
- **Вывод**: цель записи — НЕ наша dst-поверхность вообще. Запись идёт в
  внутренний буфер драйвера/HW scratch по DVA, не связанному с dst DVA
  пользователя; переполнение → fault по фиксированному DVA 0x1000003c000
  (для baseline-пейлоада; обе исторические паники results/panics-* дают ровно
  его). Recoverable-путь в syslog пишет только MSR-статусы
  (MSR_CTRL_DBGSTS=0x1628, MSR_GLBL_IRQSTS=0x2, "MSR Error Occurred") — DVA
  без паники не светится.
- 18 выстрелов с dst 1024×1024 в этой сессии: 0 паник (исторические 30–50%
  не воспроизвелись — rate зависит от состояния системы).

### Итоговый статус 0-day

- Подтверждённый примитив: DoS-паника bug 210 из App-Sandbox (rate нестабилен).
- Запись: идёт в служебный/внутренний маппинг (вне пользовательских поверхностей);
  управления адресом через X/Y/W/H не получено — formula unresolved.
- Следующий шаг (если возвращаться): полная деобфускация HAL-программирования
  (blraa-цепочки от 0xf8c344), либо fault-DVA серия по размерам через паники
  (дорого: reboot+unlock на точку).



## 91. Deep probe v97-находок (v98, фаза p_deepprobe, run-v98{,b}.log)

- **IOCoreSurfaceRoot** (бывш. IOSurfaceRoot; матчится также как класс
  "IOSurfaceRoot"): открывается ТОЛЬКО type 0 (0x1..0x100005 → 0x2c7), но живых
  struct-селекторов 0..30 и трапов 0..3 нет — публичный IOSurface-путь приложений
  идёт иначе (XPC/спецклиент); новой поверхности тут нет.
- **AppleCLCD2** (display pipe): types 0-3 × sel 0..40 × формы
  struct(0x200)/scalar(4)/async/trap — ВСЁ закрыто: 0xe00002c2 на вызовы,
  0xe00002f0 (unimplemented) на трапы. Клиент деградирован как у JPEG (v93) —
  методы требуют entitlement'а (display-драйвер mediaserverd/backboardd).
- **AppleKeyStore** (недеструктивно, только нулевые struct'ы): sel 0/1/16 принимают
  ЛЮБОЙ stInSize 0x8..0x400 с kr 0, stOut — нули (infoleak'а на нулевом вводе нет;
  вероятно validate-and-noop). sel 8/19 → 0xe00002e2 (entitlement), sel 5/6 →
  0xe00002c1, sel 17 → 0xe00002f0. Семантику sel 5/6 (возможно unlock/wrap)
  не трогали.

Вывод: нового write-примитива разведка не дала. CLCD2 закрыт entitlement'ом
(как JPEG). AKS живые селекторы для нас — пустышки без семантики; копать глубже
нельзя без риска для keybag. Открытые направления без изменений: GPU read/leak
(v90) + write-в-свои-ресурсы (v89) + scaler DoS panic (bug 210).

## 92. Широкая фазз-кампания скейлера (v99, фаза p_scalerfuzz, run-v99.log)

**sel11** — это статический getter информации/caps драйвера: kr 0 на любом
stInSize, возвращает структуру 0x298 байт (отрезает по stIn), первые поля
`13 00 00 00 04 00 0e 00 01 01 01...`, содержимое не меняется после scale —
state-independent. Доступен на types 0-3 (как и sel1). Фаззить нечего (вход
игнорируется).

**Полевая мутация sel1** (baseline = валидный scale 64×64→64×64): 108 оффсетов
× 10 значений {0, 1, 0x7fffffff, 0x80000000, 0xfffffffe, 0xffffffff, ±1, <<8,
×0x1000} = 1080 кейсов + 11 экстремальных комбо (srcWH/crop/dstWH/rect2 pairs
с ffff..ffff, 0x80000000, wrap-пары) — всего **1091 кейс, 0 крашей, 0 паник**:
- off 0x00/0x04 (surface IDs): мусор → 0xe00002f0 (invalid surface);
- off 0x20..0x34, 0x60..0x6c, 0x110, 0x138, 0x160, 0x188: часть значений → 0x2c2;
- всё остальное (включая ВСЕ комбо с экстремальной геометрией) — kr 0,
  без аномалий выхода и без паники.

Вывод: валидация sel1 устойчива к пофоловой мутации; единственный найденный класс
— border-fill wrap (требует структурной комбинации X+W wrap, не ловится
однополевым фаззом). Кампания закрыта; дальнейший прогресс по скейлеру — только
через формулу write-DVA (секция 89) или новые селекторы/форматы.

## 93. X/Y-wrap: запись ВНУТРЬ нашей поверхности подтверждена (v100, p_xywrap)

Идея: validateBorderFill заворачивает все 4 поля; до этого крутили только W/H.
Вариант **Y=0xFFFFFFF0, H=0x20** (Y+H ≡ 0x10 mod 2^32 — валидация проходит)
при giant dst 4096×4096 (64MB, чистая схема v96: wire → settle 1s → маркеры):

- **Y-wrap РАБОТАЕТ: kr 0xe00002d6, порча страниц 0x0..0x4b000** (~300KB,
  ~78k qword'ов) внутри нашего dst — первая подтверждённая запись killshot'ом
  в пользовательскую поверхность (воспроизводится 3/3 прогонов).
- Записываемое значение — **0x00** при любых валидных цветах (0xff и 0x01
  дают идентичную картину; невалидные цвета (4/3/2/1) → 0x2c2). Нулевой
  zero-fill — вероятно, color pipeline зануляет (premultiply/format).
- X-wrap (X=0xFFFFFFF0, W=0x20): recoverable, но порчи в dst нет (пишет куда-то
  ещё / не выполняется).
- Окно валидации узкое: соседние Y (0xFFFFFFE8, 0xFFFFFFF4, 0xFFFFFFF8...) →
  0x2c7/0x2c2. Принимается только Y=0xFFFFFFF0,H=0x20.
- Прицел в scratch (0x1000003c000): не достигнут — write-start для Y-wrap ложится
  на dst+0 (наша база), смещение его выше/ниже требует Y, отклоняемых
  валидацией. Прицеливание за пределы extent не выполнено.

Формула (эмпирически): write-область при Y=0xFFFFFFF0 = [dst_base, dst_base+0x4c000),
зануление. X/Y-управление стартом в допустимом окне валидации не найдено —
единственная точка = Y=0xFFFFFFF0. Паник в v100 не было.

Статус примитива: **zero-fill ~300KB в нашей собственной поверхности** через
невалидируемый wrap — шаг от DoS к write-примитиву показан концептуально
(запись реально выполняется в маппинг пользователя, а не только в scratch),
но управления адресом (за пределы нашего буфера) пока нет.

## 94. Охота за значением и span-формула (v101, фаза p_valhunt, run-v101{,b..f})

### Форматы (step 0)
| формат | wire | запись | байты |
|---|---|---|---|
| BGRA (ctrl) | 0 | 77792 qwords | 0x00 |
| L008 (luma8, без альфы) | 0 | 19440 qwords | **0x00** — premultiply-гипотеза мертва |
| L00h (luma16) | 0 | 38896 qwords | 0x00 |
| 420v / 420f | 0 | 24440 qwords | 0x00 |
| 24RGB/24BGR/2C08/64RA/b64a | 0x2c7 (scale не поддержан) | — | — |

Даже в форматах без альфа-канала пишется 0x00 → зануление НЕ из premultiply;
цветовые поля request (+0xbc..+0xc8) не доходят до железа на этом пути вообще.

### CSC-охота (step 1, 432 кейса план)
Оффсеты 0x00..0x114 × {1.0f, 2.0f, 0x10000, 0xffffffff}: записанное значение
всегда 0x00, kr всегда 0x2d6 — ни одно поле не влияет на значение. ДВА HANG'а
драйвера (синхронный вызов не возвращается; без паники): **off 0x084 =
0x00010000** и **off 0x114 = 0x3f800000** — live-lock DoS точки (эти поля
влияют на исполнение — кандидаты на coefficient/scale поля). Диапазон
0x118..0x1ac не сканирован (resume: FUZZ_VALHUNT_SKIP=277). Темп ~11 с/кейс
(recoverable fault-путь медленный).

### Span-формула (step 2)
- H варьируется мертво (0x40/0x100 → тот же extent 0x4bf80; 0x10 → 0x2c7).
- **X-wrap+Y-wrap комбо (X=0xFFFFFFF0, Y=0xFFFFFFF0): kr 0x00000000** (чисто
  принято!) и extent линеен по W: W=0x20 → 4032 qwords, 0x40 → 6048, 0x80 →
  10080 ⇒ **N_qwords ≈ 2016 + 63·W** (≈ 8064 + 252·W байт; 252 ≈ 0xFC ≈ один
  row-fragment на единицу W). Значение всё так же 0x00.
- W=0xFFFFFFF0/0xFFFFFFC0 (без X-wrap) → 0x2c7/0x2c2.

Итог: controlled value не получен (записанное значение не зависит ни от одного
поля request ни от формата — всегда 0x00); span управляем линейно через W при
двойном wrap, и такой запрос принимается с kr 0 (без recoverable-фолта!) —
технически это «молчаливое» повреждение собственной поверхности на контролируемую
длину. Управления старт-адресом по-прежнему нет (старт = dst+0).

## 95. Overrun в shared DART-домен (v102, фаза p_overrun, run-v102{,b..g}.log)

### Карта гейтов валидации (эмпирически, Y-wrap пейлоад)
Пейлоад Y=0xFFFFFFF0/H=0x20 проходит ТОЛЬКО на достаточно больших поверхностях:
PASS (0x2d6): 4096×4096, 4096×1024, 4096×256, 4096×64, 2048×2048, 2048×1024,
1024×4096, 1024×1024. FAIL (0x2c2): 4096×32, 2048×32, 64×64. Правило ≈
min(W,H) ≥ 64 ∧ max(W,H) ≥ 1024. X-wrap на мелких поверхностях тоже отсекается.
Это объясняет, почему ранние killshot'ы (64×64) паниковали через иной путь
(scratch), а рабочий in-surface путь требует большой dst.

### Семантика recoverable
Уточнена косвенно: при Y-wrap с in-extent записью — kr 0x2d6 И порча есть
(v100/v101), т.е. 0x2d6 НЕ означает откат; запись частичная/полная до фолта.
При dst 64MB+ порчи нет вовсе (v96) — запись по W'=0 маске идёт в scratch
(вне пользовательского DVA). Зависимость extent'а от геометрии не линейна —
часть пути идёт через внутренний буфер.

### Adjacency/overrun попытки
Серии на мелких поверхностях (64×64, 2048×32) — shot отклоняется гейтом (0x2c2).
На 1024×64 (256KB, gate PASS) серия из 16 поверхностей с маркерами:
**устройство ушло в панику/оффлайн в середине прогона run-v102g** (devicectl
потерял устройство; оффлайн >10 минут — вероятно паника bug 210 на одном из
выстрелов с overrun за пределы поверхности). Лог прогона остался в контейнере
приложения на устройстве — забрать Documents/fuzz.log после возвращения
устройства (он переживает ребут), panic log — idevicecrashreport в
results/panics-v102/. Номер выстрела-убийцы будет виден по хвосту лога.

### Промежуточный итог v102
- Запись подтверждена только внутри наших поверхностей (v100/v101), span
  линеен по W (N≈2016+63W qwords), двойной wrap принимается с kr 0.
- Overrun за пределы поверхности через shared-домен — правдоподобен, но
  приводит к панике устройства (v102g) — т.е. соседние страницы либо
  незамаплены (fault), либо чужие и запись в них фатальна для системы.
  Точный исход — по логу/панике после анлока.
- Железо/драйвер после серии фолтов живёт нестабильно: hang-точки (v101)
  + паника здесь.

## 96. Cross-surface write: паники и DVA-анализ (v102g/v103, фаза p_xproof)

Статика (из дизасма дескриптор-строителя, сек. 89/94): Y-wrap fill стартует с
dst_base + sign17(Y&0x1FFFF)·pitch; для Y=0xFFFFFFF0 → Y' = −16 строк (при
pitch 0x1000 → **base − 0x10000**) и идёт вперёд span'ом ≈ 8064+252·W байт.

### Забор улик и panic-DVA
- run-v102g (adjacency, 1024×64): лог контейнера ПУСТ после ребута (паника
  теряет page cache; лечится fsync перед выстрелом — внесено в p_xproof).
  Panic: bug 210, **write DVA 0x10000040000** (базовая серия v56: 0x1000003c000).
  Сдвиг +0x4000 соответствует большему замапленному extent запроса — т.е.
  wrap-запись идёт ВПЕРЁД до конца маппингов домена и фолтит на границе:
  request mapping ≈ max(0x3c000, surface+slack); 256KB-поверхность → 0x40000.
- p_xproof (4×1024×64, все legit-wired, маркеры после settle, dst=B/C/D/A):
  устройство паникует на ранних выстрелах (дважды подряд — run-v103/103b,
  логи потеряны до внесения fsync; после fsync — не успели проверить).
  Panic #2: bug 210, **READ DVA 0x10000094000** — чтение! Составной вывод:
  поверхности в DVA-домене НЕ смежны (есть дыры; wrap-траверсал попадает в
  дыру → фолт). Чтение фолтит раньше записи на этом пути.

### Выводы
1. Cross-surface write через DVA-смежность наших поверхностей НЕ подтверждён:
   аллокатор DVA оставляет дыры → wrap-траверсал фолтит (panic bug 210),
   а не течёт в соседнюю поверхность. Две паники подряд на p_xproof.
2. DVA-оракул из паник работает: fault-адрес = граница замапленного extent
   запроса (0x10000040000 при 256KB surface). READ-fault 0x10000094000 показывает,
   что и read-путь wrap'а (src-side?) участвует в траверсале.
3. Стоп по паникам (2 за серию, устройство требует анлок). Возобновление:
   FUZZ_XPROOF_SKIP=<shot#> после забора fsync-лога из контейнера
   (должен пережить панику теперь) + panic-full-*.ips из results/panics-v102/.

## 97. Groom shared-домена (v104, фаза p_groom, run-v104.log)

- Плотная серия: 32 поверхности 4096×64 (1MB), все legit-wired, маркеры — ок.
- Выстрелы с X-wrap+W=0x1000 (X=0xFFFFF010) — **отклоняются валидацией 0x2c2**
  (W ограничена surfW через второй сайт; рабочее окно W ≤ 0x80 на 4096-ширине
  из v101). S1/S2/S3 — все 0x2c2, паник нет, устройство живо.
- Геометрический тупик направления: принимаемые span'ы (≤ ~40KB при W≤0x80
  double-wrap; ~300KB при X=32-пути v100) МЕНЬШЕ гранулярности поверхностей
  (≥256KB по gate-карте min≥64∧max≥1024) — перекрыть соседнюю нашу поверхность
  невозможно; а выход за пределы extent = дыра DVA → panic bug 210
  (подтверждено v102g: write DVA 0x10000040000 ровно на границе домена).
- Побочно: push v103 долго не уходил из-за sysdiagnose (1.4GB) в panics-v102 —
  почищено (.gitignore: results/panics-*/), коммит 1ce5fb6 на origin/main.

Итог направления scaler-write: zero-fill только внутри своей поверхности
(span-контроль через W), overrun → panic. Эскалация записи в чужое закрыта
геометрией домена. Остаётся: DoS-паника (bug 210) + hang-точки (v101) +
GPU read/leak трек.
