# Журнал, часть 8 (секции 52–54, 13.08.2026) — классификация и границы примитива

## 52. Паника классифицирована: bug_type 210, DART write fault

`panic-full-2026-08-13-072843.0002.ips`:
```
panic(cpu 0 caller 0xfffffff03af8f83c): "dart-scaler (0xffffffe529dd6000):
DART(DART) error: SID 0 PTE invalid exception on write of DVA 0x1000003c000
(CTE 0x10 SEG 0 PTE 0xf) ERROR_STATUS 0x90080008 ..." @AppleT8110DART.cpp:2265
```
- Kernel: xnu-13432.0.94.502.2 RELEASE_ARM64_T8122, iOS 27.0 (24A5390f), socRevision 0x11.
- Запись пошла за пределы маппинга dst surface'а и уперлась в невалидный PTE на DVA `0x1000003c000` (окно scaler-домена ~2^40+). DART сконфигурирован фатально → kernel panic (не WDT, как предполагалось; ~50 с «жизни» после MSR error — обработчик/ретраи до фатального пути).
- Паника недетерминирована: 2 из ~6 kill-shot'ов → panic-full, остальные — recoverable MSR error (0x2d6) с выжившим устройством. Вероятно зависит от фазы/контекста фолта.

## 53. Оружейные эксперименты (v20–v25) — все отрицательные

Цель: заставить заливку писать в контролируемую память вместо фолта.
- v20: 300 surface'ов, созданных после dst — не замаплены в scaler DART-домен (маппинг только при wire). 0 порчи.
- v21: большие surface'ы (64 МБ) вокруг dst — 0 порчи. GetDiag DVA не содержит (только счётчики/таймстампы).
- v22: **wire-grooming** (200 surface'ов проведены через трансформы до kill-shot) — 0 порчи. Вывод: маппинги в домене не персистентны (unmap после трансформа) или размещаются не смежно.
- v23: E1 (420f biplanar dst) — первый прогон показал «8192 байт порчи @0x2000», но это была неинициализированная chroma (ложная тревога, проверено полной заливкой 0x33 → 0 изменений). E2 (src 4096²) — 0. E3 (dst 4096²) — 0 записей вообще (для большого dst геометрия tiled, фолт мгновенный).
- v24: flip/rotate t=0..3 с huge src — 0 порчи (направление записи не разворачивается в src).
- v25: flip × 420f/420v dst — 0 порчи (плоскости маппятся несмежно/в другом порядке).

**Текущий потолок примитива**: заливка стартует внутри dst и фолтит на первой странице за концом luma-маппинга. В scaler DART-домене в момент запроса присутствуют только src+dst текущего запроса; страница за dst всегда незамаплена. Управляемой записи пока не получено — это **надёжный 0-day DoS (kernel panic из sandboxed-приложения без entitlements)**, не write-примитив.

Открытые статические вопросы для апгрейда: кеширует ли mapIOSurface маппинги per-client (unmap-on-completion?), есть ли способ продлить жизнь маппинга (async-запросы в полёте?), как выбирается DVA внутри окна (аллокатор DART-домена), можно ли удержать «подушку» замапленной через параллельный async-трансформ в момент kill-shot (race: fill пишет, пока второй запрос держит соседние страницы замапленными).

## 54. Итоговая оценка находки

**AppleM2ScalerCSCDriver border-fill validation bypass (iOS 27.0b4, A17/t8130):**
- 32-битный wraparound в четырёх проверках границ border-fill rect (iOS kext @ 0xfffffff008f81504/0x8f81528/0x8f8154c/0x8f81570).
- Достижимо из любого приложения через IOSurfaceAccelerator (или прямой IOConnectCallMethod sel 1); entitlements не требуются.
- Валидный пейлоад: dst rect 32×32 в буфере 64×64, border X=Y=32, W=H=0xFFFFFFE0, цвета 0xff (2^n−1), crop сужен соответственно.
- Эффект: DART write fault → kernel panic bug_type 210 (воспроизводимость ~30–50% на kill-shot; иначе recoverable HW error 0x2d6).
- CVSS-оценка: локальный DoS ядра (panic по требованию), потенциал эскалации зависит от DART-груминга (см. открытые вопросы).
- Репорт-готовность: пейлоад-репродюсер в `fuzzer/t_iosurface_scaler.m` (p_borderfill/baseline2 + kill-shot), паник-логи в `results/panics-v19b/`.

### Дополнение: v26 async-cushion race (финальный эксперимент)
10 раундов × 8 in-flight async-трансформов (64→2048 upscale на 2048² cushion-surface'ах) с kill-shot в момент полёта — устройство живо, порчи cushion'ов нет. In-flight async-запросы не создают смежных маппингов в DART-домене. Оружейные идеи в рамках текущего знания исчерпаны; находка зафиксирована как 0-day kernel DoS (validation bypass → DART write fault → panic bug_type 210).
